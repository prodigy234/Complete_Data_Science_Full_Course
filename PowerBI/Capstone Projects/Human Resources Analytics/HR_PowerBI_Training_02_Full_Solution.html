1. Loading & Cleaning the Data

1.1 Importing the Workbook

  • Open Power BI Desktop, choose Get Data > Excel Workbook, and select HR_Analytics_PowerBI_Training_Dataset.xlsx.
  • In the Navigator window, tick Employees, Dim_Department, Dim_JobTitle, Dim_Location, Dim_Education, Dim_Date and Fact_PerformanceReviews. Leave ReadMe and Data_Dictionary unticked - they are reference sheets for humans, not data for the model.
  • Click Transform Data rather than Load, so every table opens in Power Query first and nothing is loaded until it has been checked.

1.2 Setting Correct Data Types

Power Query usually infers types correctly from a clean Excel table, but every type should still be checked explicitly, because a wrongly typed column (for example a date stored as text) will silently break relationships and DAX later with no obvious error message.

1.3 Cleaning Steps

  • Apply Trim and Clean to FirstName, LastName, DepartmentName, JobTitle, City and Country to strip any stray whitespace, as a defensive habit even on a clean dataset.
  • Use Remove Duplicates on each Dim_ table's primary key column to confirm each key genuinely appears only once - an important pre-relationship sanity check.
  • Confirm TerminationDate is genuinely blank (null), not an empty text string, for every Active employee.

1.4 Building the Helper Columns

JobLevelSortOrder (in Dim_JobTitle)

Add a Conditional Column in Power Query mapping JobLevel to a numeric sort order:

if [JobLevel] = "Entry" then 1
else if [JobLevel] = "Mid" then 2
else if [JobLevel] = "Senior" then 3
else if [JobLevel] = "Lead" then 4
else if [JobLevel] = "Manager" then 5
else if [JobLevel] = "Director" then 6
else 7

After loading, select the JobLevel column in Report view, open Column tools > Sort by column, and choose JobLevelSortOrder. Every visual using JobLevel on an axis now displays in correct seniority order automatically.

TenureBucket (in Employees)

if [TenureYears] < 1 then "0-1 yr"
else if [TenureYears] < 3 then "1-3 yrs"
else if [TenureYears] < 5 then "3-5 yrs"
else "5+ yrs"

PromotionGapBucket (in Employees)

if [YearsSinceLastPromotion] < 1 then "0-1 yr"
else if [YearsSinceLastPromotion] < 2 then "1-2 yrs"
else if [YearsSinceLastPromotion] < 3 then "2-3 yrs"
else "3+ yrs"

Both bucket columns can be built either as a Conditional Column in Power Query (shown above) or as a DAX calculated column using nested SWITCH(TRUE(), ...) logic.

1.5 Disabling Auto Date/Time

Before building any relationships, open File > Options and settings > Options, go to Current File > Data Load and Global > Data Load, and untick Auto date/time. Power BI's automatic hidden date tables would otherwise silently create a second, invisible date hierarchy behind every date column, competing with the purpose-built Dim_Date table.

2. Data Modelling: Relationships & Cardinality

This is the single most important part of the entire build. A wrong cardinality or cross-filter direction here will produce visuals that look plausible but quietly report the wrong numbers.

Dim_Department[DepartmentID] → Employees[DepartmentID]

Standard dimension-to-fact relationship. One department has many employees; each employee belongs to exactly one department.

Dim_JobTitle[JobTitleID] → Employees[JobTitleID]

One job title is held by many employees; each employee has exactly one current job title.

Dim_Location[LocationID] → Employees[LocationID]

One location houses many employees; each employee is assigned to exactly one location.

Dim_Education[EducationID] → Employees[EducationID]

One education combination applies to many employees; each employee has exactly one education record.

Dim_Date[Date] → Employees[HireDate]

Drives headcount, new-hire and workforce-growth visuals. This is the relationship Power BI uses automatically whenever a visual is filtered by the Dim_Date table without extra DAX.

Dim_Date[Date] → Employees[TerminationDate]

Powers attrition-by-month/quarter/year trends. Because it is inactive, every measure that needs it must explicitly invoke USERELATIONSHIP(Dim_Date[Date], Employees[TerminationDate]) inside CALCULATE.

Dim_Date[Date] → Fact_PerformanceReviews[ReviewDate]

Drives all performance and engagement trend visuals built from the review fact table.

Employees[EmployeeID] → Fact_PerformanceReviews[EmployeeID]

Each employee can have several yearly performance reviews; each review belongs to exactly one employee. This is the link that lets department, job level and location slice the review fact table even though those attributes do not exist directly on Fact_PerformanceReviews.

2.2 Relationships Deliberately NOT Built

Not every matching pair of ID columns should become a relationship. Two examples are included in this dataset specifically to teach that judgement call:

Employees[EmployeeID] to Employees[ManagerID]

This is a self-referencing (parent-child) relationship. Power BI does not allow a table to relate to itself through a standard relationship in the model diagram in a way that supports normal filtering. Instead, build an organisational hierarchy with the PATH() and PATHITEM() DAX functions, or use the built-in 'Parent-Child hierarchy' quick pattern. This is presented as an optional advanced exercise.

Dim_JobTitle[DepartmentID] to Dim_Department[DepartmentID]

Although Dim_JobTitle contains a DepartmentID column, it is deliberately left unrelated in the core model. Employees already links directly to both Dim_Department and Dim_JobTitle, so adding this third relationship would create a second filter path between Dim_Department and Employees (one direct, one via Dim_JobTitle). Power BI would force one of the two paths to be inactive to avoid an ambiguous filter, adding complexity with no analytical benefit here. This is used as a teaching example of when NOT to build a relationship just because a matching key column exists.

2.3 Understanding Cardinality

  • One-to-Many (1:*): one row in the 'one' table (a Dim_ table) can match many rows in the 'many' table (Employees or Fact_PerformanceReviews). Every relationship in this model uses this cardinality.
  • Many-to-Many (*:*): both sides can have multiple matches. Technically supported but avoided here, since it can produce ambiguous or double-counted results.
  • One-to-One (1:1): each row on both sides matches exactly one row on the other side. Also avoided, since it usually signals the two tables should simply be merged.

2.4 Understanding Cross-Filter Direction

Single direction (used throughout this model) means the 'one' side (a Dim_ table) filters the 'many' side, but not the other way around. This is the correct, safe default for a star/snowflake schema and should only change to Both when a specific visual genuinely requires bidirectional filtering - which does not occur anywhere in this model.

2.5 Active vs Inactive Relationships

A table can only have one active relationship path to another table at a time. Because Employees has two date columns that both logically relate to Dim_Date (HireDate and TerminationDate), both relationships can exist, but only HireDate is active by default. TerminationDate must be built as Inactive (a dashed line in Model view), and then explicitly activated inside individual DAX measures with USERELATIONSHIP - see the Attrition Rate % (Trend) measure in Section 3.

2.6 Model View Checklist

  • Every relationship line in Model view shows a '1' at the Dim_ end and a '*' (many) at the Employees or Fact_PerformanceReviews end.
  • The Dim_Date to TerminationDate line is dashed (inactive); every other line is solid (active).
  • No relationship line shows a warning icon (which would indicate an ambiguous or many-to-many relationship).
  • Dim_Date has a calendar icon, confirming it has been marked as the official date table.
  • Foreign key columns are hidden from Report view.

3. DAX Measures, Explained Line by Line

Every measure below follows the same structure: the exact DAX formula, a line-by-line breakdown, why the measure is needed, and its specific impact on the finished dashboard. Build these in the order given - several later measures reuse earlier ones.

1. Core Workforce Measures

Total Employees

Total Employees = COUNTROWS ( Employees )

Line-by-line explanation:

  • COUNTROWS ( Employees ) counts every row currently visible in the Employees table given whatever filters are active in the visual.
  • There is no CALCULATE wrapper because no filter override is needed - the measure should simply respect whatever the visual is already filtering by (department, location, and so on).

Why this measure was written this way: This is the foundation measure almost every other workforce measure divides into or compares against. It also becomes the denominator for every percentage-based measure below.

Impact on the dashboard: Used as the headline KPI card on the Executive Overview page, and as the base of every bar and column chart that shows 'headcount by X'.

Active Employees

Active Employees = CALCULATE ( [Total Employees], Employees[EmploymentStatus] = "Active" )

Line-by-line explanation:

  • CALCULATE changes the filter context that [Total Employees] is evaluated in.
  • Employees[EmploymentStatus] = "Active" is a simple filter argument that overrides any existing filter on that column and restricts the row set to active staff only.
  • Wrapping the existing [Total Employees] measure (rather than writing COUNTROWS again) keeps the logic in one place - if the definition of 'total' ever changes, this measure inherits the change automatically.

Why this measure was written this way: Distinguishes current, working headcount from historical headcount that includes people who have since left.

Impact on the dashboard: Drives the 'Active Employees' KPI card and is the denominator for every rate that should only consider the current workforce, such as average salary of current staff.

Terminated Employees

Terminated Employees = CALCULATE ( [Total Employees], Employees[EmploymentStatus] = "Terminated" )

Line-by-line explanation:

  • Mirrors Active Employees but filters the opposite status.
  • Because EmploymentStatus only ever holds two values, Active Employees + Terminated Employees will always reconcile back to Total Employees, which is a useful validation check to show students.

Why this measure was written this way: The numerator for attrition rate and the base count for every 'who left and why' visual.

Impact on the dashboard: Feeds the Attrition & Retention dashboard page KPI cards and the termination-reason donut chart.

Average Tenure (Years)

Average Tenure (Years) = AVERAGE ( Employees[TenureYears] )

Line-by-line explanation:

  • AVERAGE ( Employees[TenureYears] ) takes the simple arithmetic mean of the TenureYears formula column that was pre-computed in Excel.
  • Because TenureYears already accounts for whether an employee is active (measured to today) or terminated (measured to their termination date), no extra CALCULATE logic is required here.

Why this measure was written this way: Tenure is one of the single strongest predictors of attrition risk in real HR analytics, and a simple, honest average is the right first metric before building tenure buckets.

Impact on the dashboard: Displayed as a KPI card on both the Executive Overview and Attrition pages, and used as the source field for the tenure-bucket bar chart.

Average Age

Average Age = AVERAGE ( Employees[AgeYears] )

Line-by-line explanation:

  • Straightforward average over the AgeYears formula column.

Why this measure was written this way: Gives a quick generational profile of the workforce, useful context for succession-planning discussions.

Impact on the dashboard: Used in a KPI card and as a secondary axis on the workforce-profile visual on the Executive Overview page.

2. Attrition & Retention Measures

Attrition Rate %

Attrition Rate % = DIVIDE ( [Terminated Employees], [Total Employees], 0 )

Line-by-line explanation:

  • DIVIDE is used instead of the / operator because DIVIDE safely returns the third argument (0 here) instead of throwing a divide-by-zero error whenever a filter context produces zero total employees, for example a department with no historical headcount at all.
  • The result is a decimal fraction (for example 0.152) that is formatted as a percentage in the visual, not multiplied by 100 in the DAX itself - formatting belongs in the model, not the formula.

Why this measure was written this way: This is the single most requested HR KPI in almost every real-world Power BI HR project.

Impact on the dashboard: The headline KPI card on the Attrition & Retention page, and the value plotted on the attrition trend line chart.

Voluntary Attrition %

Voluntary Attrition % = DIVIDE ( CALCULATE ( [Terminated Employees], Employees[TerminationReason] IN { "Voluntary - Better Opportunity", "Voluntary - Relocation", "Voluntary - Career Change", "Voluntary - Further Education", "Voluntary - Personal Reasons" } ), [Total Employees], 0 )

Line-by-line explanation:

  • The inner CALCULATE narrows Terminated Employees down further, to only the rows whose TerminationReason starts with 'Voluntary'.
  • IN { ... } is used instead of five separate OR conditions, which keeps the filter argument compact and easy to extend if a new voluntary reason category is added later.
  • DIVIDE by the unfiltered [Total Employees] (not by Terminated Employees) so the result answers 'what share of the whole workforce left voluntarily', which is the version HR leaders usually want first.

Why this measure was written this way: Voluntary and involuntary attrition need very different management responses, so leadership almost always wants them split apart rather than blended into one number.

Impact on the dashboard: One of two stacked segments in the Attrition Type donut chart and a KPI card on the Attrition page.

Involuntary Attrition %

Involuntary Attrition % = DIVIDE ( CALCULATE ( [Terminated Employees], Employees[TerminationReason] IN { "Involuntary - Performance", "Involuntary - Restructuring", "Involuntary - Policy Violation" } ), [Total Employees], 0 )

Line-by-line explanation:

  • Same structure as Voluntary Attrition %, filtered to the three involuntary reason categories instead.

Why this measure was written this way: Completes the voluntary/involuntary split so the two measures always sum to the overall Attrition Rate %, which is another useful in-class validation exercise.

Impact on the dashboard: The second segment of the Attrition Type donut chart.

Attrition Rate % (by termination date, time intelligence)

Attrition Rate % (Trend) = VAR TerminatedInPeriod = CALCULATE ( [Total Employees], Employees[EmploymentStatus] = "Terminated", USERELATIONSHIP ( Dim_Date[Date], Employees[TerminationDate] ) ) VAR HeadcountAtStart = [Active Headcount (Cumulative)] RETURN DIVIDE ( TerminatedInPeriod, HeadcountAtStart, 0 )

Line-by-line explanation:

  • USERELATIONSHIP ( Dim_Date[Date], Employees[TerminationDate] ) temporarily activates the otherwise-inactive relationship between Dim_Date and Employees[TerminationDate] for the duration of this CALCULATE only, without disturbing the default active relationship on HireDate anywhere else in the model.
  • VAR TerminatedInPeriod stores how many employees have a termination date inside whatever month/quarter/year the visual's axis is currently showing.
  • VAR HeadcountAtStart reuses the cumulative active-headcount measure defined below, giving a more meaningful denominator than simply the current filter's total employees.
  • RETURN DIVIDE (...) safely produces the final rate, guarding against a zero denominator in early periods before the company had any staff.

Why this measure was written this way: This is the measure that actually lets a line chart show attrition rate changing month by month or year by year - without it, every period would show the same flat overall Attrition Rate %, because the default relationship in this model is on HireDate, not TerminationDate.

Impact on the dashboard: The single most important measure on the Attrition & Retention dashboard page - it is what makes the attrition trend line chart move at all, and is a deliberate teaching moment about active versus inactive relationships.

Active Headcount (Cumulative)

Active Headcount (Cumulative) = CALCULATE ( [Total Employees], FILTER ( ALL ( Dim_Date ), Dim_Date[Date] <= MAX ( Dim_Date[Date] ) ), Employees[HireDate] <= MAX ( Dim_Date[Date] ), OR ( Employees[TerminationDate] > MAX ( Dim_Date[Date] ), ISBLANK ( Employees[TerminationDate] ) ) )

Line-by-line explanation:

  • FILTER ( ALL ( Dim_Date ), Dim_Date[Date] <= MAX ( Dim_Date[Date] ) ) removes the visual's own date filter and rebuilds it as 'every date up to and including the current period', which is what turns a single month into a running, cumulative total.
  • Employees[HireDate] <= MAX ( Dim_Date[Date] ) keeps only employees who had already joined by that point in time.
  • OR ( Employees[TerminationDate] > MAX ( Dim_Date[Date] ), ISBLANK ( Employees[TerminationDate] ) ) keeps only employees who either had not yet left by that date, or have never left at all (a blank TerminationDate).
  • Together the three conditions reconstruct, for any date on the axis, exactly how many people were actually employed on that date - true point-in-time headcount, not a same-period count.

Why this measure was written this way: A simple COUNTROWS filtered by month would only show people hired in that specific month, not the running total of everyone employed - this is one of the most common beginner mistakes in HR headcount reporting, so it is included deliberately as a teaching measure.

Impact on the dashboard: Powers the Headcount Trend line chart on the Executive Overview page and is reused inside the Attrition Rate % (Trend) measure above.

Average Tenure at Exit

Average Tenure at Exit = CALCULATE ( AVERAGE ( Employees[TenureYears] ), Employees[EmploymentStatus] = "Terminated" )

Line-by-line explanation:

  • AVERAGE ( Employees[TenureYears] ) is wrapped in CALCULATE with a filter down to only terminated employees.
  • Because TenureYears was computed relative to TerminationDate for terminated staff (see the Excel formula), this correctly measures how long people typically stayed before leaving, not their tenure as of today.

Why this measure was written this way: Distinguishes 'people who barely started and left quickly' from 'people who left after a long, healthy career', which need very different retention responses.

Impact on the dashboard: A KPI card on the Attrition & Retention page, often shown next to Average Tenure (Years) for contrast.

3. Compensation Measures

Average Salary

Average Salary = AVERAGE ( Employees[AnnualSalaryUSD] )

Line-by-line explanation:

  • A direct average over the AnnualSalaryUSD column, respecting whatever department, job level or location filters are active.

Why this measure was written this way: The baseline compensation benchmark for every other pay comparison in the workbook.

Impact on the dashboard: A KPI card and the value plotted on the Average Salary by Job Level bar chart.

Median Salary

Median Salary = MEDIAN ( Employees[AnnualSalaryUSD] )

Line-by-line explanation:

  • MEDIAN returns the middle value of the AnnualSalaryUSD distribution in the current filter context, rather than the arithmetic mean.

Why this measure was written this way: Salary distributions are typically right-skewed by a small number of very highly paid executives, so the median is a more honest 'typical employee' figure than the average, and comparing the two teaches students why both matter.

Impact on the dashboard: Shown alongside Average Salary as a paired KPI card so the gap between them is visible at a glance.

Total Payroll Cost

Total Payroll Cost = SUM ( Employees[AnnualSalaryUSD] )

Line-by-line explanation:

  • SUM aggregates AnnualSalaryUSD across every row currently in context.

Why this measure was written this way: Finance and executive stakeholders think in total cost, not averages, so this measure translates the same underlying column into a budgeting-relevant figure.

Impact on the dashboard: A KPI card on the Compensation & Diversity page, and the basis for the Budget Utilisation % measure below.

Budget Utilisation %

Budget Utilisation % = DIVIDE ( CALCULATE ( [Total Payroll Cost] ), CALCULATE ( SUM ( Dim_Department[DepartmentBudgetUSD] ), ALLEXCEPT ( Employees, Employees[DepartmentID] ) ), 0 )

Line-by-line explanation:

  • The numerator CALCULATE ( [Total Payroll Cost] ) simply re-evaluates payroll cost in whatever context the visual is already in - department, division, or business unit.
  • The denominator sums Dim_Department[DepartmentBudgetUSD] but wraps it in ALLEXCEPT ( Employees, Employees[DepartmentID] ), which removes every filter coming from the Employees table except the department filter itself - this prevents a job-level or gender slicer from accidentally shrinking the budget figure, which should only ever change when the department changes.
  • DIVIDE again guards against a department with no budget recorded.

Why this measure was written this way: Shows what percentage of each department's allocated budget is actually being consumed by salaries, a very common real-world Finance-and-HR crossover metric.

Impact on the dashboard: A gauge or KPI card on the Compensation page, and a deliberately more advanced measure used to teach ALLEXCEPT versus a plain CALCULATE.

Gender Pay Gap %

Gender Pay Gap % = VAR AvgMale = CALCULATE ( [Average Salary], Employees[Gender] = "Male" ) VAR AvgFemale = CALCULATE ( [Average Salary], Employees[Gender] = "Female" ) RETURN DIVIDE ( AvgMale - AvgFemale, AvgMale, 0 )

Line-by-line explanation:

  • Two variables independently recalculate Average Salary filtered to Male and Female employees respectively, ignoring whatever the current Gender filter (if any) is - CALCULATE's explicit filter argument overrides it.
  • The RETURN line expresses the gap as a percentage of the male average, the most common convention used in real pay-equity reporting, again guarded by DIVIDE.

Why this measure was written this way: Pay equity is one of the most requested analyses in modern HR analytics and a natural showcase for variables used to compare two differently-filtered versions of the same base measure.

Impact on the dashboard: A KPI card on the Compensation & Diversity page, ideally shown with a clear note that this is a simple unadjusted gap, not a role-adjusted statistical analysis.

4. Performance & Engagement Measures

Average Performance Rating

Average Performance Rating = AVERAGE ( Employees[PerformanceRatingLastReview] )

Line-by-line explanation:

  • A direct average of the most recent rating snapshot stored on the Employees table.

Why this measure was written this way: Gives a current-state performance benchmark without needing to touch the review history fact table.

Impact on the dashboard: A KPI card on the Performance & Engagement page.

Average Engagement Score

Average Engagement Score = AVERAGE ( Employees[EngagementScorePercent] )

Line-by-line explanation:

  • Straightforward average over the current-snapshot engagement column.

Why this measure was written this way: Engagement is consistently one of the top three metrics HR leadership tracks, alongside attrition and headcount.

Impact on the dashboard: A KPI card, and the field driving conditional formatting (colour) on several matrix visuals.

High Performer %

High Performer % = DIVIDE ( CALCULATE ( [Total Employees], Employees[PerformanceRatingLastReview] >= 4 ), [Total Employees], 0 )

Line-by-line explanation:

  • The inner CALCULATE filters down to employees whose most recent rating is 4 or 5 out of 5.
  • Dividing by the unfiltered [Total Employees] shows what proportion of the whole (currently filtered) workforce are high performers.

Why this measure was written this way: Talent-density is a key input to succession planning and retention prioritisation - you protect your high performers first.

Impact on the dashboard: A KPI card and the value plotted by department on the High Performer bar chart.

Average Review Rating (History)

Average Review Rating (History) = AVERAGE ( Fact_PerformanceReviews[PerformanceRating] )

Line-by-line explanation:

  • Unlike Average Performance Rating above, this measure reads from Fact_PerformanceReviews, which holds one row per employee per review year.
  • Because the grain is different, this average is a true multi-year average across every historical review, not just the latest snapshot.

Why this measure was written this way: Lets students directly compare a 'current snapshot' measure against a 'full history' measure built from a proper fact table, reinforcing why the fact table exists at all.

Impact on the dashboard: The value plotted on the multi-year Engagement & Performance trend line chart, broken out by ReviewYear from Dim_Date.

Promotion Recommended Rate

Promotion Recommended Rate = DIVIDE ( CALCULATE ( COUNTROWS ( Fact_PerformanceReviews ), Fact_PerformanceReviews[PromotionRecommended] = "Yes" ), COUNTROWS ( Fact_PerformanceReviews ), 0 )

Line-by-line explanation:

  • The numerator counts only review rows where the manager ticked 'Yes' for promotion recommendation.
  • The denominator counts every review row in the current context, so the result is 'what share of reviews resulted in a promotion recommendation', which can be sliced by department, job level, or review year.

Why this measure was written this way: A leading indicator of internal mobility and career progression health, useful alongside YearsSinceLastPromotion.

Impact on the dashboard: A bar chart broken down by department on the Performance & Engagement page.

Average Training Hours

Average Training Hours = AVERAGE ( Employees[TrainingHoursLastYear] )

Line-by-line explanation:

  • A direct average of the TrainingHoursLastYear column.

Why this measure was written this way: Connects development investment to the performance and engagement metrics sitting next to it, inviting a natural correlation discussion in class.

Impact on the dashboard: A KPI card and one axis of the Training Hours vs Performance scatter chart.

5. Talent & Workforce Planning Measures

New Hires (Period)

New Hires (Period) = CALCULATE ( [Total Employees], USERELATIONSHIP ( Dim_Date[Date], Employees[HireDate] ) )

Line-by-line explanation:

  • Although Dim_Date[Date] to Employees[HireDate] is already the active relationship in this model, USERELATIONSHIP is still written explicitly here as defensive, self-documenting DAX - if a future student later makes the TerminationDate relationship active instead, this measure keeps working correctly without silently breaking.
  • Because there is no extra status filter, this measure simply counts every employee whose HireDate falls in the period the visual is currently showing.

Why this measure was written this way: The direct count of people who joined in a given month, quarter or year - the mirror image of the attrition trend measure.

Impact on the dashboard: The New Hires by Month bar chart on the Talent & Workforce Planning page.

Net Headcount Change

Net Headcount Change = [New Hires (Period)] - CALCULATE ( [Total Employees], Employees[EmploymentStatus] = "Terminated", USERELATIONSHIP ( Dim_Date[Date], Employees[TerminationDate] ) )

Line-by-line explanation:

  • Reuses [New Hires (Period)] for the joiners side.
  • Subtracts a CALCULATE that counts terminations in the same period using the same USERELATIONSHIP pattern seen in the attrition trend measure above.

Why this measure was written this way: A single number that tells leadership whether the organisation grew or shrank in a given period, combining both relationships in one measure.

Impact on the dashboard: Plotted as a column chart with New Hires and Terminations shown alongside it for context.

Average Years Since Last Promotion

Average Years Since Last Promotion = AVERAGE ( Employees[YearsSinceLastPromotion] )

Line-by-line explanation:

  • A direct average over the YearsSinceLastPromotion column.

Why this measure was written this way: A simple stagnation-risk indicator - long gaps since the last promotion correlate strongly with voluntary attrition in real organisations.

Impact on the dashboard: A KPI card, and the source field for the Years Since Promotion bucket bar chart (0-1, 1-2, 2-3, 3+ years).

Remote Work %

Remote Work % = DIVIDE ( CALCULATE ( [Total Employees], Employees[WorkModel] = "Remote" ), [Total Employees], 0 )

Line-by-line explanation:

  • The inner CALCULATE isolates employees whose WorkModel equals Remote.
  • Dividing by the unfiltered [Total Employees] gives the remote share of whatever population the visual is currently showing.

Why this measure was written this way: Work-model mix is now a standard, expected metric on any modern workforce-planning dashboard.

Impact on the dashboard: One segment of the Work Model donut chart on the Talent & Workforce Planning page.

Average Span of Control

Average Span of Control = VAR DirectReportCounts = ADDCOLUMNS ( VALUES ( Employees[ManagerID] ), "@Reports", CALCULATE ( COUNTROWS ( Employees ) ) ) RETURN AVERAGEX ( FILTER ( DirectReportCounts, [ManagerID] <> BLANK () ), [@Reports] )

Line-by-line explanation:

  • VALUES ( Employees[ManagerID] ) produces the distinct list of every ManagerID that appears in the current filter context.
  • ADDCOLUMNS (...) adds a virtual @Reports column next to each manager, using CALCULATE ( COUNTROWS ( Employees ) ) to count how many employees currently have that ManagerID.
  • FILTER (..., [ManagerID] <> BLANK ()) removes the one row representing employees with no manager (the CEO), so a missing manager does not distort the average.
  • AVERAGEX then iterates that virtual table and averages the @Reports value across every manager.

Why this measure was written this way: Span of control (average team size per manager) is a classic organisational-design metric, and this measure is deliberately included as the most advanced DAX pattern in the course - it introduces table functions, virtual columns and iterators together.

Impact on the dashboard: A KPI card on the Talent & Workforce Planning page, presented in class as the 'capstone' measure students should attempt last.

4. Building the Dashboards

The finished report has five pages. Every chart below lists its exact type, the fields placed in each well, and why it was designed that way. Build the pages in order given, since several pages reuse a pattern introduced on an earlier page.

Page 1 - Executive Workforce Overview

Purpose: A single-screen summary a CHRO or CEO can read in under a minute: how big is the workforce, where are people, and is it growing or shrinking.

KPI Card Row 5 Card visuals

5. Final QA Checklist & Publishing

5.1 Data Model QA

  • All eight relationships present with correct 1:* cardinality and Single cross-filter direction.
  • Dim_Date to TerminationDate confirmed Inactive; every other relationship confirmed Active.
  • Dim_Date marked as the official date table.
  • No orphaned rows: every DepartmentID, JobTitleID, LocationID and EducationID in Employees exists in its Dim_ table.

5.2 DAX QA

  • Every measure exists, is correctly formatted (%, currency, or whole number as appropriate), and has a description.
  • Voluntary Attrition % + Involuntary Attrition % = Attrition Rate %, checked on at least three different department filters.
  • Active Employees + Terminated Employees = Total Employees, checked with no filters applied.
  • Attrition Rate % (Trend) actually changes month to month on the line chart (if it is flat, the USERELATIONSHIP call was likely written incorrectly).

5.3 Dashboard QA

  • All five pages present with the exact titles given in Section 4.
  • Every chart renders with no blank, overlapping, or error-displaying visuals.
  • A single consistent theme and colour palette is applied across all five pages.
  • Cross-filtering works as expected: clicking a bar on any chart correctly filters the other visuals on the same page.
  • Slicers (department and date range) are synced across all five pages.

5.4 Publishing

  • Save the .pbix file with a clear version number in the filename.
  • Publish to a Power BI workspace (Home > Publish), selecting the appropriate workspace.
  • Once published, open the report in the Power BI Service and confirm every visual renders identically to Power BI Desktop before sharing the link with stakeholders.
