Operations Sheet: Operations

Daily production output, downtime and quality performance across all BUA plants.

1. Column-by-column data dictionary 12 columns

ColumnTypeBusiness description
RecordIDTextUnique ID for each production log entry
Production DateDateDate the shift ran, stored as mixed text/date formats
LocationIDTextPlant where production happened, links to Dim_Location
Product LineTextProduct manufactured (Cement, Sugar, Flour, Pasta, Steel)
ShiftTextMorning, Afternoon or Night shift
Units ProducedNumberTotal units produced in the shift, stored as text with thousand separators
Downtime HoursNumberHours the line was not running
Quality Reject RatePercentShare of output rejected at QC, stored as text with % sign
Machine IDTextEquipment identifier
SupervisorIDTextEmployeeID of the shift supervisor, links to Dim_Employee
DepartmentIDTextLinks to Dim_Department (always DPT01)
RemarksTextFree-text shift notes

2. Data quality problems planted in this sheet 8 problems

  • Problem: Production Date mixes at least three formats in one column: 12/01/2025, 2025-01-12 and 1-Dec-25, so Power BI reads the column as Text instead of Date.
  • Problem: Units Produced is stored as text because of thousand-separator commas (e.g. "12,450"), so it cannot be summed.
  • Problem: Quality Reject Rate is stored as text with a trailing % sign (e.g. "4.5%") instead of a numeric percentage.
  • Problem: Downtime Hours has blank cells for shifts with zero downtime instead of a 0, which breaks average calculations.
  • Problem: Shift values are inconsistently capitalised: "morning", "Morning ", "MORNING" all appear for the same shift.
  • Problem: Product Line has trailing/leading spaces and inconsistent naming ("Cement", "cement ", "CEMENT BAGS") for the same product.
  • Problem: A handful of rows are exact duplicates from a copy-paste error during month-end consolidation.
  • Problem: Remarks contains stray double spaces and non-printable characters copied from email.

3. Power Query cleaning tasks - work these out yourself

  1. Fix the Production Date column so every row is a true Date type, regardless of which of the three source formats it started as.
  2. Convert Units Produced into a clean whole number that can be summed and used in a visual.
  3. Convert Quality Reject Rate into a true decimal percentage field.
  4. Replace blank Downtime Hours with 0 and set the column's data type to a Decimal Number.
  5. Standardise Shift into exactly three values: Morning, Afternoon, Night.
  6. Standardise Product Line into a clean, consistent list of product names.
  7. Remove duplicate rows introduced by the copy-paste error.
  8. Trim and clean the Remarks column of extra spaces and non-printable characters.

4. Relationships to build in the Power BI model

  • Operations[LocationID] -> Dim_Location[LocationID] (many-to-one)
  • Operations[DepartmentID] -> Dim_Department[DepartmentID] (many-to-one)
  • Operations[SupervisorID] -> Dim_Employee[EmployeeID] (many-to-one)
  • Operations[Production Date] -> Dim_Date[Date] (many-to-one, mark Dim_Date as the model's Date Table)

5. DAX measures to build - specification only

  1. Total Units Produced - a measure summing production across the whole table.
  2. Average Downtime per Shift - a measure showing the average downtime hours per shift.
  3. Overall Reject Rate % - a measure computing the weighted reject rate across all production, not a simple average of the row-level percentages.
  4. MoM Production Growth % - a measure comparing this month's Total Units Produced to the prior month.
  5. Downtime % of Available Time - a measure expressing downtime as a percentage of scheduled shift hours.

2. Data quality problems planted in this sheet 7 problems

  • Problem: Risk Level is entered as "High", "high", "HIGH " and even "Hi" for the same category.
  • Problem: Contract/Claim Value is stored as text such as "N4,500,000" and "₦2.3m", mixing full figures with abbreviated millions.

  • Problem: Status has synonyms for the same state: "Open", "Ongoing", "In Progress" all mean the same thing.
  • Problem: Counterparty names for the same organisation are spelled differently across rows ("Dangote Ltd", "Dangote Limited", "DANGOTE").

3. Power Query cleaning tasks - work these out yourself

  1. Standardise Risk Level into exactly three values: Low, Medium, High.
  2. Convert Contract/Claim Value into a single clean numeric Naira column, resolving the "₦2.3m" style entries into full numbers.
  3. Find and correct or flag impossible dates in Filing Date and Next Action Date.
  4. Consolidate Status into a clean set of values: Open, Closed, Under Review.
  5. Fix inconsistent Counterparty spellings so the same organisation always reads identically.
  6. Decide on and apply a rule for blank Handling OfficerID values (e.g. tag as "Unassigned").
  7. Strip the leading numbering from Case Title.

4. Relationships to build in the Power BI model

  2. Open High-Risk Cases - a count of cases that are both High risk and still Open.
  3. Average Case Age (Days) - average number of days an open case has been outstanding.
  4. Cases by Officer Workload - a measure supporting a table of open case count per Handling Officer.

2. Data quality problems planted in this sheet 7 problems

  • Problem: Supplier Name has multiple spellings for the same supplier ("Dangote Ltd", "DANGOTE LIMITED", "Dangote Ltd" with a double space).
  • Problem: Quantity Ordered and Unit Price are both stored as text due to commas and currency symbols.
  • Problem: Total Value does not always equal Quantity Ordered x Unit Price because it was typed manually rather than calculated.
  • Problem: Delivery Status has overlapping free-text values: "Delivered", "delivered", "Fully Delivered", "Complete".
  • Problem: Actual Delivery Date is blank for orders that are Pending or Cancelled, which is correct, but also blank for a few orders marked Delivered - a genuine data error to catch.
  • Problem: Category values are inconsistently capitalised and one entry is simply blank.
  • Problem: A few Expected Delivery Date values are stored as serial numbers (e.g. 45678) instead of dates because of an Excel formatting slip.

3. Power Query cleaning tasks - work these out yourself

  1. Standardise Supplier Name so every variant of the same supplier reads identically.
  2. Convert Quantity Ordered and Unit Price into clean numeric columns.
  3. Recalculate Total Value from clean Quantity Ordered and Unit Price rather than trusting the source figure, and flag rows where the source figure disagreed.
  4. Standardise Delivery Status into four clean categories: Pending, Delivered, Delayed, Cancelled.
  5. Identify and flag rows marked Delivered with a blank Actual Delivery Date as an exception for follow-up.
  6. Clean Category, filling or flagging the blank entry.
  7. Fix Expected Delivery Date values that were stored as serial numbers so they display as real dates.

4. Relationships to build in the Power BI model

  • Supply Chain[DepartmentID] -> Dim_Department[DepartmentID] (many-to-one)
  • Supply Chain[LocationID] -> Dim_Location[LocationID] (many-to-one)
  • Supply Chain[RequestedByID] -> Dim_Employee[EmployeeID] (many-to-one)
  • Supply Chain[PO Date] -> Dim_Date[Date] (many-to-one)

5. DAX measures to build - specification only

  1. Total Purchase Value - sum of Total Value across all POs.
  2. On-Time Delivery % - share of delivered orders where Actual Delivery Date <= Expected Delivery Date.
  3. Average Lead Time (Days) - average days between PO Date and Actual Delivery Date.
  4. Top Suppliers by Spend - a measure supporting a ranked table/chart of supplier spend.

Cross-department data model - tasks

The workbook is deliberately built as a star schema: Dim_Employee, Dim_Department, Dim_Location and Dim_Date sit in the centre as lookup (dimension) tables, and the eleven department sheets (Operations, Legal, Supply Chain, Admin, Customer Service, IT, Accounts and Finance, Internal Control, Risk Management, Compliance, plus the HR master itself acting as Dim_Employee) are the fact tables around them. Every fact table carries a DepartmentID and, where relevant, a LocationID and one or more EmployeeID columns, so the whole model can be sliced consistently by department, site, officer and date from a single set of shared filters.

Model-building tasks

  1. Load all fifteen sheets into Power BI and confirm each department fact table lands with the correct data types after your Power Query cleaning steps.
  2. Build a dedicated Dim_Date table (either with Power Query's date table pattern or a CALENDAR() DAX table) spanning the full range of dates found across every fact table.
  3. Create the relationship from Dim_Department[DepartmentID] to each fact table's DepartmentID column - all should be one-to-many, single direction, from Dim_Department to the fact table.
  4. Create the relationship from Dim_Location[LocationID] to each fact table's LocationID column.
  5. Create the relationship from Dim_Employee[EmployeeID] to the primary EmployeeID-style column on each fact table (SupervisorID, HandledByID, RequestedByID, ApprovedByID, Responsible OfficerID, Risk OwnerID, Handling OfficerID as appropriate).
  6. Where a fact table has a second EmployeeID-style column (for example IT's AssignedToID, Admin's ApprovedByID), create that relationship as inactive and activate it inside specific measures with USERELATIONSHIP.
  7. Relate every fact table's date column to Dim_Date[Date], and mark Dim_Date as the model's official Date Table (Table Tools > Mark as Date Table) so time intelligence functions work correctly.
  8. Build a self-referencing relationship on Dim_Employee (EmployeeID to SupervisorID) to support organisational-hierarchy analysis.
  9. Set every fact-to-dimension relationship's cross-filter direction to Single, and confirm no circular or ambiguous relationships remain by checking the Model view for warning icons.
