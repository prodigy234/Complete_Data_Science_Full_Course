Operations - Full Solution

Daily production output, downtime and quality performance across all BUA plants.

1. Power Query cleaning - worked solution, step by step

Step 1.Fix the Production Date column so every row is a true Date type, regardless of which of the three source formats it started as.

Use Transform > Data Type > Date first; where it returns errors, use Add Column > Custom Column with Date.FromText combined with a Text.Replace / Text.Split branch that tests for "-" separators and month names, or simply use Table.TransformColumns with a try/otherwise wrapping three parse attempts (each source format), then keep the first one that succeeds. In practice: right-click the column > Change Type > Using Locale (English-United Kingdom, Date) resolves the day/month formats, then a Conditional Column patches the "1-Dec-25" style rows before the final date conversion.

Step 2.Convert Units Produced into a clean whole number that can be summed and used in a visual.

Select Units Produced > Transform > Data Type > Text (to freeze it as text) > Transform > Format > Clean, then Replace Values "," with "" (empty), then Transform > Data Type > Whole Number.

Step 3.Convert Quality Reject Rate into a true decimal percentage field.

Select Quality Reject Rate > Replace Values "%" with "" (empty) > Change Type to Decimal Number > Add Column: Custom Column [RejectRate] / 100, or simply change the column format to Percentage after removing the % text and dividing by 100.

Step 4.Replace blank Downtime Hours with 0 and set the column's data type to a Decimal Number.

Select Downtime Hours > Transform > Replace Values: null with 0 > Change Type > Decimal Number.

Step 5.Standardise Shift into exactly three values: Morning, Afternoon, Night.

Select Shift > Transform > Format > Trim, then Format > Capitalize Each Word, then use Replace Values to fold any remaining variants (e.g. "Night " ) into the three canonical values.

Step 6.Standardise Product Line into a clean, consistent list of product names.

Select Product Line > Format > Trim > Format > Capitalize Each Word > Replace Values to merge variants such as "Cement Bags" into "Cement".

Step 7.Remove duplicate rows introduced by the copy-paste error.

Use Home > Remove Rows > Remove Duplicates on the full row (or on RecordID once RecordID is confirmed unique) after the cleaning steps above, so duplicates create identical rows and are caught reliably.

Step 8.Trim and clean the Remarks column of extra spaces and non-printable characters.

Select Remarks > Transform > Format > Trim and Format > Clean to strip non-printable characters and collapse double spaces.

3. DAX measures - full formulas

Total Units Produced= SUM('Operations'[Units Produced]) -- a simple additive measure once Units Produced is a clean Whole Number.
Average Downtime per Shift= AVERAGE('Operations'[Downtime Hours]) -- use AVERAGEX if you need to average by a grouping such as plant: AVERAGEX(VALUES('Operations'[LocationID]), CALCULATE(AVERAGE('Operations'[Downtime Hours]))).
Overall Reject Rate %= DIVIDE(SUMX('Operations','Operations'[Units Produced]*'Operations'[Quality Reject Rate]), SUM('Operations'[Units Produced])) -- a weighted average avoids the distortion of averaging percentages from shifts of very different sizes.
MoM Production Growth %= VAR CurrentM = [Total Units Produced] VAR PriorM = CALCULATE([Total Units Produced], DATEADD('Dim_Date'[Date], -1, MONTH)) RETURN DIVIDE(CurrentM - PriorM, PriorM) -- requires a marked Date table related to Production Date.
Downtime % of Available Time= DIVIDE(SUM('Operations'[Downtime Hours]), SUM('Operations'[Downtime Hours]) + (COUNTROWS('Operations') * 8)) -- assumes an 8-hour standard shift; swap in a real scheduled-hours column if BUA tracks one.

Legal - Full Solution

Contract, litigation and legal-risk case tracking across BUA's operating companies.

1. Power Query cleaning - worked solution, step by step

Step 1.Standardise Risk Level into exactly three values: Low, Medium, High.

Select Risk Level > Format > Trim > Format > Lowercase, then Replace Values to map "hi"/"high" to "High", "med"/"medium" to "Medium", "low" to "Low", finishing with Format > Capitalize Each Word for a clean display value.

Step 2.Convert Contract/Claim Value into a single clean numeric Naira column, resolving the "₦2.3m" style entries into full numbers.

Split the column logic with a Conditional Column: if the text contains "m" (after removing the ₦ / N symbol) multiply the numeric part by 1,000,000, else parse the full number directly; implement with Text.Contains, Text.Remove of non-numeric characters, and Number.FromText, wrapped in an if-then-else custom column, then set the result to Currency/Fixed Decimal.

Step 3.Find and correct or flag impossible dates in Filing Date and Next Action Date.

Add a Custom Column that flags rows where Date.Day is greater than the number of days in that month (or simply where the Try...Otherwise date conversion errors out); route flagged rows to a review query instead of silently converting them.

Step 4.Consolidate Status into a clean set of values: Open, Closed, Under Review.

Use Replace Values to map "Ongoing" and "In Progress" to "Open", keeping "Closed" and "Under Review" as-is.

Step 5.Fix inconsistent Counterparty spellings so the same organisation always reads identically.

Trim and uppercase a helper column, then use Replace Values / a manual mapping table (Merge Query against a small Counterparty lookup table) to standardise names such as Dangote, BUA competitors, and government agencies.

Step 6.Decide on and apply a rule for blank Handling OfficerID values (e.g. tag as "Unassigned").

Use Replace Values null -> "Unassigned" on Handling OfficerID once the column type is confirmed Text.

Step 7.Strip the leading numbering from Case Title.

Use Text.PositionOf / a Custom Column with Text.Middle, or Split Column by Delimiter on ". " (period-space) keeping the text after the first split, to strip the leading numbering.

Supply Chain - Full Solution

Purchase orders, supplier performance and inventory movement for BUA's procurement function.

1. Power Query cleaning - worked solution, step by step

Step 1.Standardise Supplier Name so every variant of the same supplier reads identically.

Trim, uppercase for comparison, collapse repeated spaces (Text.Combine(Text.Split(...),)), then Merge Query against a small Supplier lookup table keyed on a cleaned name to snap every variant to one canonical Supplier Name.

Step 2.Convert Quantity Ordered and Unit Price into clean numeric columns.

Format > Clean and Replace Values to strip commas and currency symbols/spaces, then Change Type to Whole Number (Quantity) and Fixed Decimal Number (Unit Price).

Step 3.Recalculate Total Value from clean Quantity Ordered and Unit Price rather than trusting the source figure, and flag rows where the source figure disagreed.

Add a Custom Column [Calculated Total] = [Quantity Ordered] * [Unit Price], then Add Column [Value Mismatch Flag] = if Number.Round([Total Value],2) <> Number.Round([Calculated Total],2) then "Review" else "OK", and use the calculated column as the trusted Total Value going forward.

Step 4.Standardise Delivery Status into four clean categories: Pending, Delivered, Delayed, Cancelled.

Trim, lowercase, Replace Values to map "fully delivered"/"complete" to "delivered", then Capitalize Each Word for the final four-value list.

Step 5.Identify and flag rows marked Delivered with a blank Actual Delivery Date as an exception for follow-up.

Add a Custom Column [Delivery Data Issue] = if [Delivery Status] = "Delivered" and [Actual Delivery Date] = null then "Missing Actual Date" else null, and route flagged rows to an exceptions query for the Supply Chain team to fix at source.

Step 6.Clean Category, filling or flagging the blank entry.

Trim and Capitalize Each Word on Category; Replace Values null -> "Uncategorised" so the blank is visible rather than silently excluded from visuals.

Step 7.Fix Expected Delivery Date values that were stored as serial numbers so they display as real dates.

Change Type on Expected Delivery Date to Date - Power Query converts a valid Excel serial number automatically once the column type is set correctly; confirm no rows land on 1899-12-30 (the classic sign of a genuine text value being misread).

Cross-department data model - full solution

The workbook is deliberately built as a star schema: Dim_Employee, Dim_Department, Dim_Location and Dim_Date sit in the centre as lookup (dimension) tables, and the eleven department sheets (Operations, Legal, Supply Chain, Admin, Customer Service, IT, Accounts and Finance, Internal Control, Risk Management, Compliance, plus the HR master itself acting as Dim_Employee) are the fact tables around them. Every fact table carries a DepartmentID and, where relevant, a LocationID and one or more EmployeeID columns, so the whole model can be sliced consistently by department, site, officer and date from a single set of shared filters.

Model-building solution, step by step

Step 1.Load all fifteen sheets into Power BI and confirm each department fact table lands with the correct data types after your Power Query cleaning steps.

In Power Query, apply the department-specific cleaning steps documented in each department's section, then Close & Apply. Spot-check row counts before and after each cleaning query against the raw sheet to confirm no rows were silently dropped.

Step 2.Build a dedicated Dim_Date table (either with Power Query's date table pattern or a CALENDAR() DAX table) spanning the full range of dates found across every fact table.

Recommended pattern: a Custom Column table built with `Dim_Date = CALENDAR(MIN of all fact date columns, MAX of all fact date columns)`, then add Year, Month, Month Name, Quarter, and Year-Month columns with DAX, e.g. `Year = YEAR('Dim_Date'[Date])`, `Month Name = FORMAT('Dim_Date'[Date],"MMMM")`, `Year-Month = FORMAT('Dim_Date'[Date],"YYYY-MM")`.

Step 3.Create the relationship from Dim_Department[DepartmentID] to each fact table's DepartmentID column - all should be one-to-many, single direction, from Dim_Department to the fact table.

In Model view, drag DepartmentID from Dim_Department onto DepartmentID in each fact table one at a time; Power BI infers many-to-one automatically when Dim_Department[DepartmentID] is unique - confirm the cardinality shown is Many to One (fact to dimension) and cross filter direction is Single.

Step 4.Create the relationship from Dim_Location[LocationID] to each fact table's LocationID column.

Same drag-and-drop pattern as DepartmentID, from Dim_Location[LocationID].

Step 5.Create the relationship from Dim_Employee[EmployeeID] to the primary EmployeeID-style column on each fact table (SupervisorID, HandledByID, RequestedByID, ApprovedByID, Responsible OfficerID, Risk OwnerID, Handling OfficerID as appropriate).

Same drag-and-drop pattern; where a column name differs from EmployeeID (e.g. HandledByID), the relationship still works because Power BI relates on values, not names - just confirm the data types match (both Text).

Step 6.Where a fact table has a second EmployeeID-style column (for example IT's AssignedToID, Admin's ApprovedByID), create that relationship as inactive and activate it inside specific measures with USERELATIONSHIP.

Create the second relationship the same way; Power BI will mark it dashed/inactive automatically because Dim_Employee already has an active relationship to the table. Reference it inside a measure, e.g. `Assigned Technician Workload = CALCULATE(COUNTROWS('IT'), USERELATIONSHIP('IT'[AssignedToID],'Dim_Employee'[EmployeeID]))`.

Step 7.Relate every fact table's date column to Dim_Date[Date], and mark Dim_Date as the model's official Date Table (Table Tools > Mark as Date Table) so time intelligence functions work correctly.

Drag each fact table's cleaned date column onto Dim_Date[Date]; in Model view select Dim_Date, go to Table Tools (or the ribbon's Date Table settings) and choose Mark as Date Table, pointing it at the Date column.

Step 8.Build a self-referencing relationship on Dim_Employee (EmployeeID to SupervisorID) to support organisational-hierarchy analysis.

In Model view, drag Dim_Employee[EmployeeID] onto Dim_Employee[SupervisorID] within the same table; Power BI supports self-joins and will mark this relationship inactive by default - activate it inside hierarchy-specific measures with USERELATIONSHIP, or use a DAX PATH()/PATHITEM() pattern for full org-chart traversal.

Step 9.Set every fact-to-dimension relationship's cross-filter direction to Single, and confirm no circular or ambiguous relationships remain by checking the Model view for warning icons.

Open Model view, use View > Relationships to visually confirm every join line points from the dimension (one side) to the fact table (many side) with a single arrowhead; any double-headed arrow or dotted warning line means the direction needs correcting in the relationship's Edit dialog.
