1. Loading the clean data - Power Query solutions

Step-by-step solution for loading every one of the nine sheets from PM_PowerBI_Training_Dataset.xlsx and preparing them correctly in the model.

General first step: Home > Get Data > Excel Workbook > select PM_PowerBI_Training_Dataset.xlsx > in the Navigator, tick all nine data sheets (Dim_Date, Dim_Employees, Dim_Clients, Dim_Projects, Dim_Tasks, Fact_Timesheets, Fact_Budget, Fact_Milestones, Fact_Risks - skip the Read Me sheet) > Transform Data to open Power Query.
Solution 1 - Dim_Date

Home > Data source settings not needed since it's a local workbook. In Power Query, select Dim_Date, right-click the Date column header > Change Type > Date. Close & Apply, then in Model view select the table, go to the Table Tools ribbon > Mark as Date Table > choose Date as the date column, and confirm the OK prompt.

Solution 2 - Dim_Employees

In Power Query, click the data type icon on HourlyRate_USD > Decimal Number, and on HireDate > Date. Close & Apply. In Model view, right-click the Email field in the field list > Hide in Report View.

Solution 3 - Dim_Clients

In Power Query, set ContractValue_USD's type to Decimal Number and ClientSince's type to Date via the column header type icons. Close & Apply.

Solution 4 - Dim_Projects

Set StartDate, PlannedEndDate and ActualEndDate to Date type, and PlannedBudget_USD to Decimal Number. Leave ClientID as Text - do not filter out or error-check blank values, since blank ClientID on internal projects is expected and valid.

Solution 5 - Dim_Tasks

Set EstimatedHours type to Whole Number; set StartDate, DueDate and CompletionDate to Date. Close & Apply.

Solution 6 - Fact_Timesheets

Set HoursLogged to Decimal Number type. Since this is already a clean flat table there is no staging step needed - load it directly. Confirm row count after load matches the source (2,575 rows) using the status bar in Power Query.

Solution 7 - Fact_Budget

Set the two cost columns to Decimal Number and Month to Date via the column type icons. Close & Apply.

Solution 8 - Fact_Milestones

Set both date columns to Date type. Do not replace blank ActualDate values - they represent milestones not yet reached and must stay blank for the Delayed/At Risk/On Track logic to work correctly downstream.

Solution 9 - Fact_Risks

Set RiskScore to Whole Number type, DateIdentified and DateResolved to Date type. Close & Apply, then load all nine queries to the model.

Final step: Click Close & Apply. Confirm in Model view that all nine tables appear with the correct icons (a calendar icon on Dim_Date once marked as a date table) and that row counts match: Dim_Date 1,461 · Dim_Employees 48 · Dim_Clients 18 · Dim_Projects 32 · Dim_Tasks 350 · Fact_Timesheets 2,575 · Fact_Budget 1,820 · Fact_Milestones 160 · Fact_Risks 127.

Go to Model view and create each relationship below by dragging from the "from" field to the "to" field, or via Manage Relationships > New. Power BI will auto-detect cardinality - always double check it matches the table below before saving.

Why four Employee relationships cannot all be active: Power BI only allows one active (usable-by-default) relationship path between any two tables, because allowing more than one would make a plain filter on Dim_Employees ambiguous - the engine would not know which path to propagate through. The relationship on AssignedToID is left active since "who is doing the work" is the most common slicing need; the other three (ProjectManagerID, AccountManagerID, OwnerID) are created as inactive (Power BI greys them out and draws them as dashed lines) and are switched on only inside specific DAX measures using USERELATIONSHIP(), which activates a named relationship for the duration of a single CALCULATE. This is the standard pattern for a "role-playing dimension".

3. DAX measures - full solutions

Every measure below is given in full, with a line-by-line explanation of what each part of the formula does, why that particular DAX pattern was chosen over the alternatives, and exactly what it drives on the finished dashboard.

Foundational measures (used across every page)

Total Projects

Total Projects = DISTINCTCOUNT(Dim_Projects[ProjectID])
Line-by-line explanation
  1. DISTINCTCOUNT counts unique ProjectID values in the currently filtered context, so the result always matches whatever slicers/filters are applied.
Why this pattern was used
DISTINCTCOUNT rather than COUNTROWS is used because ProjectID is the grain of Dim_Projects; using COUNTROWS would give the same answer here, but DISTINCTCOUNT is the safer habit once a measure is later reused against a fact table where a project can repeat many times.
Impact on the dashboard
Feeds every KPI card that shows a project count, and is the denominator for On-Time Completion %.

Active Projects

Active Projects =
CALCULATE(
    [Total Projects],
    Dim_Projects[Status] = "In Progress"
)
Line-by-line explanation
  1. CALCULATE takes the existing [Total Projects] measure and overrides its filter context.
  2. The Status filter narrows the count down to only rows where Status equals "In Progress", regardless of what the report page's own filters/slicers are doing to Status.
Why this pattern was used
Wrapping the base measure keeps a single definition of 'how to count a project' in one place, so a future change to Total Projects automatically flows into Active Projects.
Impact on the dashboard
Executive Portfolio Overview KPI card and the Status donut chart's callout.

Completed On-Time %

Completed On-Time % =
VAR CompletedProjects =
    CALCULATE([Total Projects], Dim_Projects[Status] = "Completed")
VAR OnTimeProjects =
    CALCULATE(
        [Total Projects],
        Dim_Projects[Status] = "Completed",
        Dim_Projects[ActualEndDate] <= Dim_Projects[PlannedEndDate]
    )
RETURN
    DIVIDE(OnTimeProjects, CompletedProjects)
Line-by-line explanation
  1. VAR CompletedProjects stores the count of all completed projects, computed once so it is not re-evaluated twice.
  2. VAR OnTimeProjects adds a second condition: the actual end date must be on or before the planned end date.
  3. DIVIDE(OnTimeProjects, CompletedProjects) safely divides the two, returning BLANK instead of an error when CompletedProjects is 0.
Why this pattern was used
Using VAR makes the two-step logic readable and avoids repeating the CALCULATE filter twice; DIVIDE is used in place of the / operator specifically to avoid a divide-by-zero error when no projects are completed yet in the current filter context.
Impact on the dashboard
Headline KPI card on the Executive Overview page - the single most-watched number in the whole report.

Total Planned Budget

Total Planned Budget = SUM(Dim_Projects[PlannedBudget_USD])
Line-by-line explanation
  1. SUM adds PlannedBudget_USD across every row of Dim_Projects visible in the current filter context.
Why this pattern was used
PlannedBudget_USD lives once per project on Dim_Projects (not per month like actual cost), so summing the dimension table directly is correct and avoids overcounting.
Impact on the dashboard
Budget KPI cards and the Planned vs Actual chart on the Budget & Cost Analysis page.

Total Actual Cost

Total Actual Cost = SUM(Fact_Budget[ActualCost_USD])
Line-by-line explanation
  1. SUM adds every ActualCost_USD row in Fact_Budget that is visible in the current filter context (after project, category and date filters are applied).
Why this pattern was used
Actual cost is captured monthly and by category in the fact table, so it must be summed from the fact table rather than the project dimension.
Impact on the dashboard
Compared directly against Total Planned Budget on the Budget & Cost Analysis page and portfolio KPI cards.

Budget Variance

Budget Variance = [Total Planned Budget] - [Total Actual Cost]
Line-by-line explanation
  1. A simple subtraction between two existing measures; positive means under budget, negative means over budget.
Why this pattern was used
Built as a measure (not a calculated column) so it recalculates correctly at every level - project, department or portfolio - as the report is filtered.
Impact on the dashboard
Conditional-formatted KPI card and the 'Top Overbudget Projects' bar chart (sorted ascending on this measure).

Budget Variance %

Budget Variance % = DIVIDE([Budget Variance], [Total Planned Budget])
Line-by-line explanation
  1. DIVIDE expresses the variance as a proportion of planned budget, returning BLANK rather than an error if planned budget is 0.
Why this pattern was used
A percentage is easier to compare fairly across projects of very different sizes than the absolute dollar variance is.
Impact on the dashboard
Used as the color/data-label field on the Budget & Cost Analysis matrix visual.
Task & schedule measures

Total Tasks

Total Tasks = COUNTROWS(Dim_Tasks)
Line-by-line explanation
  1. COUNTROWS simply counts the rows of Dim_Tasks visible in the current filter context.
Why this pattern was used
COUNTROWS is used instead of DISTINCTCOUNT because Dim_Tasks is already at one-row-per-task grain, so there is nothing to de-duplicate.
Impact on the dashboard
Denominator for Task Completion Rate % and the base of every task-count KPI.

Completed Tasks

Completed Tasks =
CALCULATE([Total Tasks], Dim_Tasks[Status] = "Completed")
Line-by-line explanation
  1. CALCULATE overrides the Status filter to isolate completed tasks only.
Why this pattern was used
Reuses [Total Tasks] rather than writing COUNTROWS again, keeping the counting logic in one place.
Impact on the dashboard
Task Status donut chart and Task Completion Rate %.

Task Completion Rate %

Task Completion Rate % = DIVIDE([Completed Tasks], [Total Tasks])
Line-by-line explanation
  1. DIVIDE guards against a blank denominator when a filter context returns zero tasks (e.g. a brand-new project).
Why this pattern was used
A rate is more meaningful than a raw count when comparing progress across projects of different sizes.
Impact on the dashboard
KPI card and conditional formatting on the Task & Schedule Management page.

Overdue Tasks

Overdue Tasks =
CALCULATE(
    [Total Tasks],
    Dim_Tasks[Status] <> "Completed",
    Dim_Tasks[DueDate] < TODAY()
)
Line-by-line explanation
  1. The first condition excludes tasks already marked Completed.
  2. The second condition compares DueDate against TODAY(), Power BI's function for the current system date, so the measure is always evaluated against 'right now'.
Why this pattern was used
TODAY() is used instead of a hardcoded date so the measure stays correct every time the report is opened or refreshed, without any manual edits.
Impact on the dashboard
The single most important alert metric on the Task & Schedule page - drives a red KPI card and an 'Overdue Tasks by Assignee' bar chart.

Average Task Duration (Days)

Average Task Duration (Days) =
AVERAGEX(
    FILTER(Dim_Tasks, Dim_Tasks[Status] = "Completed"),
    DATEDIFF(Dim_Tasks[StartDate], Dim_Tasks[CompletionDate], DAY)
)
Line-by-line explanation
  1. FILTER builds a virtual table containing only completed tasks.
  2. AVERAGEX iterates row-by-row over that virtual table.
  3. DATEDIFF calculates the number of days between StartDate and CompletionDate for each row, and AVERAGEX then averages those per-row results.
Why this pattern was used
AVERAGEX (an iterator) is required rather than a plain AVERAGE because the duration is not a stored column - it has to be computed per row before it can be averaged.
Impact on the dashboard
Line/KPI showing how delivery speed is trending on the Task & Schedule page.

Tasks Completed (Running Total)

Tasks Completed (Running Total) =
CALCULATE(
    [Completed Tasks],
    FILTER(
        ALLSELECTED(Dim_Date[Date]),
        Dim_Date[Date] <= MAX(Dim_Date[Date])
    )
)
Line-by-line explanation
  1. ALLSELECTED(Dim_Date[Date]) removes the row-level date filter from the visual's own axis while still respecting any slicers on the page, giving a clean base of dates to accumulate over.
  2. FILTER keeps only the dates less than or equal to the current date on the axis.
  3. CALCULATE then evaluates [Completed Tasks] across that accumulated set of dates, producing a running total as the axis moves forward in time.
Why this pattern was used
ALLSELECTED is preferred over ALL because it keeps external slicer selections (e.g. a Department slicer) working, only removing the internal chart-axis filter that would otherwise stop the accumulation.
Impact on the dashboard
The cumulative completion trend line on the Task & Schedule Management page.
Budget & cost measures

Cost Per Hour

Cost Per Hour = DIVIDE([Total Actual Cost], [Total Hours Logged])
Line-by-line explanation
  1. Divides total actual cost by total hours logged, with DIVIDE protecting against a zero-hour filter context.
Why this pattern was used
Blends two fact tables (Fact_Budget and Fact_Timesheets) purely through measures, which is the safe way to compare two different grains without needing a physical relationship between them.
Impact on the dashboard
Efficiency KPI on the Budget & Cost Analysis page, and a scatter-chart axis (Cost per Hour vs Hours Logged) by project.

Labor Cost Share %

Labor Cost Share % =
VAR LaborCost =
    CALCULATE([Total Actual Cost], Fact_Budget[Category] = "Labor")
RETURN
    DIVIDE(LaborCost, [Total Actual Cost])
Line-by-line explanation
  1. VAR LaborCost isolates actual cost for just the Labor category.
  2. DIVIDE then expresses that as a share of total actual cost across all categories.
Why this pattern was used
Written with CALCULATE + a single hardcoded category rather than a SWITCH/multi-category pattern because the dashboard only needs this one specific share as a callout, not a general-purpose category measure.
Impact on the dashboard
Callout on the Budget & Cost Analysis page highlighting how labour-heavy the portfolio is.

Budget Utilization %

Budget Utilization % = DIVIDE([Total Actual Cost], [Total Planned Budget])
Line-by-line explanation
  1. A straightforward ratio of spend to plan, expressed as a percentage by the visual's number formatting.
Why this pattern was used
Kept separate from Budget Variance % (which is signed and centred on zero) because gauge/KPI visuals read a 0-100%+ utilization ratio more intuitively than a positive/negative variance.
Impact on the dashboard
Gauge visual on the Budget & Cost Analysis page, coloured red above 100%.

MoM Actual Cost Change

MoM Actual Cost Change =
VAR CurrentCost = [Total Actual Cost]
VAR PreviousCost =
    CALCULATE(
        [Total Actual Cost],
        DATEADD(Dim_Date[Date], -1, MONTH)
    )
RETURN
    DIVIDE(CurrentCost - PreviousCost, PreviousCost)
Line-by-line explanation
  1. VAR CurrentCost captures the actual cost for whatever month is currently in context.
  2. DATEADD(Dim_Date[Date], -1, MONTH) shifts the date filter back by exactly one month, so VAR PreviousCost recalculates [Total Actual Cost] for the prior month.
  3. DIVIDE returns the percentage change, guarding against a zero prior-month cost.
Why this pattern was used
DATEADD is a time-intelligence function that only works correctly because Dim_Date is marked as a proper Date Table with no gaps - this measure is used in the training specifically to demonstrate why that step matters.
Impact on the dashboard
Month-over-month trend arrow on the Budget & Cost Analysis KPI strip.
Resource & utilization measures

Total Hours Logged

Total Hours Logged = SUM(Fact_Timesheets[HoursLogged])
Line-by-line explanation
  1. Adds every HoursLogged value in Fact_Timesheets visible in the current filter context.
Why this pattern was used
The base additive measure of the timesheet fact table - almost every other resourcing measure builds on top of it.
Impact on the dashboard
Feeds KPI cards, the utilization gauge, and every hours-based chart on the Resource & Team Utilization page.

Billable Hours

Billable Hours =
CALCULATE([Total Hours Logged], Fact_Timesheets[BillableFlag] = "Yes")
Line-by-line explanation
  1. CALCULATE narrows Total Hours Logged down to only rows flagged as billable.
Why this pattern was used
Reuses the base measure so the definition of 'an hour' only lives in one place.
Impact on the dashboard
Billable vs Non-Billable stacked bar chart, and the numerator of Billable Utilization %.

Billable Utilization %

Billable Utilization % = DIVIDE([Billable Hours], [Total Hours Logged])
Line-by-line explanation
  1. Expresses billable hours as a share of all hours logged.
Why this pattern was used
DIVIDE avoids an error for any employee/period with zero logged hours.
Impact on the dashboard
Headline KPI and conditional formatting in the employee utilization table.

Overtime Hours

Overtime Hours =
CALCULATE([Total Hours Logged], Fact_Timesheets[OvertimeFlag] = "Yes")
Line-by-line explanation
  1. CALCULATE narrows Total Hours Logged to rows flagged as overtime.
Why this pattern was used
Kept as its own measure (rather than a column filter on a visual) so it can be combined with other measures, e.g. in a ratio.
Impact on the dashboard
Overtime-cost callout and the 'employees most at risk of burnout' table, sorted by this measure.

Estimated vs Actual Hours Variance

Estimated vs Actual Hours Variance =
SUMX(
    Dim_Tasks,
    Dim_Tasks[EstimatedHours]
) - [Total Hours Logged]
Line-by-line explanation
  1. SUMX iterates over Dim_Tasks and totals the EstimatedHours column for the tasks in the current filter context.
  2. That total is then compared against [Total Hours Logged], the actual hours pulled from the timesheet fact table.
Why this pattern was used
SUMX is required (rather than a plain SUM) purely as a matter of style consistency in this training so students see both SUM and SUMX used correctly - here a plain SUM(Dim_Tasks[EstimatedHours]) would in fact work identically, and the guide calls that out explicitly.
Impact on the dashboard
Estimation-accuracy KPI on the Resource & Team Utilization page - highlights chronic under- or over-estimation.

Active Employees

Active Employees =
CALCULATE(DISTINCTCOUNT(Dim_Employees[EmployeeID]), Dim_Employees[EmploymentStatus] = "Active")
Line-by-line explanation
  1. DISTINCTCOUNT counts unique employees; CALCULATE narrows that to only those currently marked Active.
Why this pattern was used
Used as the denominator base for any future average-hours-per-employee style measure, and to exclude former staff from headcount cards.
Impact on the dashboard
Headcount KPI card on the Resource & Team Utilization page.

Projects Managed (by PM)

Projects Managed (by PM) =
CALCULATE(
    [Total Projects],
    USERELATIONSHIP(Dim_Employees[EmployeeID], Dim_Projects[ProjectManagerID])
)
Line-by-line explanation
  1. USERELATIONSHIP tells this one CALCULATE to temporarily activate the otherwise-inactive Employees-to-Projects relationship on ProjectManagerID, without changing the model's default active path.
  2. With that relationship active for the duration of the calculation, [Total Projects] is then evaluated filtered by whichever employee is in context.
Why this pattern was used
This is the direct, textbook use of USERELATIONSHIP: the model only allows one active relationship between two tables, so this measure activates the second (PM) relationship on demand instead of the default (assignee) one.
Impact on the dashboard
Employee-level table on the Resource & Team Utilization page showing how many projects each PM leads, next to their hours logged as an assignee.
Risk measures

Open Risks

Open Risks =
CALCULATE(COUNTROWS(Fact_Risks), Fact_Risks[Status] = "Open")
Line-by-line explanation
  1. COUNTROWS counts risk rows; CALCULATE narrows that to Status = Open.
Why this pattern was used
COUNTROWS is correct here (not DISTINCTCOUNT) because Fact_Risks is already at one-row-per-risk grain.
Impact on the dashboard
Headline red KPI on the Risk Management page.

High Severity Risks

High Severity Risks =
CALCULATE(
    COUNTROWS(Fact_Risks),
    Fact_Risks[RiskScore] >= 6,
    Fact_Risks[Status] IN {"Open", "Occurred"}
)
Line-by-line explanation
  1. RiskScore >= 6 keeps only the higher end of the 1-9 probability x impact scale.
  2. The IN operator checks Status against a small set of values in one line, equivalent to Status = "Open" || Status = "Occurred" but easier to read and extend.
Why this pattern was used
IN was chosen over nested OR() calls purely for readability - this is the pattern the training recommends whenever a measure needs to match against more than one text value.
Impact on the dashboard
Drives the colour thresholds on the Risk Matrix heatmap and a 'Top High-Severity Risks' table.

Average Risk Score

Average Risk Score = AVERAGE(Fact_Risks[RiskScore])
Line-by-line explanation
  1. AVERAGE computes the mean RiskScore across the risks visible in the current filter context.
Why this pattern was used
A plain AVERAGE is sufficient because RiskScore is already a stored column, not something that needs to be computed per row first.
Impact on the dashboard
Gauge visual and the axis reference line on the risk trend chart.

Risk Resolution Rate %

Risk Resolution Rate % =
VAR ResolvedRisks =
    CALCULATE(COUNTROWS(Fact_Risks), Fact_Risks[Status] IN {"Mitigated", "Closed"})
VAR TotalRisks = COUNTROWS(Fact_Risks)
RETURN
    DIVIDE(ResolvedRisks, TotalRisks)
Line-by-line explanation
  1. VAR ResolvedRisks counts risks whose status shows they have been dealt with.
  2. VAR TotalRisks counts every risk in the current context.
  3. DIVIDE returns the percentage resolved, safe against a zero-risk filter context.
Why this pattern was used
VARs are used to make the two counts explicit and reusable within the measure, avoiding evaluating COUNTROWS(Fact_Risks) redundantly.
Impact on the dashboard
KPI card and conditional formatting on the Risk Management page's project-level risk table.

Risks Owned (by Employee)

Risks Owned (by Employee) =
CALCULATE(
    COUNTROWS(Fact_Risks),
    USERELATIONSHIP(Dim_Employees[EmployeeID], Fact_Risks[OwnerID])
)
Line-by-line explanation
  1. USERELATIONSHIP activates the inactive Employees-to-Fact_Risks relationship on OwnerID for this calculation only.
  2. COUNTROWS then counts risk rows filtered by whichever employee is in the current row/filter context, via that temporarily active relationship.
Why this pattern was used
Same pattern as Projects Managed (by PM) - demonstrates that USERELATIONSHIP is reused any time a role-playing dimension needs a non-default path activated.
Impact on the dashboard
Employee-level risk ownership table on the Risk Management page.
