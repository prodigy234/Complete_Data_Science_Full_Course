1. Solution Overview

This file is the fully worked solution to every task listed in the Tasks and Problem Brief file. It follows the standard Power BI project sequence: Load & Shape > Model & Relate > Measure with DAX > Visualise & Publish. Read it alongside the Tasks file rather than instead of it - the real learning happens in attempting each task before checking it here.

2. Step 1 - Loading & Preparing the Data

1Get Data

Open Power BI Desktop, choose Get Data > Excel Workbook, and select Disease_Surveillance_Dataset.xlsx. In the Navigator window, tick all 13 data tables (skip the Read Me sheet) and click Transform Data to open Power Query Editor before loading, so every type can be checked first.

2Confirm data types

Click through each query and confirm: every *ID key column is Text; every date column (OnsetDate, ReportDate, DateDeclared, DateClosed, SpecimenCollectionDate, ResultDate, VaccinationDate, MonitoringStartDate, MonitoringEndDate, SurveillanceDate, DateEstablished, DateHired, DateOfBirth and Date) is Date; and Population, AreaKm2, DosesAdministered and similar count columns are Whole Number. Power Query usually infers these correctly from a clean Excel source, but this dataset was built specifically so a student practises verifying, not assuming.

3Rename queries

Confirm the query names in the Queries pane exactly match the sheet names (Dim_Geography, Dim_Diseases, Dim_HealthFacilities, Dim_SurveillanceOfficers, Dim_Vaccines, Dim_Patients, Dim_Date, Fact_Outbreaks, Fact_CaseReports, Fact_LabResults, Fact_Immunizations, Fact_ContactTracing, Fact_EnvironmentalSurveillance), since every relationship and DAX formula in this walkthrough references these exact names.

4Close & Apply

Click Close & Apply. Power BI loads all 13 tables into the semantic model. Open Model view and confirm you see 13 tables with no relationships yet - Power BI's autodetect sometimes proposes relationships on load; delete any that were auto-created so you build every one deliberately in the next step.

Mark Dim_Date as a Date Table

Right-click Dim_Date in the Fields pane > Mark as Date Table > Mark as Date Table, then choose the Date column when prompted. Confirm the dialog reports no errors. 4. Step 3 - Building the DAX Measures

Create a blank Measures table first (Model view > Enter Data > leave it empty > name it Measures) and build every measure below inside it, in this order, since several later measures reference earlier ones.

Total Cases Reported

Used on: Used on every page
Total Cases Reported = DISTINCTCOUNT(Fact_CaseReports[CaseID])

Line by line:

  • DISTINCTCOUNT(Fact_CaseReports[CaseID]) counts the number of unique case reports remaining in the current filter context.
Why this measure exists: The foundation KPI of the entire report; almost every other measure either builds on it or is filtered the same way it is.
Impact on the dashboard: The first KPI card on the Executive Overview page and the value plotted on the epi curve line chart.

Confirmed Cases

Used on: Executive Overview
Confirmed Cases = CALCULATE([Total Cases Reported], Fact_CaseReports[CaseClassification] = "Confirmed")

Line by line:

  • CALCULATE overrides the filter context by adding CaseClassification = "Confirmed" while preserving whatever Date, Disease or Geography filters are already active, combining them with AND logic.
Why this measure exists: Distinguishes laboratory- or clinically-confirmed disease burden from the broader Suspected and Probable case pool, an important distinction in every surveillance bulletin.
Impact on the dashboard: Shown as a KPI card next to Total Cases Reported so the gap between the two numbers is immediately visible.

Case Fatality Rate %

Used on: Executive Overview, Disease & Outbreak Surveillance
Case Fatality Rate % = DIVIDE( CALCULATE([Total Cases Reported], Fact_CaseReports[CaseOutcome] = "Died"), [Total Cases Reported], 0 )

Line by line:

  • The inner CALCULATE counts only cases whose outcome is Died, while still respecting any Date, Disease or Geography filters already on the page.
  • DIVIDE expresses that count as a percentage of all cases in the same filter context, returning 0 rather than an error when there are no cases at all.
Why this measure exists: One of the most closely watched indicators in any disease surveillance bulletin, and one that must be presented carefully given its sensitivity.
Impact on the dashboard: Shown as a KPI card on the Executive Overview page, deliberately not broken down to a granularity that could identify an individual case.

Incidence Rate per 100,000

Used on: Executive Overview, Disease & Outbreak Surveillance
Incidence Rate per 100,000 = DIVIDE([Total Cases Reported], SUM(Dim_Geography[Population]), 0) * 100000

Line by line:

  • SUM(Dim_Geography[Population]) adds population only across the geography rows currently in the filter context; because Population lives on the dimension side of a one-to-many relationship, each LGA's population is counted exactly once no matter how many case reports exist for it.
  • DIVIDE expresses total cases as a fraction of that population, and multiplying by 100000 converts the result into the standard epidemiological 'per 100,000 population' scale used in virtually every public health report worldwide.
Why this measure exists: The single most authentic epidemiological measure in this project: a raw case count is close to meaningless without knowing the size of the population it came from, since a populous LGA will always report more cases than a sparsely populated one even if the underlying risk is identical.
Impact on the dashboard: Displayed as a KPI card and used on a State-level map or bar chart, letting students compare disease burden fairly across LGAs of very different sizes.

Average Reporting Delay (Days)

Used on: Disease & Outbreak Surveillance
Average Reporting Delay (Days) = AVERAGE(Fact_CaseReports[ReportingDelayDays])

Line by line:

  • AVERAGE(Fact_CaseReports[ReportingDelayDays]) computes the mean number of days between symptom onset and formal reporting across every case in the current filter context.
Why this measure exists: A core surveillance-system-performance indicator: the faster cases are reported, the faster an outbreak can be detected and contained.
Impact on the dashboard: Shown as a KPI card and plotted as a monthly trend line, letting students spot whether reporting speed is improving or worsening over time.

Timely Reporting %

Used on: Disease & Outbreak Surveillance
Timely Reporting % = DIVIDE( CALCULATE([Total Cases Reported], Fact_CaseReports[ReportingDelayDays] <= 3), [Total Cases Reported], 0 )

Line by line:

  • CALCULATE filters cases down to those reported within 3 days of symptom onset, a common surveillance-timeliness benchmark.
  • DIVIDE expresses that count as a percentage of all cases in the same filter context.
Why this measure exists: Turns the raw delay figure into a target-based percentage that is easier to track against a performance goal (for example, a target of 80% of cases reported within 3 days).
Impact on the dashboard: Shown as a gauge visual on the Disease & Outbreak Surveillance page with an informal target band.

Hospitalization Rate %

Used on: Executive Overview
Hospitalization Rate % = DIVIDE( CALCULATE([Total Cases Reported], Fact_CaseReports[HospitalizationStatus] = "Yes"), [Total Cases Reported], 0 )

Line by line:

  • Same CALCULATE-then-DIVIDE pattern as the measures above, filtered instead to HospitalizationStatus = "Yes".
Why this measure exists: Indicates disease severity and health-system burden; a rising hospitalization rate for a given disease often signals either worsening severity or delayed presentation.
Impact on the dashboard: Shown as a KPI card on the Executive Overview page.

Outbreak-Linked Cases %

Used on: Disease & Outbreak Surveillance
Outbreak-Linked Cases % = DIVIDE( CALCULATE([Total Cases Reported], NOT ISBLANK(Fact_CaseReports[OutbreakID])), [Total Cases Reported], 0 )

Line by line:

  • ISBLANK(Fact_CaseReports[OutbreakID]) returns TRUE for the roughly 70% of case rows with no linked outbreak; wrapping it in NOT flips that to TRUE only for rows that DO have a populated OutbreakID.
  • CALCULATE applies that condition as a filter, counting only outbreak-linked cases, before DIVIDE expresses the result as a percentage of all cases in context.
Why this measure exists: Demonstrates the correct, robust way to test an optional foreign key for blank versus populated in DAX, rather than comparing it to an empty string, which behaves differently and less reliably.
Impact on the dashboard: Shown as a KPI card on the Disease & Outbreak Surveillance page, next to the outbreak log table.

Cases by Report Date (USERELATIONSHIP demo)

Used on: Disease & Outbreak Surveillance
Cases by Report Date = CALCULATE( [Total Cases Reported], USERELATIONSHIP(Dim_Date[Date], Fact_CaseReports[ReportDate]) )

Line by line:

  • USERELATIONSHIP(Dim_Date[Date], Fact_CaseReports[ReportDate]) temporarily activates the otherwise-inactive relationship between Dim_Date and ReportDate, for the duration of this CALCULATE call only.
  • Placed on a visual next to the default onset-date-based Total Cases Reported, this measure lets a surveillance officer distinguish 'when did people actually get sick' from 'when did the system find out about it', two genuinely different and both important questions.
Why this measure exists: The clearest possible demonstration in this project of why a dedicated date table sometimes needs more than one relationship to the same fact table, and why USERELATIONSHIP exists to resolve the resulting ambiguity safely.
Impact on the dashboard: Placed on a dedicated 'DAX Concepts' tooltip or comparison visual on the Disease & Outbreak Surveillance page.

Total Lab Tests Conducted

Used on: Laboratory & Diagnostics
Total Lab Tests Conducted = DISTINCTCOUNT(Fact_LabResults[LabResultID])

Line by line:

  • DISTINCTCOUNT(Fact_LabResults[LabResultID]) counts unique laboratory tests in the current filter context.
Why this measure exists: The foundation activity KPI for the entire Laboratory & Diagnostics dashboard page.
Impact on the dashboard: The first KPI card on that page, and the value plotted on the monthly testing volume trend line.

Lab Positivity Rate %

Used on: Laboratory & Diagnostics
Lab Positivity Rate % = DIVIDE( CALCULATE([Total Lab Tests Conducted], Fact_LabResults[TestResult] = "Positive"), [Total Lab Tests Conducted], 0 )

Line by line:

  • A CALCULATE-then-DIVIDE ratio measure filtering tests down to Positive results before expressing them as a share of all tests conducted.
Why this measure exists: A core diagnostic-yield indicator; a rising positivity rate for a given disease, even without a rise in absolute case counts, can be an early warning sign that testing is not keeping pace with true transmission.
Impact on the dashboard: Shown as a KPI card and used on a Positivity Rate by Disease bar chart.

Average Lab Turnaround Time (Days)

Used on: Laboratory & Diagnostics
Average Lab Turnaround Time (Days) = AVERAGE(Fact_LabResults[TurnaroundTimeDays])

Line by line:

  • AVERAGE(Fact_LabResults[TurnaroundTimeDays]) computes the mean number of days between specimen collection and result release across every test in the current filter context.
Why this measure exists: A core laboratory-system-performance indicator, since a confirmed diagnosis that arrives too late to change clinical management or trigger a timely outbreak response has limited practical value.
Impact on the dashboard: Shown as a KPI card and plotted as a monthly trend line on the Laboratory & Diagnostics page.

Lab Positivity by Testing Facility (USERELATIONSHIP demo)

Used on: Laboratory & Diagnostics
Lab Positivity by Testing Facility = CALCULATE( [Lab Positivity Rate %], USERELATIONSHIP(Dim_HealthFacilities[FacilityID], Fact_LabResults[TestingFacilityID]) )

Line by line:

  • Without this override, placing FacilityName from Dim_HealthFacilities on a visual alongside [Lab Positivity Rate %] would filter Fact_LabResults indirectly through the chain Dim_HealthFacilities to Fact_CaseReports to Fact_LabResults, which answers 'what is the positivity rate among tests linked to cases REPORTED at this facility', not 'what is the positivity rate among tests actually PROCESSED at this facility's laboratory'.
  • USERELATIONSHIP(Dim_HealthFacilities[FacilityID], Fact_LabResults[TestingFacilityID]) activates the direct, otherwise-inactive relationship for the duration of this CALCULATE call, correctly answering the second, testing-facility-centred question instead.
Why this measure exists: The single most advanced DAX pattern in this project: it shows that USERELATIONSHIP is not only needed for role-playing date columns, but for any pair of tables where a fact-to-fact chain has already created an indirect, differently-meaning path.
Impact on the dashboard: Placed side by side with the default Lab Positivity Rate % in a matrix visual with FacilityName on rows, so students can see the two numbers differ and understand exactly why.

Total Doses Administered

Used on: Immunization & Vaccine-Preventable Disease
Total Doses Administered = SUM(Fact_Immunizations[DosesAdministered])

Line by line:

  • SUM(Fact_Immunizations[DosesAdministered]) adds up doses given across every immunization session in the current filter context.
Why this measure exists: The primary immunization-activity KPI, a proxy for vaccination coverage since this dataset does not model a formal target-population denominator for coverage percentage.
Impact on the dashboard: The main KPI card on the Immunization page and the value plotted on the Doses Administered by Vaccine column chart.

Vaccine Wastage Rate %

Used on: Immunization & Vaccine-Preventable Disease
Vaccine Wastage Rate % = DIVIDE( SUM(Fact_Immunizations[DosesWasted]), SUM(Fact_Immunizations[DosesAdministered]) + SUM(Fact_Immunizations[DosesWasted]), 0 )

Line by line:

  • The denominator adds administered and wasted doses together to represent every dose that was opened for use, whether it was ultimately given to a patient or lost.
  • DIVIDE expresses wasted doses as a share of that total, the standard formula used in real vaccine-supply-chain reporting.
Why this measure exists: An important vaccine-supply-chain efficiency indicator; consistently high wastage at a specific facility or for a specific vaccine type signals a cold-chain or session-planning problem worth investigating.
Impact on the dashboard: Shown as a KPI card with conditional formatting flagging facilities or vaccines above an acceptable wastage threshold.

Total Active Outbreaks

Used on: Disease & Outbreak Surveillance
Total Active Outbreaks = CALCULATE( DISTINCTCOUNT(Fact_Outbreaks[OutbreakID]), Fact_Outbreaks[OutbreakStatus] = "Active" )

Line by line:

  • CALCULATE filters Fact_Outbreaks down to rows flagged Active before DISTINCTCOUNT counts the unique outbreaks remaining.
Why this measure exists: A live operational KPI for outbreak response coordination teams; unlike most other measures in this project, this one is most meaningful at the current point in time rather than as a historical trend.
Impact on the dashboard: Shown as a prominent KPI card on both the Executive Overview and Disease & Outbreak Surveillance pages.

Average Outbreak Duration (Days)

Used on: Disease & Outbreak Surveillance
Average Outbreak Duration (Days) = AVERAGEX( FILTER(Fact_Outbreaks, NOT ISBLANK(Fact_Outbreaks[DateClosed])), DATEDIFF(Fact_Outbreaks[DateDeclared], Fact_Outbreaks[DateClosed], DAY) )

Line by line:

  • FILTER(Fact_Outbreaks, NOT ISBLANK(Fact_Outbreaks[DateClosed])) builds a temporary table containing only outbreaks that have actually been closed, deliberately excluding any outbreak still flagged Active with a blank DateClosed.
  • AVERAGEX then iterates over that filtered table, calculating DATEDIFF(DateDeclared, DateClosed, DAY) for each row before averaging the results, which is necessary because the duration must be computed per outbreak before it can be averaged, not from a single pre-existing column.
  • Excluding blank DateClosed values is essential here: including them would either error or, worse, silently treat an ongoing outbreak as having a duration of zero or a nonsensical negative number, quietly corrupting the average.
Why this measure exists: A core outbreak-response KPI; shorter average outbreak durations generally indicate a more effective and timely response system.
Impact on the dashboard: Shown as a KPI card next to Total Active Outbreaks on the Disease & Outbreak Surveillance page.

Total Contacts Identified

Used on: Contact Tracing & Field Operations
Total Contacts Identified = DISTINCTCOUNT(Fact_ContactTracing[ContactTracingID])

Line by line:

  • DISTINCTCOUNT(Fact_ContactTracing[ContactTracingID]) counts unique traced contacts in the current filter context.
Why this measure exists: The foundation activity KPI for the entire contact tracing operation.
Impact on the dashboard: The first KPI card on the Contact Tracing & Field Operations page.

Contacts Converted to Cases %

Used on: Contact Tracing & Field Operations
Contacts Converted to Cases % = DIVIDE( CALCULATE([Total Contacts Identified], Fact_ContactTracing[ContactStatus] = "Became a Case"), [Total Contacts Identified], 0 )

Line by line:

  • A CALCULATE-then-DIVIDE ratio measure filtering contacts down to those whose status became Became a Case before expressing them as a share of all contacts traced.
Why this measure exists: Functions as a rough secondary-attack-rate indicator: a high conversion rate among traced contacts suggests either a highly transmissible disease or a delay between exposure and contact tracing initiation.
Impact on the dashboard: Shown as a KPI card and used on a Contact Status Split donut chart.

Average Contacts per Index Case

Used on: Contact Tracing & Field Operations
Average Contacts per Index Case = DIVIDE( [Total Contacts Identified], DISTINCTCOUNT(Fact_ContactTracing[IndexCaseID]), 0 )

Line by line:

  • Divides total contacts by the number of distinct index cases that generated at least one traced contact, giving an average 'contacts per case' figure rather than a raw total.
Why this measure exists: A field-operations workload indicator: diseases or settings that generate unusually high average contacts per case (for example, a case in a crowded household or workplace) place a proportionally higher burden on the contact tracing team.
Impact on the dashboard: Shown as a KPI card on the Contact Tracing & Field Operations page.

Vector Surveillance Positivity %

Used on: Contact Tracing & Field Operations
Vector Surveillance Positivity % = DIVIDE( CALCULATE( DISTINCTCOUNT(Fact_EnvironmentalSurveillance[EnvSurveillanceID]), Fact_EnvironmentalSurveillance[SurveillanceType] = "Vector Surveillance - Mosquito", Fact_EnvironmentalSurveillance[FindingResult] = "Positive" ), CALCULATE( DISTINCTCOUNT(Fact_EnvironmentalSurveillance[EnvSurveillanceID]), Fact_EnvironmentalSurveillance[SurveillanceType] = "Vector Surveillance - Mosquito" ), 0 )

Line by line:

  • The numerator CALCULATE filters to mosquito vector surveillance activities that came back Positive.
  • The denominator CALCULATE filters to all mosquito vector surveillance activities regardless of result, using two separate filter arguments inside the same CALCULATE, which DAX combines with AND logic.
  • DIVIDE expresses the positive subset as a percentage of all mosquito surveillance activity, safely returning 0 if none were conducted in the current context.
Why this measure exists: An early-warning environmental indicator for vector-borne disease risk (Malaria, Yellow Fever, Dengue), often rising before a corresponding increase in human case counts.
Impact on the dashboard: Shown as a KPI card on the Contact Tracing & Field Operations page, deliberately paired with human case data from other pages for a combined early-warning discussion.

Case Growth % (WoW)

Used on: Executive Overview
Case Growth % WoW = VAR CurrentWeekCases = [Total Cases Reported] VAR PreviousWeekCases = CALCULATE( [Total Cases Reported], DATEADD('Dim_Date'[Date], -7, DAY) ) RETURN DIVIDE(CurrentWeekCases - PreviousWeekCases, PreviousWeekCases, 0)

Line by line:

  • VAR CurrentWeekCases stores [Total Cases Reported] for whatever period is currently in filter context.
  • VAR PreviousWeekCases uses CALCULATE with DATEADD('Dim_Date'[Date], -7, DAY) to shift the entire filter context back exactly seven days and re-evaluate the same measure inside that shifted context, mirroring how epidemiologists compare week-over-week rather than month-over-month when watching for an emerging outbreak.
  • RETURN DIVIDE(...) calculates the percentage change between the two variables, safely returning blank rather than an error for the first week of the dataset's history, where no prior week exists.
Why this measure exists: Week-over-week comparison is the standard cadence in real epidemic intelligence, since month-over-month comparisons react too slowly to catch an emerging outbreak in its earliest, most controllable phase.
Impact on the dashboard: Plotted as a secondary line on a combo chart against the Total Cases Reported line on the Executive Overview page's epi curve.

Outbreak-Level Case Fatality Rate %

Used on: Disease & Outbreak Surveillance
Outbreak-Level Case Fatality Rate % = DIVIDE( SUM(Fact_Outbreaks[TotalDeathsAtClosure]), SUM(Fact_Outbreaks[TotalCasesAtClosure]), 0 )

Line by line:

  • Divides the officially reported death total by the officially reported case total across every outbreak in the current filter context, both summed directly from Fact_Outbreaks rather than derived from Fact_CaseReports.
Why this measure exists: Deliberately kept as a separate measure from the case-level Case Fatality Rate %, since the two are calculated from different source data (officially reported outbreak totals versus individual case outcomes) and will not always agree exactly, a realistic data-reconciliation discussion point worth raising with students.
Impact on the dashboard: Shown alongside Case Fatality Rate % on the Disease & Outbreak Surveillance page so students can compare the two figures and discuss why they might differ.

Cross-Page Consistency

Add a Year slicer (Dim_Date[Year]) and a Disease Category slicer (Dim_Diseases[DiseaseCategory]) to every page in the same top-right position. Select both, go to the View ribbon, open Sync Slicers, and tick every page so a filter choice on Page 1 automatically applies across Pages 2 to 5. Add five navigation buttons (Insert > Buttons > Blank, with Action type set to Page Navigation) in a consistent header band so users never need the page tabs at the bottom.
