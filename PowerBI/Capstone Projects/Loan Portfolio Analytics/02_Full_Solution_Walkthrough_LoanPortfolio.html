2. Solution - Loading & Cleaning the Data

Step A - Connecting to the Source Workbook

  1. Open Power BI Desktop > Home > Get Data > Excel Workbook > select NTMB_Loan_Portfolio_Dataset.xlsx.
  2. In the Navigator window, tick exactly these nine tables: dim_Date, dim_Branch, dim_Customer, dim_LoanOfficer, dim_LoanProduct, fact_Applications, fact_Portfolio, fact_Repayments, fact_Collections. The README, Data_Dictionary and Model_Map sheets are for humans reading the workbook directly, not for the data model - leave them unchecked.
  3. Click "Transform Data" (never "Load" directly) so every table opens in the Power Query Editor first.
Why Transform Data, not Load: loading directly skips the one chance to catch type mismatches, stray whitespace, and null-handling problems while they are still cheap to fix. Every problem caught in Power Query costs one click to fix; the same problem caught later, after 25 DAX measures and 5 report pages are built on top of it, can cost hours.

Step B - Cleaning Each Table in Power Query

B1. dim_Date

The Date column must be set to Date type (not Date/Time) - Excel occasionally exports a hidden 00:00:00 time component that, left in place, causes a date to fail to match visually-identical dates in a fact table during troubleshooting. IsWeekend should be a true Boolean; if it imports as the text "TRUE"/"FALSE" instead, change its type explicitly via Transform > Data Type > True/False. DateKey must be Whole Number, matching the type used for every *DateKey column in the fact tables - a relationship will refuse to build cleanly across mismatched types.

B2. dim_Branch, dim_LoanOfficer, dim_LoanProduct

Apply Trim and Clean (Transform > Format > Trim / Clean) to every text column in dim_Branch. This single step prevents the single most common relationship failure in this entire exercise: a BranchID like "B01 " (with a trailing space) that looks identical to "B01" in the preview grid but will not match it in a relationship. Confirm HireDate in dim_LoanOfficer is Date type, and confirm MinAmount, MaxAmount, and BaseInterestRatePct in dim_LoanProduct are Decimal Number.

B3. dim_Customer

DateOfBirth and OnboardingDate must both be Date type. Age and Customer Tenure are deliberately NOT built here as Power Query calculated columns - they are built later as DAX measures (against TODAY()) so they always reflect the current date rather than being frozen at the moment the file was last refreshed. This is an important modeling principle: anything that depends on "now" belongs in DAX, not in a static ETL step.

B4. fact_Applications and fact_Portfolio (the two-date tables)

Both tables have two date columns relating to dim_Date, and both need careful null handling. DecisionDateKey in fact_Applications and MaturityDateKey in fact_Portfolio must be Whole Number, with genuine nulls where a value doesn't apply (a Pending application has no decision date yet) - watch for the literal text "None" or a stray 0 surviving a CSV round-trip, either of which would silently break the relationship or create a phantom blank-date bucket. AmountRequested, PrincipalAmount, InterestRatePct, OutstandingBalance, and MonthlyInstallment must all be Decimal Number. Trim every ID/key column in both tables.

B5. fact_Repayments and fact_Collections

ScheduledAmount, ActualAmountPaid, and AmountRecovered must be Decimal Number. DaysLate must be Whole Number. Trim LoanID and OfficerID in both tables - these are the keys that let fact_Portfolio act as a bridge table down to these two child fact tables.

Once every table above is confirmed clean, click Home > Close & Apply.

3. Solution - Data Model, Relationships & Cardinality

Step C - Building the Data Model

C1. Mark the Date Table

Select dim_Date > Table Tools ribbon > Mark as Date Table > choose the Date column. This is a prerequisite, not a nicety: SAMEPERIODLASTYEAR, TOTALYTD, DATESINPERIOD and every other time-intelligence function used in Section 6 below silently misbehave (or outright error) against a calendar table that hasn't been marked, because Power BI needs to know, structurally, that this table's date column is contiguous and unique.

C3. Why fact_Portfolio Acts as a Bridge Table

fact_Repayments and fact_Collections do not relate directly to dim_Customer, dim_Branch, or dim_LoanProduct - they relate only to fact_Portfolio via LoanID. A repayment or a collection action belongs to a specific loan, and everything else about that loan (which customer, which branch, which product) is inherited by following the chain fact_Repayments > fact_Portfolio > dim_Customer/dim_Branch/dim_LoanProduct. Power BI resolves this automatically as long as the relationships are all single-direction, many-to-one, and chained correctly.

C4. Why Every Relationship Is Many-to-One and Single-Direction

Cardinality: each row in a fact table (one application, one disbursed loan, one repayment, one collection action) belongs to exactly one date, one customer, one branch, one officer, and one product - but any given date/customer/branch/officer/product can appear on many fact rows. That is the definition of a many-to-one relationship.

Filter direction: every relationship here is kept single-direction (dimension filters fact, and fact_Portfolio filters its two child fact tables). If cross filtering were set to "Both" everywhere, filtering fact_Applications by ApplicationChannel would also ripple into fact_Repayments and fact_Collections through the shared dim_Branch/dim_Date tables - producing confusing, hard-to-debug results. Keep every relationship single-direction.

C5. The Two-Dates-to-dim_Date Problem (Twice Over)

Both fact_Applications and fact_Portfolio have two legitimate date columns relating to dim_Date: submission/decision date in fact_Applications, and disbursement/maturity date in fact_Portfolio. In both cases, only ONE relationship per table pair can be Active - Active means "the relationship DAX uses automatically, unless a measure explicitly says otherwise." The submission/disbursement date is set Active in both tables; the second relationship in each table (DecisionDateKey, MaturityDateKey) is left Inactive (a dashed line in Model view) and is only invoked, on demand, inside specific measures using USERELATIONSHIP() - see Loans Maturing Next 30 Days and Applications Beyond Decision SLA in Section 6 below.

C6. Common Relationship Failures and How to Diagnose Them

  • A relationship auto-builds as many-to-many (shown as "*...*") - almost always means a key that should be unique on the "one" side has duplicates. Fix: find and remove the duplicate in dim_Branch/dim_Customer/dim_LoanProduct/ dim_LoanOfficer/dim_Date, or in fact_Portfolio's LoanID for the bridge relationships.
  • A relationship refuses to build, or shows a warning triangle - almost always a data type mismatch. Fix this in Power Query, never by forcing the relationship through.
  • A "(Blank)" category appears in a visual after a relationship is built - usually means a fact-table key value has no match in the dimension/bridge table (a typo, or a value trimmed on one side but not the other).

C7. Build the Measures Table

Home > Enter Data (or New Table):

_Measures = ROW("Info", "NTMB Loan Portfolio Measures - see Section 6 of this guide")

Hide the Info column (right-click > Hide in Report View), then reassign every measure created in Section 6 to live inside this table so all 25+ measures sit in one clean, browsable folder in the Fields pane rather than being scattered across nine data tables.

4. Solution - Every DAX Measure, Explained Line by Line

Every measure below should be created inside a dedicated measures table called _Measures (see Section 3.6). Read each card top to bottom: the DAX code first, then the line-by-line breakdown of what each part of the formula does, then why it was written that way, then its direct impact on the dashboard.

GROUP 1 - CORE COUNTING MEASURES

1.1 Total Applications
Total Applications = COUNTROWS(fact_Applications)

Line by line:

  • COUNTROWS(fact_Applications) counts every row currently visible in fact_Applications after all active filters (slicers, visual filters, cross-filters from slicing dimension tables) have been applied.
Why written this way: COUNTROWS is used instead of COUNT(fact_Applications[ApplicationID]) because it does not need to touch a specific column, so it is marginally faster and never breaks if a column is renamed.
Impact on the dashboard: this is the base measure that the entire application funnel is built from (approval rate, rejection rate, processing time). It is the top-left KPI card on the Origination page.
1.2 Approved Applications / Rejected Applications / Pending Applications
Approved Applications =
CALCULATE([Total Applications], fact_Applications[ApplicationStatus] = "Approved")

Rejected Applications =
CALCULATE([Total Applications], fact_Applications[ApplicationStatus] = "Rejected")

Pending Applications =
CALCULATE([Total Applications], fact_Applications[ApplicationStatus] = "Pending")

Line by line:

  • CALCULATE( ... ) changes the filter context that [Total Applications] is evaluated in.
  • fact_Applications[ApplicationStatus] = "..." overrides any existing filter on ApplicationStatus and restricts the row context to just that outcome.
Impact: these three feed the approval funnel visuals and the Approval Rate % measure below.
1.3 Total Loans Disbursed / Total Principal Disbursed
Total Loans Disbursed = COUNTROWS(fact_Portfolio)

Total Principal Disbursed = SUM(fact_Portfolio[PrincipalAmount])

Straightforward counting and summing aggregations over the core fact table. Total Principal Disbursed is the headline "how much money have we lent" KPI, formatted as currency (Naira).

1.4 Total Outstanding Balance
Total Outstanding Balance = SUM(fact_Portfolio[OutstandingBalance])

Adds the OutstandingBalance column across all currently-filtered loans. This is the "how much do customers currently owe us" KPI, and the denominator/numerator base for every risk ratio in Group 3.

1.5 Non-Performing Loans (count and balance)
Non-Performing Loan Count =
CALCULATE(
    [Total Loans Disbursed],
    fact_Portfolio[RiskClassification] IN { "Substandard", "Doubtful", "Loss" }
)

Non-Performing Loan Balance =
CALCULATE(
    [Total Outstanding Balance],
    fact_Portfolio[RiskClassification] IN { "Substandard", "Doubtful", "Loss" }
)

Line by line:

  • fact_Portfolio[RiskClassification] IN { "Substandard", "Doubtful", "Loss" } is a shorthand for an OR condition across the three prudential classifications that count as "non-performing" under standard banking regulation (Performing and Watch are NOT non-performing).
Why this grouping: banking regulators (and internal risk committees) define a loan as non-performing once it crosses roughly 90 days past due, which in this dataset's classification scheme corresponds to Substandard, Doubtful, and Loss.
Impact: these two measures are the direct numerator of the NPL Ratio, the single most important KPI in the entire dashboard.
1.6 Total Repayments Collected / Total Scheduled
Total Scheduled Repayments = SUM(fact_Repayments[ScheduledAmount])

Total Actual Repayments = SUM(fact_Repayments[ActualAmountPaid])

Straightforward SUM aggregations, used to compute the Collection Efficiency Ratio in Group 3 and displayed as twin KPI cards on the Collections page.

1.7 Total Amount Recovered (Collections)
Total Amount Recovered = SUM(fact_Collections[AmountRecovered])

Sums the AmountRecovered column across all collection actions. Used to show how much of the delinquent book has actually been clawed back through active collections effort, as distinct from normal scheduled repayments.

GROUP 2 - TIME INTELLIGENCE MEASURES

These require dim_Date to be marked as the official Date Table in Power BI (Table tools > Mark as Date Table > pick the Date column) because every time-intelligence DAX function (SAMEPERIODLASTYEAR, DATEADD, TOTALYTD, etc.) depends on a contiguous, unique-date calendar table with an active relationship to the fact table it is filtering.

2.1 Disbursements PY (Prior Year, same period)
Principal Disbursed PY =
CALCULATE(
    [Total Principal Disbursed],
    SAMEPERIODLASTYEAR(dim_Date[Date])
)

Line by line:

  • SAMEPERIODLASTYEAR(dim_Date[Date]) returns the same date range as whatever is currently filtered (e.g., January 2024) but shifted back exactly one year (January 2023).
  • CALCULATE re-evaluates [Total Principal Disbursed] inside that shifted date filter.
Impact: this is the comparison half of every YoY chart and KPI on the Executive Overview page, showing whether the bank is growing or shrinking its lending book year over year.
2.2 Disbursement YoY % Change
Disbursement YoY % Change =
VAR CurrentValue = [Total Principal Disbursed]
VAR PriorValue = [Principal Disbursed PY]
RETURN
    DIVIDE(CurrentValue - PriorValue, PriorValue)

Line by line:

  • VAR CurrentValue stores this period's disbursement total once, avoiding recalculating the base measure twice.
  • VAR PriorValue stores last year's figure using measure 2.1.
  • DIVIDE(CurrentValue - PriorValue, PriorValue) calculates percentage change and safely returns BLANK() instead of an error if PriorValue is 0.

Why DIVIDE and not /: DIVIDE has a built-in safe-divide behavior (returns BLANK or an optional default instead of a divide-by-zero error), which matters once the dashboard is filtered down to a branch/product combination that may have zero prior-year disbursements.

Impact: displayed as a KPI card with an up/down arrow and conditional color - the first number a Chief Risk Officer or Head of Lending looks at on a Monday morning portfolio review.
2.3 Disbursements YTD
Disbursements YTD = TOTALYTD([Total Principal Disbursed], dim_Date[Date])

Line by line:

  • TOTALYTD internally filters dim_Date[Date] from the first day of the current calendar year up to the latest date in the current filter context, then evaluates [Total Principal Disbursed] inside that filter.
Impact: used as a running cumulative total overlay on the Executive Overview line chart, letting management compare "how far into the year we are vs how much we have lent so far."
2.4 NPL Ratio 3-Month Trend (rolling average)
NPL Ratio 3M Avg =
AVERAGEX(
    DATESINPERIOD(dim_Date[Date], MAX(dim_Date[Date]), -3, MONTH),
    [NPL Ratio %]
)

Line by line:

  • DATESINPERIOD(dim_Date[Date], MAX(dim_Date[Date]), -3, MONTH) builds a table of dates covering the 3 months ending on whatever the latest date in context is.
  • AVERAGEX( table, expression ) iterates that date table, evaluates [NPL Ratio %] (Group 3) for each period, and averages the results.
Impact: smooths the naturally noisy monthly NPL ratio line chart so a single bad month of write-offs does not visually overstate a trend that isn't really there.

GROUP 3 - RATE AND RATIO MEASURES (industry-standard banking KPIs)

3.1 Approval Rate %
Approval Rate % = DIVIDE([Approved Applications], [Total Applications])

The percentage of applications that were approved. The single most-watched loan origination KPI, shown as a headline card on the Origination page.

3.2 Rejection Rate %
Rejection Rate % = DIVIDE([Rejected Applications], [Total Applications])

The mirror image of Approval Rate %, useful when analyzed by RejectionReason to identify the most common reasons customers are declined.

3.3 Average Processing Days
Average Processing Days = AVERAGE(fact_Applications[ProcessingDays])

Straightforward average; a key operational efficiency KPI showing how quickly the bank turns around a lending decision - directly affects customer experience and competitiveness.

3.4 NPL Ratio %
NPL Ratio % = DIVIDE([Non-Performing Loan Balance], [Total Outstanding Balance])

Line by line:

  • [Non-Performing Loan Balance] (Group 1) is the outstanding balance of loans classified Substandard, Doubtful, or Loss.
  • [Total Outstanding Balance] (Group 1) is the outstanding balance of the entire book.
  • DIVIDE(...) expresses this as a safe percentage.
Impact: NPL Ratio % is the single most important risk KPI in the entire dashboard - it is the number a bank's board and regulator watch first. It is displayed prominently on the Executive Overview page with conditional formatting (green below a target threshold, red above it).
3.5 Portfolio at Risk 30/60/90 (PAR30, PAR60, PAR90)
PAR 30 =
DIVIDE(
    CALCULATE([Total Outstanding Balance], fact_Portfolio[DaysPastDue] >= 30),
    [Total Outstanding Balance]
)

PAR 60 =
DIVIDE(
    CALCULATE([Total Outstanding Balance], fact_Portfolio[DaysPastDue] >= 60),
    [Total Outstanding Balance]
)

PAR 90 =
DIVIDE(
    CALCULATE([Total Outstanding Balance], fact_Portfolio[DaysPastDue] >= 90),
    [Total Outstanding Balance]
)

Line by line:

  • Each measure filters fact_Portfolio to loans whose DaysPastDue has crossed a specific threshold (30, 60, or 90 days), sums their outstanding balance, then divides by the total book.

Why three separate but almost identical measures instead of one parameterized measure: PAR30, PAR60, and PAR90 are each individually a named, standard industry metric that risk teams expect to see side by side on one page - collapsing them into a single "PAR at N days" measure with a parameter would actually make the report harder to read for a banking audience used to seeing all three at once.

Impact: these three measures, shown together as a small multiple or a combo chart, tell management not just how many loans are non-performing, but how quickly the book is deteriorating through the aging buckets - a portfolio with high PAR30 but low PAR90 is a very different risk story than one with high PAR90.
3.6 Collection Efficiency Ratio
Collection Efficiency Ratio = DIVIDE([Total Actual Repayments], [Total Scheduled Repayments])

The percentage of scheduled repayments that were actually collected. A ratio below 100% means the bank is collecting less than what was contractually due - the complement of this ratio (1 minus this value) is roughly the in-period delinquency rate.

3.7 Average Interest Rate (Portfolio Yield Proxy)
Average Interest Rate = AVERAGE(fact_Portfolio[InterestRatePct])

Simple average of the InterestRatePct column; used as a proxy for portfolio yield when compared across products, branches, or credit score bands - useful for pricing strategy discussions.

3.8 Write-Off Rate %
Written Off Balance =
CALCULATE([Total Principal Disbursed], fact_Portfolio[LoanStatus] = "Written Off")

Write-Off Rate % = DIVIDE([Written Off Balance], [Total Principal Disbursed])

Line by line:

  • Written Off Balance filters to only loans whose LoanStatus is "Written Off" and sums their original principal (not their outstanding balance, which is intentional - write-off rate is conventionally measured against what was originally lent).
  • Write-Off Rate % expresses this as a percentage of everything ever disbursed.
Impact: while NPL Ratio % shows current risk in the live book, Write-Off Rate % shows realized, permanent losses - the two measures answer different questions and both are needed on the Risk page.

GROUP 4 - APPLICATION FUNNEL & CHANNEL MEASURES

4.1 Applications by Channel Share %
Application Channel Share % =
DIVIDE([Total Applications], CALCULATE([Total Applications], ALL(fact_Applications[ApplicationChannel])))

Line by line:

  • ALL(fact_Applications[ApplicationChannel]) removes any existing filter on ApplicationChannel, so the denominator always represents the grand total across every channel, regardless of which channel the current row/visual is filtered to.
  • The numerator keeps the current filter context (e.g., a specific channel from a bar chart axis).
Impact: powers a 100%-stacked or share-of-total visual showing what proportion of applications come through Branch vs Mobile App vs Web Portal vs Agent Network - useful for a digital-channel adoption story.
4.2 Average Credit Score at Application
Average Credit Score = AVERAGE(fact_Applications[CreditScoreAtApplication])

Simple average; trended over time or split by product/channel, this shows whether the bank's underwriting is drifting toward riskier or safer applicants.

GROUP 5 - COLLECTIONS & RECOVERY MEASURES

5.1 Total Collection Actions / Successful Actions
Total Collection Actions = COUNTROWS(fact_Collections)

Successful Collection Actions =
CALCULATE([Total Collection Actions], fact_Collections[OutcomeStatus] = "Payment Received")

Straightforward counting measures; the ratio of the two (Group 5.2) shows collections team effectiveness.

5.2 Collection Success Rate %
Collection Success Rate % = DIVIDE([Successful Collection Actions], [Total Collection Actions])

The percentage of collection actions (calls, visits, notices) that directly resulted in a payment. A key performance measure for the collections/recovery team, often tracked per officer.

5.3 Recovery Rate on Non-Performing Loans
Recovery Rate % = DIVIDE([Total Amount Recovered], [Non-Performing Loan Balance])

Line by line:

  • Divides everything recovered through active collections effort by the total balance currently classified as non-performing.
Impact: shows what fraction of the "at risk" book has actually been clawed back - a low recovery rate against a high NPL balance is an early warning sign that collections capacity may need to be increased.

GROUP 6 - KPI STATUS / CONDITIONAL FORMATTING HELPER MEASURES

6.1 NPL Ratio Status (traffic-light helper)
NPL Ratio Status =
SWITCH(
    TRUE(),
    [NPL Ratio %] = BLANK(), "No Data",
    [NPL Ratio %] <= 0.05, "Healthy",
    [NPL Ratio %] <= 0.10, "Watch",
    "Elevated Risk"
)

Line by line:

  • SWITCH(TRUE(), condition1, result1, condition2, result2, ..., default) is the standard DAX pattern for an IF/ELSE-IF chain that is easier to read than nested IF() statements.
  • Each condition is checked top to bottom; the first TRUE condition wins.
  • Thresholds (5%, 10%) are illustrative targets that should be replaced with the institution's actual internal risk appetite - documented explicitly so students know these are placeholders, not universal regulatory standards.
Impact: this text measure is bound to a card's conditional formatting so the NPL Ratio KPI card shows green/amber/red without a separate visual just for color, and is also usable directly in a table/tooltip as a readable status label.
6.2 Approval Rate Status
Approval Rate Status =
SWITCH(
    TRUE(),
    [Approval Rate %] = BLANK(), "No Data",
    [Approval Rate %] >= 0.65, "Strong",
    [Approval Rate %] >= 0.45, "Moderate",
    "Weak"
)

Same SWITCH(TRUE()) pattern as 6.1, applied to origination performance thresholds.

GROUP 7 - THE INACTIVE-RELATIONSHIP MEASURES (USERELATIONSHIP)

7.1 Loans Maturing in Next 30 Days
Loans Maturing Next 30 Days =
CALCULATE(
    [Total Loans Disbursed],
    USERELATIONSHIP(fact_Portfolio[MaturityDateKey], dim_Date[DateKey]),
    DATESBETWEEN(
        dim_Date[Date],
        TODAY(),
        TODAY() + 30
    ),
    fact_Portfolio[LoanStatus] = "Active"
)

Line by line:

  • USERELATIONSHIP(fact_Portfolio[MaturityDateKey], dim_Date[DateKey]) temporarily activates the otherwise-inactive relationship between fact_Portfolio's maturity date and dim_Date, for the duration of this CALCULATE only. Without this line, the DATESBETWEEN filter below would silently apply to the ACTIVE relationship (disbursement date) instead, giving a completely wrong (and non-obvious) answer.
  • DATESBETWEEN(dim_Date[Date], TODAY(), TODAY() + 30) builds a 30-day forward-looking date window from today.
  • fact_Portfolio[LoanStatus] = "Active" excludes loans that are already closed, written off, or restructured, since only currently active loans have a meaningful upcoming maturity.
Why this measure is included deliberately: it is the single best teaching example in this dataset of (a) why Power BI restricts a table pair to one active relationship at a time, and (b) how USERELATIONSHIP lets a measure reach for the inactive one on demand. Every student should be able to explain, from this one measure, why fact_Portfolio[DisbursementDateKey] and fact_Portfolio[MaturityDateKey] cannot both be active relationships to dim_Date simultaneously.
Impact: this measure powers the "loans maturing soon" watch-list table on the Portfolio Risk page, which is directly actionable for a relationship manager planning renewal or exit conversations with customers.
7.2 Applications Awaiting Decision Beyond SLA (using the second inactive relationship)
Applications Beyond Decision SLA =
CALCULATE(
    [Total Applications],
    USERELATIONSHIP(fact_Applications[DecisionDateKey], dim_Date[DateKey]),
    fact_Applications[ApplicationStatus] = "Pending",
    fact_Applications[ProcessingDays] > 14
)

Line by line:

  • USERELATIONSHIP(fact_Applications[DecisionDateKey], dim_Date[DateKey]) activates the second, normally-inactive relationship on fact_Applications for this calculation only.
  • The two additional filter arguments restrict the count to applications that are still Pending and have already taken more than 14 days to process - i.e., applications breaching a typical service-level agreement (SLA).
Impact: demonstrates that the USERELATIONSHIP pattern from Group 7.1 is not a one-off trick for fact_Portfolio - it is a general technique that recurs anywhere a fact table has two legitimate dates against the same calendar table, which is a very common real-world modeling situation in lending, insurance, and subscription businesses alike.

7. Cross-Page Design Standards

These rules were applied consistently across all five pages so the finished report reads as one coherent product rather than five disconnected pages.

  • Every KPI card uses the same card visual style (rounded corners, 2px border, category label above value, YoY/target sub-label below in smaller gray text) for visual consistency.
  • Every page has the same slicer panel position (top strip, height 60px) so students learn to build a repeatable dashboard template, not a one-off page.
  • Every chart has a one-line "Why this chart" note placed in the Word document and HTML solution file (not on the canvas itself) so students learn the reasoning, not just the mechanics.
  • Tooltips: every column/bar/line visual should have a tooltip page or extended tooltip fields added (Branch, Product, Customer Segment) so hovering reveals context without needing to click through.
  • Bookmarks (optional stretch task): create a bookmark group toggling between "Balance view" and "Count view" on Page 3, to teach students bookmark + selection pane + button interactions.

8. Final Quality Checklist

  • Every visual on every page renders with no error triangles and no "(Blank)" categories.
  • Every KPI card's conditional formatting (NPL Ratio Status, Approval Rate Status) displays the correct color at realistic filter combinations (try filtering to a single small branch to confirm BLANK() handling works).
  • The Loans Maturing Next 30 Days measure returns different, sensible numbers than a naive count using the active DisbursementDateKey relationship - if it returns the same number, USERELATIONSHIP is not being applied correctly.
  • The Applications Beyond Decision SLA measure behaves the same way against fact_Applications's two dates.
  • Every slicer on every page cross-filters the visuals on that page correctly, and does not unexpectedly affect other pages (Power BI report-level vs page-level slicer scope should be deliberately chosen, not accidental).
  • All monetary values are formatted consistently (Naira, thousands separator) and all percentages are formatted to one decimal place throughout the report.
  • The report has been tested with at least three different slicer combinations to confirm no visual breaks or misleading blank results.
