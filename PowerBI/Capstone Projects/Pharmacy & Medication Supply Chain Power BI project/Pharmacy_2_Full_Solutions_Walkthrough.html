1. Solution Overview

This file is the fully worked solution to every task listed in the Tasks and Problem Brief file. It follows the standard Power BI project sequence: Load & Shape > Model & Relate > Measure with DAX > Visualise & Publish. Read it alongside the Tasks file rather than instead of it - the real learning happens in attempting each task before checking it here.

2. Step 1 - Loading & Preparing the Data

1Get Data

Open Power BI Desktop, choose Get Data > Excel Workbook, and select Pharmacy_Supply_Chain_Dataset.xlsx. In the Navigator window, tick all 11 data tables (skip the Read Me sheet) and click Transform Data to open Power Query Editor before loading, so every type can be checked first.

2Confirm data types

Click through each query and confirm: every *ID key column is Text; OrderDate, ExpectedDeliveryDate, ReceiptDate, ExpiryDate, SaleDate, TransferDate, ReturnDate, OpeningDate, DateHired and Date are all Date; every *NGN column is Whole Number. Power Query usually infers these correctly from a clean Excel source, but this dataset was built specifically so a student practises verifying, not assuming.

3Rename queries

Confirm the query names in the Queries pane exactly match the sheet names (Dim_Medications, Dim_Suppliers, Dim_Branches, Dim_Prescribers, Dim_Employees, Dim_Date, Fact_PurchaseOrders, Fact_StockReceipts, Fact_Sales, Fact_StockTransfers, Fact_Returns), since every relationship and DAX formula in this walkthrough references these exact names.

4Close & Apply

Click Close & Apply. Power BI loads all 11 tables into the semantic model. Open Model view and confirm you see 11 tables with no relationships yet - Power BI's autodetect sometimes proposes relationships on load; delete any that were auto-created so you build every one deliberately in the next step.

Power BI infers cardinality automatically from the data, but always open the relationship's properties and confirm it reads One-to-Many before moving to the next one.

When you build relationship 6 (Dim_Date to ExpectedDeliveryDate) and relationship 15 (Dim_Branches to ToBranchID), Power BI will automatically create them as inactive (shown as a dashed line in Model view) because an active path to each of those tables already exists. This is expected and correct - do not try to force them active.

Mark Dim_Date as a Date Table

Right-click Dim_Date in the Fields pane > Mark as Date Table > Mark as Date Table, then choose the Date column when prompted. Confirm the dialog reports no errors. This step is mandatory before any DATEADD, SAMEPERIODLASTYEAR or TOTALYTD measure will calculate correctly, because Power BI needs to verify the column is unique, contiguous and contains no gaps or blanks across the full calendar range.

Calculated Columns

Full Name = Dim_Employees[FirstName] & " " & Dim_Employees[LastName] Medication Label = Dim_Medications[MedicationName] & " (" & Dim_Medications[ATCCode] & ")"

Full Name concatenates FirstName and LastName so a single clean field can be placed on the Top 10 Dispensing Staff visual instead of two separate name columns. Medication Label combines a medication's display name and its ATC-style code into one string, giving students practice building a compound label field similar to the diagnosis-code pattern used in other Power BI training projects.

4. Step 3 - Building the DAX Measures

Create a blank Measures table first (Model view > Enter Data > leave it empty > name it Measures) and build every measure below inside it, in this order, since several later measures reference earlier ones.

Total Purchase Orders

Used on: Procurement & Supplier Performance
Total Purchase Orders = DISTINCTCOUNT(Fact_PurchaseOrders[POID])

Line by line:

  • DISTINCTCOUNT(Fact_PurchaseOrders[POID]) counts the number of unique purchase order lines remaining in the current filter context.
Why this measure exists: The foundation activity KPI for the whole procurement side of the business.
Impact on the dashboard: The first KPI card on the Procurement & Supplier Performance page.

Total Purchase Order Value

Used on: Procurement & Supplier Performance, Executive Overview
Total Purchase Order Value = SUM(Fact_PurchaseOrders[TotalOrderValueNGN])

Line by line:

  • SUM(Fact_PurchaseOrders[TotalOrderValueNGN]) adds up the billed value of every purchase order line currently in context.
Why this measure exists: Represents total procurement spend committed to suppliers, the starting point of the supply chain cost story.
Impact on the dashboard: A KPI card on both the Executive Overview and Procurement pages, and the value plotted on the monthly procurement spend trend line.

Total Quantity Ordered

Used on: Procurement & Supplier Performance
Total Quantity Ordered = SUM(Fact_PurchaseOrders[QuantityOrdered])

Line by line:

  • SUM(Fact_PurchaseOrders[QuantityOrdered]) adds up the units ordered across every purchase order line in the current filter context.
Why this measure exists: The denominator needed to calculate Fill Rate %, and a useful volume KPI in its own right.
Impact on the dashboard: Used internally by Fill Rate % and shown on its own on a procurement volume card.

Total Quantity Received

Used on: Procurement & Supplier Performance
Total Quantity Received = SUM(Fact_StockReceipts[QuantityReceived])

Line by line:

  • SUM(Fact_StockReceipts[QuantityReceived]) adds up units actually received across every receipt row in the current filter context, which may span multiple receipts per order.
Why this measure exists: Represents what physically arrived, as distinct from what was ordered - the two numbers should diverge for Partially Delivered and Delayed orders.
Impact on the dashboard: The numerator of the Fill Rate % measure.

Fill Rate %

Used on: Procurement & Supplier Performance
Fill Rate % = DIVIDE([Total Quantity Received], [Total Quantity Ordered], 0)

Line by line:

  • [Total Quantity Received] and [Total Quantity Ordered] are both measure references, so this ratio automatically recalculates correctly under any combination of Supplier, Medication or Date filters.
  • DIVIDE is used instead of the plain / operator so the measure safely returns 0, instead of an error, whenever there are no orders in the current filter context.
Why this measure exists: A core procurement-quality KPI: a Fill Rate consistently below 100% for a given supplier signals a reliability problem worth escalating.
Impact on the dashboard: Shown as a percentage KPI card and as a column in the supplier scorecard table.

Average Supplier Lead Time (Days)

Used on: Procurement & Supplier Performance
Average Supplier Lead Time (Days) = AVERAGE(Dim_Suppliers[LeadTimeDays])

Line by line:

  • AVERAGE(Dim_Suppliers[LeadTimeDays]) averages the supplier's own stated standard lead time across whichever suppliers remain in the current filter context, most commonly filtered down to a single supplier on the scorecard table.
Why this measure exists: Gives a quick reference point for how long a supplier says it needs, to compare against the measures below that calculate how long it actually took.
Impact on the dashboard: Shown as a column on the supplier scorecard table, next to On-Time Delivery %.

On-Time Delivery %

Used on: Procurement & Supplier Performance
On-Time Delivery % = VAR OnTimeOrders = CALCULATE( [Total Purchase Orders], Fact_PurchaseOrders[OrderStatus] = "Delivered", USERELATIONSHIP(Dim_Date[Date], Fact_PurchaseOrders[ExpectedDeliveryDate]) ) RETURN DIVIDE(OnTimeOrders, [Total Purchase Orders], 0)

Line by line:

  • VAR OnTimeOrders stores a CALCULATE call that filters down to orders with OrderStatus = "Delivered" while simultaneously activating the otherwise-inactive relationship between Dim_Date and ExpectedDeliveryDate using USERELATIONSHIP, for the duration of this measure only.
  • In practice this measure is best read alongside a Date slicer set to ExpectedDeliveryDate's month, letting a procurement manager ask 'of everything that was due this month, how much actually arrived' rather than 'of everything ordered this month, how much has arrived so far' - two subtly different but easily confused questions.
  • RETURN DIVIDE(...) expresses the on-time count as a percentage of all orders in the same context, safely returning 0 if there were no orders at all.
Why this measure exists: The single most important supplier-reliability KPI in the project, and the clearest possible demonstration of why USERELATIONSHIP exists: without it, this measure would silently use the wrong date column.
Impact on the dashboard: Displayed as a gauge visual on the Procurement & Supplier Performance page and as a column on the supplier scorecard table.

Total Sales Revenue

Used on: Executive Overview, Sales & Revenue Performance
Total Sales Revenue = SUM(Fact_Sales[TotalSaleNGN])

Line by line:

  • SUM(Fact_Sales[TotalSaleNGN]) adds up the net sale value (after discount) of every transaction in the current filter context.
Why this measure exists: The single most important revenue KPI in the whole project.
Impact on the dashboard: The largest KPI card on the Sales & Revenue page and the value plotted on the monthly revenue trend line on both that page and the Executive Overview.

Total Quantity Sold

Used on: Sales & Revenue Performance
Total Quantity Sold = SUM(Fact_Sales[QuantitySold])

Line by line:

  • SUM(Fact_Sales[QuantitySold]) adds up units sold across every transaction in the current filter context.
Why this measure exists: A volume KPI distinct from revenue, useful because a high-volume, low-cost medication and a low-volume, high-cost medication can generate similar revenue but represent very different operational realities.
Impact on the dashboard: A KPI card and the value used on the Top Selling Medications by Volume visual, shown alongside the revenue-based version.

Gross Margin NGN

Used on: Sales & Revenue Performance
Gross Margin NGN = SUMX( Fact_Sales, Fact_Sales[TotalSaleNGN] - (Fact_Sales[QuantitySold] * RELATED(Dim_Medications[UnitCostNGN])) )

Line by line:

  • SUMX iterates row by row over Fact_Sales rather than aggregating a single column, which is necessary here because gross margin must be calculated per transaction before it can be summed.
  • For each row, RELATED(Dim_Medications[UnitCostNGN]) pulls the medication's unit cost across the active many-to-one relationship from Fact_Sales to Dim_Medications, giving the cost basis for that specific sale.
  • Fact_Sales[QuantitySold] * RELATED(...) calculates the total cost of goods sold for that row, which is then subtracted from Fact_Sales[TotalSaleNGN] to give the row's profit, before SUMX adds every row's profit together.
Why this measure exists: Revenue alone does not tell a pharmacy business whether it is actually profitable on a given medication or branch; this measure introduces true row-by-row profitability.
Impact on the dashboard: Shown as a KPI card and as the value behind the Gross Margin % measure below.

Gross Margin %

Used on: Sales & Revenue Performance
Gross Margin % = DIVIDE([Gross Margin NGN], [Total Sales Revenue], 0)

Line by line:

  • Divides absolute profit by revenue to express margin as a percentage that is comparable across branches and medication categories of very different sizes.
Why this measure exists: The standard way to communicate profitability so it is comparable across a small branch and a large one.
Impact on the dashboard: Displayed as a KPI card with conditional formatting, and used on a Margin % by Category visual to identify the most and least profitable therapeutic categories.

Prescription Sales %

Used on: Sales & Revenue Performance
Prescription Sales % = DIVIDE( CALCULATE([Total Sales Revenue], Fact_Sales[IsPrescriptionSale] = "Yes"), [Total Sales Revenue], 0 )

Line by line:

  • CALCULATE filters revenue down to only transactions flagged IsPrescriptionSale = "Yes".
  • DIVIDE then expresses that subset as a percentage of all revenue in the same filter context.
Why this measure exists: A useful regulatory and business-mix indicator: a pharmacy business heavily skewed toward prescription sales has a different risk and staffing profile than one skewed toward OTC retail.
Impact on the dashboard: Displayed as a KPI card on the Sales & Revenue page.

Total Stock Transferred

Used on: Inventory & Loss Management
Total Stock Transferred = SUM(Fact_StockTransfers[QuantityTransferred])

Line by line:

  • SUM(Fact_StockTransfers[QuantityTransferred]) adds up units moved across every transfer row in the current filter context.
Why this measure exists: The base activity KPI for the inter-branch redistribution side of the supply chain.
Impact on the dashboard: A KPI card and the value behind the Stock Sent by Branch visual.

Stock Received via Transfer

Used on: Inventory & Loss Management
Stock Received via Transfer = CALCULATE( [Total Stock Transferred], USERELATIONSHIP(Dim_Branches[BranchID], Fact_StockTransfers[ToBranchID]) )

Line by line:

  • USERELATIONSHIP(Dim_Branches[BranchID], Fact_StockTransfers[ToBranchID]) temporarily activates the otherwise-inactive relationship on the receiving-branch column, for the duration of this CALCULATE call only.
  • Wrapping [Total Stock Transferred] inside that CALCULATE means the measure now attributes transferred quantity to the branch that RECEIVED the stock rather than the branch that sent it, without permanently changing which relationship is active for every other visual in the report.
Why this measure exists: This measure is the clearest possible demonstration of why role-playing dimensions and USERELATIONSHIP matter: placed in a table with BranchName on rows, Total Stock Transferred shows what a branch sent out, while this measure shows what the same branch received in.
Impact on the dashboard: Placed side by side with Total Stock Transferred in a matrix visual with BranchName on rows, so students can see the two numbers differ for every branch and understand why.

Total Loss Value

Used on: Inventory & Loss Management
Total Loss Value = SUM(Fact_Returns[ValueNGN])

Line by line:

  • SUM(Fact_Returns[ValueNGN]) adds up the cost value of every returned or written-off unit in the current filter context, calculated at the medication's unit cost rather than its selling price.
Why this measure exists: A core shrinkage/wastage KPI. Using cost rather than selling price is deliberate, since a written-off unit was never sold and therefore never generated the margin embedded in the selling price.
Impact on the dashboard: The main KPI card on the Inventory & Loss Management page.

Expired Stock Loss %

Used on: Inventory & Loss Management
Expired Stock Loss % = DIVIDE( CALCULATE([Total Loss Value], Fact_Returns[ReturnReason] = "Expired"), [Total Loss Value], 0 )

Line by line:

  • CALCULATE isolates loss value specifically attributed to the Expired reason.
  • DIVIDE expresses that as a percentage of total loss value from all reasons combined, which is useful because it separates a preventable inventory-management problem (expiry) from largely unavoidable ones (transit damage, recalls).
Why this measure exists: Expiry is usually the single most controllable source of pharmacy shrinkage, since it is a direct function of ordering too much stock relative to sell-through speed; this measure isolates that specific driver.
Impact on the dashboard: Shown as a KPI card next to Total Loss Value, and used on the Returns by Reason bar chart to highlight the Expired segment specifically.

Purchase Order Growth % (MoM)

Used on: Executive Overview
Purchase Order Growth % MoM = VAR CurrentMonthValue = [Total Purchase Order Value] VAR PreviousMonthValue = CALCULATE( [Total Purchase Order Value], DATEADD('Dim_Date'[Date], -1, MONTH) ) RETURN DIVIDE(CurrentMonthValue - PreviousMonthValue, PreviousMonthValue, 0)

Line by line:

  • VAR CurrentMonthValue stores [Total Purchase Order Value] for whichever month is currently in filter context.
  • VAR PreviousMonthValue uses CALCULATE with DATEADD('Dim_Date'[Date], -1, MONTH) to shift the entire filter context back exactly one month and re-evaluate the same measure inside that shifted context. This requires Dim_Date to be marked as an official Date Table with a contiguous, gap-free Date column.
  • RETURN DIVIDE(...) calculates the percentage change between the two variables, safely returning blank rather than an error for January 2021, the first month with no prior month available in this dataset.
Why this measure exists: Teaches the VAR/RETURN pattern for readable DAX and introduces time intelligence functions dependent on a properly configured date table, mirroring the equivalent admissions-growth measure from the hospital analytics project but applied to procurement spend.
Impact on the dashboard: Plotted as a secondary line on a combo chart against the Total Purchase Order Value column chart on the Executive Overview page.

Below Reorder Level Flag

Used on: Procurement & Supplier Performance
Below Reorder Level Flag = VAR TotalOrdered = [Total Quantity Ordered] VAR ReorderLevel = SELECTEDVALUE(Dim_Medications[ReorderLevelUnits]) RETURN IF( NOT ISBLANK(ReorderLevel) && TotalOrdered < ReorderLevel, "Below Reorder Level", "Adequate" )

Line by line:

  • SELECTEDVALUE(Dim_Medications[ReorderLevelUnits]) returns the reorder threshold only when exactly one medication is in context (for example, one row of a table visual); it returns blank if multiple medications are being summarised together, which is exactly the safety behaviour needed here.
  • The IF then compares total ordered quantity against that threshold and returns a simple text flag, which is easier to apply conditional formatting to on a table visual than a raw numeric comparison.
Why this measure exists: A simplified illustrative reorder-alert measure. Note this dataset does not model live stock-on-hand, so this measure compares period ordering volume against the reorder threshold as a teaching proxy, not as a substitute for a true point-in-time inventory balance, which is explicitly called out as a discussion point in the Solutions file.
Impact on the dashboard: Used as a conditional-formatting-driven column on a medication-level table, colouring rows red when flagged Below Reorder Level.

Cross-Page Consistency

Add a Year slicer (Dim_Date[Year]) and a Branch slicer (Dim_Branches[BranchName]) to every page in the same top-right position. Select both, go to the View ribbon, open Sync Slicers, and tick every page so a filter choice on Page 1 automatically applies across Pages 2 to 5. Add five navigation buttons (Insert > Buttons > Blank, with Action type set to Page Navigation) in a consistent header band so users never need the page tabs at the bottom.

6. Step 5 - Quality Check & Publish

1
Click through every slicer combination on every page and confirm no card visual shows (Blank) and no chart shows an empty plot area.
2
Right-click each measure and use Quick Measure or the Performance Analyzer (View ribbon) to confirm no visual takes longer than roughly one second to render on this dataset size.
3
Check that MonthName axes read January to December in calendar order, confirming the Sort By Column setting on Dim_Date took effect.
4
Verify Fill Rate %, On-Time Delivery % and Expired Stock Loss % conditional formatting rules trigger correctly by temporarily filtering to a supplier or month where the values cross the threshold.
5
Confirm the two inactive relationships remain dashed in Model view, and that Stock Received via Transfer genuinely returns a different number than Total Stock Transferred for the same branch, proving USERELATIONSHIP is working.
6
Save the .pbix file, then use File > Publish to publish the report to the Prodigy Training Hub Power BI Service workspace for the class.
