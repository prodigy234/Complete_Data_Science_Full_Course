This is the companion solution to 01_Tasks_and_Planning.html. Where that file asked you to attempt each step yourself, this file explains, in full, every decision: why each Power Query cleaning step matters, why each relationship has the cardinality it has, what every single DAX measure does line by line and why it was written that way, and how each of the five dashboard pages was designed, chart by chart. 2. Solution - Loading & Cleaning the Data

Step A - Connecting to the Source Workbook

  1. Open Power BI Desktop > Home > Get Data > Excel Workbook > select HSE_Training_Dataset.xlsx.
  2. In the Navigator window, tick exactly these seven tables: dim_Date, dim_Site, dim_Employee, fact_Incidents, fact_Observations, fact_Environmental, fact_Training. The README, Data_Dictionary and Model_Map sheets are for humans reading the workbook directly, not for the data model - leave them unchecked.
  3. Click "Transform Data" (never "Load" directly) so every table opens in the Power Query Editor first.
Why Transform Data, not Load: loading directly skips the one chance to catch type mismatches, stray whitespace, and null-handling problems while they are still cheap to fix. Every problem caught in Power Query costs one click to fix; the same problem caught later, after 30 DAX measures and 5 report pages are built on top of it, can cost hours.

Step B - Cleaning Each Table in Power Query

B1. dim_Date

The Date column must be set to Date type (not Date/Time) - Excel occasionally exports a hidden 00:00:00 time component that, left in place, causes a date to fail to match visually-identical dates in a fact table during troubleshooting. IsWeekend should be a true Boolean; if it imports as the text "TRUE"/"FALSE" instead, change its type explicitly via Transform > Data Type > True/False. DateKey must be Whole Number, matching the type used for the same column in every fact table - a relationship will refuse to build cleanly across mismatched types.

B2. dim_Site

Apply Trim and Clean (Transform > Format > Trim / Clean) to every text column. This single step prevents the single most common relationship failure in this entire exercise: a SiteID like "S01 " (with a trailing space) that looks identical to "S01" in the preview grid but will not match it in a relationship.

B3. dim_Employee

DateOfBirth and HireDate must both be Date type. Age is deliberately NOT built here as a Power Query calculated column - it is built later as a DAX measure (DATEDIF-style calculation against TODAY()) so that it always reflects the current date rather than being frozen at the moment the file was last refreshed. This is an important modeling principle: anything that depends on "now" belongs in DAX, not in a static ETL step.

B4. fact_Incidents

DateKey and SiteID both need Trim applied. EstimatedCostUSD must be Decimal Number (Fixed Decimal Number is also acceptable) - if it imported as text because of a stray currency symbol upstream, use Replace Values to strip non-numeric characters before changing the type. DateClosed should be Date type with genuine nulls for open investigations - watch for the literal text "None" surviving a CSV round-trip and convert it to null first via Replace Values. DaysLost must be Whole Number.

B5, B6, B7. fact_Observations, fact_Environmental, fact_Training

Score is Whole Number in both fact_Observations and fact_Training. Value and ComplianceLimit in fact_Environmental are Decimal Number. ExpiryDateKey in fact_Training is Whole Number, with true nulls (not 0) for any row where an expiry genuinely does not apply - a stray 0 would otherwise try to resolve to the epoch date and either break the relationship or silently create a phantom "blank date" bucket in every visual that uses it.

Once every table above is confirmed clean, click Home > Close & Apply.

3. Solution - Data Model, Relationships & Cardinality

Step C - Building the Data Model

C1. Mark the Date Table

Select dim_Date > Table Tools ribbon > Mark as Date Table > choose the Date column. This is a prerequisite, not a nicety: SAMEPERIODLASTYEAR, TOTALYTD, DATESINPERIOD and every other time-intelligence function used in Section 6 below silently misbehave (or outright error) against a calendar table that hasn't been marked, because Power BI needs to know, structurally, that this table's date column is contiguous and unique.

C3. Why Every Relationship Is Many-to-One and Single-Direction

Cardinality: each row in a fact table (one incident, one observation, one environmental reading, one training record) belongs to exactly one date, one site, and one employee - but any given date, site, or employee shows up across many fact rows. That asymmetry is the definition of a many-to-one relationship, and it is why every dimension table sits on the "one" side.

Filter direction: every relationship here is kept single-direction (dimension filters fact). If cross filtering were set to "Both" everywhere, filtering fact_Incidents by IncidentType would also silently ripple into fact_Observations and fact_Training through the shared dim_Site/dim_Date tables - producing numbers on unrelated visuals that change for reasons that are very difficult to explain or debug. Single-direction is the correct default for a star schema like this one; bidirectional filtering should only be added deliberately, for a specific, well-understood need.

C4. The Two Dates on fact_Training

fact_Training has two legitimate relationships to dim_Date: DateKey (when the training happened) and ExpiryDateKey (when the resulting certification expires). Power BI allows both relationships to exist, but only one of them can be Active at a time - Active means "the relationship DAX uses automatically, unless a measure explicitly says otherwise." DateKey is set Active because most measures need "how many trainings happened in a given month." ExpiryDateKey is left Inactive (shown as a dashed line in Model view) and is only invoked, on demand, inside the Certifications Expiring Next 30 Days measure (Section 6.4 below) using USERELATIONSHIP().

C5. Common Relationship Failures and How to Diagnose Them

  • A relationship auto-builds as many-to-many (shown as "*...*") - almost always means a key that should be unique on the "one" side has duplicates. Fix: find and remove the duplicate in dim_Site/dim_Employee/dim_Date.
  • A relationship refuses to build, or shows a warning triangle - almost always a data type mismatch (e.g., DateKey stored as Text on one side, Whole Number on the other). Fix this in Power Query, never by forcing the relationship through.
  • A "(Blank)" category appears in a visual after a relationship is built - usually means a fact-table key value has no match in the dimension table (a typo, or a value that was trimmed on one side but not the other).

C6. Build the Measures Table

Home > Enter Data (or New Table):

_Measures = ROW("Info", "HSE Measures - see Section 6 of this guide")

Hide the Info column (right-click > Hide in Report View), then reassign every measure created in Section 6 to live inside this table (select the measure, use the Home ribbon's "Table" / "Home Table" control) so all 30+ measures sit in one clean, browsable folder in the Fields pane rather than being scattered across seven data tables.

4. Solution - Every DAX Measure, Explained Line by Line

Every measure below should be created inside a dedicated measures table called _Measures (see Section 3.6). Read each card top to bottom: the DAX code first, then the line-by-line breakdown of what each part of the formula does, then why it was written that way, then its direct impact on the dashboard.

GROUP 1 - CORE COUNTING MEASURES

1.1 Total Incidents
Total Incidents = COUNTROWS(fact_Incidents)

Line by line:

  • COUNTROWS(fact_Incidents) counts every row currently visible in fact_Incidents after all active filters (slicers, visual filters, cross-filters from slicing dimension tables) have been applied.
Why written this way: COUNTROWS is used instead of COUNT(fact_Incidents[IncidentID]) because it does not need to touch a specific column, so it is marginally faster and never breaks if a column is renamed.
Impact on the dashboard: this is the base measure that almost every other incident measure is built from (rates, percentages, YoY change). It is the KPI card at the top-left of Page 1 and Page 2, and it is the value field behind every incident bar/line chart in this workbook.
1.2 Total Near Misses
Total Near Misses = CALCULATE([Total Incidents], fact_Incidents[IncidentType] = "Near Miss")

Line by line:

  • CALCULATE( ... ) changes the filter context that [Total Incidents] is evaluated in.
  • fact_Incidents[IncidentType] = "Near Miss" is a filter argument that overrides any existing filter on IncidentType and restricts the row context to only Near Miss rows.
Why: Near misses sit at the base of the safety pyramid and are a strong leading indicator - the more near misses reported (and acted on), the more incidents are typically prevented downstream.
Impact: used as its own KPI card and as the numerator in the Near-Miss-to-LTI ratio, which HSE managers use to judge whether the reporting culture is healthy.
1.3 Total Lost Time Injuries (LTI)
Total LTI = CALCULATE([Total Incidents], fact_Incidents[IncidentType] = "Lost Time Injury")

Same mechanic as 1.2, filtered to "Lost Time Injury". This is a lagging indicator - the inverse of Near Misses - and is the numerator of the LTIFR measure in Group 3.

1.4 Total Fatalities
Total Fatalities = CALCULATE([Total Incidents], fact_Incidents[IncidentType] = "Fatality")

Used sparingly - typically as a single always-visible KPI card with conditional formatting (red if > 0) because even one fatality is organizationally significant regardless of all other metrics. Rarely charted as a trend line because the numbers are intentionally very small in a well-run operation.

1.5 Total Days Lost
Total Days Lost = SUM(fact_Incidents[DaysLost])

Line by line:

  • SUM(fact_Incidents[DaysLost]) adds the DaysLost column across all currently-filtered rows.
Impact: feeds the Severity Rate measure (Group 3) and is displayed as its own KPI to show the real productivity cost of incidents, not just the incident count.
1.6 Total Incident Cost
Total Incident Cost = SUM(fact_Incidents[EstimatedCostUSD])

Straightforward SUM aggregation. Displayed formatted as currency ($#,##0) on the Executive Overview page and used to compute Average Cost per Incident (Group 3).

1.7 Total Observations / Safe Observations / At-Risk Observations
Total Observations = COUNTROWS(fact_Observations)

Safe Observations =
CALCULATE([Total Observations], fact_Observations[ObservationType] = "Safe Behavior")

At-Risk Observations =
CALCULATE([Total Observations], fact_Observations[ObservationType] = "At-Risk Behavior")
Impact: these three feed the Safe Behavior % measure in Group 4 and populate the BBS (Behaviour-Based Safety) visuals on Page 3.
1.8 Total Environmental Readings / Compliant Readings / Non-Compliant Readings
Total Env Readings = COUNTROWS(fact_Environmental)

Compliant Readings =
CALCULATE([Total Env Readings], fact_Environmental[ComplianceStatus] = "Compliant")

Non-Compliant Readings =
CALCULATE([Total Env Readings], fact_Environmental[ComplianceStatus] = "Non-Compliant")
Impact: feed Environmental Compliance % (Group 5) and the KPI cards/donut chart on Page 4.
1.9 Total Trainings / Passed Trainings / Failed Trainings
Total Trainings = COUNTROWS(fact_Training)

Passed Trainings =
CALCULATE([Total Trainings], fact_Training[ResultStatus] = "Pass")

Failed Trainings =
CALCULATE([Total Trainings], fact_Training[ResultStatus] = "Fail")
Impact: feed Training Pass Rate % (Group 6) and the Page 5 KPI cards and charts.

GROUP 2 - TIME INTELLIGENCE MEASURES

These require dim_Date to be marked as the official Date Table in Power BI (Table tools > Mark as Date Table > pick the Date column) because every time-intelligence DAX function (SAMEPERIODLASTYEAR, DATEADD, TOTALYTD, etc.) depends on a contiguous, unique-date calendar table with an active relationship to the fact table it is filtering.

2.1 Incidents PY (Prior Year, same period)
Incidents PY =
CALCULATE(
    [Total Incidents],
    SAMEPERIODLASTYEAR(dim_Date[Date])
)

Line by line:

  • SAMEPERIODLASTYEAR(dim_Date[Date]) returns the same date range as whatever is currently filtered (e.g., January 2024) but shifted back exactly one year (January 2023).
  • CALCULATE re-evaluates [Total Incidents] inside that shifted date filter.
Impact: this is the "comparison" half of every YoY chart and KPI on the Executive Overview page.
2.2 Incidents YoY % Change
Incidents YoY % Change =
VAR CurrentValue = [Total Incidents]
VAR PriorValue = [Incidents PY]
RETURN
    DIVIDE(CurrentValue - PriorValue, PriorValue)

Line by line:

  • VAR CurrentValue stores this period's incident count once, avoiding recalculating [Total Incidents] twice.
  • VAR PriorValue stores last year's figure using measure 2.1.
  • DIVIDE(CurrentValue - PriorValue, PriorValue) calculates percentage change and safely returns BLANK() instead of an error if PriorValue is 0.

Why DIVIDE and not /: DIVIDE has a built-in safe-divide behavior (returns BLANK or an optional third-argument default instead of throwing a divide-by-zero error), which matters a great deal once the dashboard is filtered down to a site/month combination that may have zero prior-year incidents.

Impact: displayed as a KPI card with an up/down arrow and conditional color (red = incidents increased, green = incidents decreased) - this single measure is usually the first thing an HSE director looks at on the Monday morning review.
2.3 Incidents YTD
Incidents YTD =
TOTALYTD([Total Incidents], dim_Date[Date])

Line by line:

  • TOTALYTD is a time-intelligence shorthand that internally filters dim_Date[Date] from the first day of the current fiscal/calendar year up to the latest date in the current filter context, then evaluates [Total Incidents] inside that filter.
Impact: used in the Page 1 line chart as a running cumulative total overlay, letting students compare "how far we are into the year vs how many incidents have already happened."
2.4 Rolling 3-Month Average Incidents
Incidents 3M Avg =
AVERAGEX(
    DATESINPERIOD(dim_Date[Date], MAX(dim_Date[Date]), -3, MONTH),
    [Total Incidents]
)

Line by line:

  • DATESINPERIOD(dim_Date[Date], MAX(dim_Date[Date]), -3, MONTH) builds a table of dates covering the 3 months ending on whatever the latest date in context is.
  • AVERAGEX( table, expression ) iterates that date table row by row (in this case, effectively month by month once combined with a monthly-grain visual), evaluates [Total Incidents] for each, and averages the results.
Impact: smooths the noisy monthly incident line chart on Page 1 so a trend line doesn't overreact to a single bad month - a standard leading-indicator smoothing technique in HSE reporting.

GROUP 3 - RATE AND RATIO MEASURES (industry-standard HSE KPIs)

These use one important supporting measure, Total Hours Worked, which is an ESTIMATE because this teaching dataset does not include a payroll/timesheet fact table. This assumption is called out deliberately so students learn to document assumptions inside their DAX.

3.1 Active Employees (headcount)
Active Employees = DISTINCTCOUNT(dim_Employee[EmployeeID])

Counts unique employees in the current filter context (e.g., filtered to one site or one department). Used as the denominator for per-capita measures.

3.2 Total Hours Worked (estimated)
Total Hours Worked =
VAR WorkingDaysInPeriod =
    CALCULATE(
        COUNTROWS(dim_Date),
        dim_Date[IsWeekend] = FALSE()
    )
RETURN
    [Active Employees] * WorkingDaysInPeriod * 8

Line by line:

  • VAR WorkingDaysInPeriod counts the weekdays (Monday-Friday) inside whatever date range is currently filtered, using the IsWeekend flag built into dim_Date.
  • The RETURN line multiplies headcount x working days x an assumed 8-hour shift.
Documented assumption: real HSE reporting uses actual payroll/timesheet hours; this dataset approximates it so LTIFR/TRIR can still be taught. Students should replace this with a real hours-worked fact table when they apply this to an actual company dataset.
Impact: denominator for LTIFR and TRIR below - without it, those two industry-standard KPIs could not be calculated at all.
3.3 LTIFR (Lost Time Injury Frequency Rate, per 200,000 hours)
LTIFR =
DIVIDE([Total LTI] * 200000, [Total Hours Worked])

Line by line:

  • [Total LTI] * 200000 scales lost-time injuries to the standard OSHA-style base rate of 200,000 hours (equivalent to 100 employees working 40 hours/week for 50 weeks).
  • DIVIDE( ..., [Total Hours Worked]) produces the rate safely.
Impact: this is the single most-watched KPI in almost every real-world HSE dashboard; it lets sites of very different sizes be compared fairly (a big site will always have more raw incidents than a small site, but LTIFR normalizes for exposure hours).
3.4 TRIR (Total Recordable Incident Rate, per 200,000 hours)
Total Recordable Incidents =
CALCULATE(
    [Total Incidents],
    fact_Incidents[IncidentType] IN
        { "Medical Treatment Case", "Restricted Work Case", "Lost Time Injury", "Fatality" }
)

TRIR =
DIVIDE([Total Recordable Incidents] * 200000, [Total Hours Worked])

Line by line:

  • fact_Incidents[IncidentType] IN { ... } is a shorthand for an OR condition across the four incident types that count as "recordable" under standard HSE classification (near misses and first-aid-only cases do NOT count as recordable).
  • The TRIR calculation follows the same 200,000-hour scaling logic as LTIFR.
Impact: TRIR is broader than LTIFR (it includes cases that didn't cause lost time) and is the second most-watched HSE KPI; shown side-by-side with LTIFR as twin KPI cards on Page 1.
3.5 Severity Rate
Severity Rate =
DIVIDE([Total Days Lost] * 200000, [Total Hours Worked])

Same normalization logic as LTIFR/TRIR, but measures how severe incidents are (days lost) rather than how frequent they are. A site could have a low LTIFR but a high Severity Rate if its few incidents tend to be serious - this measure exists specifically to catch that pattern.

3.6 Incident Rate per 100 Employees
Incidents per 100 Employees =
DIVIDE([Total Incidents] * 100, [Active Employees])

A simpler, non-hours-based normalization that is easier for non-technical stakeholders to read than LTIFR. Used on the site comparison bar chart (Page 1) as a secondary label.

3.7 Average Cost per Incident
Average Cost per Incident =
DIVIDE([Total Incident Cost], [Total Incidents])

Straightforward ratio; used to show finance stakeholders the average financial exposure per event, and trended over time to show whether corrective actions are reducing incident severity in cost terms even if the count of incidents isn't falling as fast.

3.8 Near Miss to LTI Ratio
Near Miss to LTI Ratio =
DIVIDE([Total Near Misses], [Total LTI])

A classic leading-vs-lagging indicator ratio. A healthy safety reporting culture typically shows a HIGH ratio (many near misses reported for every actual injury), because it means people are reporting small problems before they become big ones. A LOW ratio can mean either genuinely few near misses, or - more worryingly - under-reporting.

GROUP 4 - SAFETY BEHAVIOUR (BBS) MEASURES

4.1 Safe Behavior %
Safe Behavior % = DIVIDE([Safe Observations], [Total Observations])

Percentage of all logged observations that were rated as safe behavior. Displayed as a KPI card formatted as a percentage, with conditional formatting (green above 80%, amber 60-80%, red below 60%) - thresholds documented in the Word document.

4.2 Average Safety Score
Average Safety Score = AVERAGE(fact_Observations[Score])

Straightforward average of the 1-10 Score column; used as a secondary quality-of-behavior indicator alongside the simpler Safe Behavior %.

4.3 High Risk Observations
High Risk Observations =
CALCULATE([Total Observations], fact_Observations[RiskRating] = "High")

Isolates the most serious at-risk observations; charted separately because a High-risk observation deserves more management attention than a Low-risk one even though both count as "At-Risk Behavior."

GROUP 5 - ENVIRONMENTAL MEASURES

5.1 Environmental Compliance %
Environmental Compliance % = DIVIDE([Compliant Readings], [Total Env Readings])

Percentage of all environmental readings that fell within their ComplianceLimit. This is the headline KPI on Page 4.

5.2 Average Value by Parameter
Avg Environmental Value = AVERAGE(fact_Environmental[Value])

Used inside a matrix/table visual where ParameterType is a row so each parameter's average naturally breaks out per row via the visual's own filter context - the DAX itself stays simple because Power BI's automatic row-context filtering does the segmentation work.

5.3 Variance to Compliance Limit
Variance to Limit % =
VAR AvgValue = [Avg Environmental Value]
VAR AvgLimit = AVERAGE(fact_Environmental[ComplianceLimit])
RETURN
    DIVIDE(AvgValue - AvgLimit, AvgLimit)

Line by line:

  • AvgValue captures the average reading in the current context.
  • AvgLimit captures the average allowed limit in the same context.
  • The RETURN line expresses how far over (positive) or under (negative) the limit the site or parameter is running, as a percentage.
Impact: used as a conditional-formatted column inside the Page 4 table so reviewers can spot which parameter, at which site, is closest to breaching its limit - even before it actually goes Non-Compliant.

GROUP 6 - TRAINING MEASURES

6.1 Training Pass Rate %
Training Pass Rate % = DIVIDE([Passed Trainings], [Total Trainings])

Basic pass-rate percentage, headline KPI on Page 5.

6.2 Average Training Score
Average Training Score = AVERAGE(fact_Training[Score])

Simple average, used alongside pass rate because a course can have a 100% pass rate (60+ score) while still trending down in average score - the two measures catch different problems.

6.3 Certifications Expiring Soon
Certifications Expiring Soon =
CALCULATE(
    [Total Trainings],
    fact_Training[CertificationStatus] = "Expiring Soon"
)

Simple filtered count, but conceptually important because of where its date actually lives:

CertificationStatus is driven by ExpiryDateKey, a SECOND relationship to dim_Date that is INACTIVE by default (see Group 7 below for how to reactivate it inside a measure).

6.4 Certifications Expiring in Next 30 Days (using USERELATIONSHIP)
Certifications Expiring Next 30 Days =
CALCULATE(
    [Total Trainings],
    USERELATIONSHIP(fact_Training[ExpiryDateKey], dim_Date[DateKey]),
    DATESBETWEEN(
        dim_Date[Date],
        TODAY(),
        TODAY() + 30
    )
)

Line by line:

  • USERELATIONSHIP(fact_Training[ExpiryDateKey], dim_Date[DateKey]) temporarily activates the otherwise-inactive relationship between fact_Training's expiry date and dim_Date, for the duration of this CALCULATE only. Without this line, the DATESBETWEEN filter below would silently apply to the ACTIVE relationship (training delivery date) instead, giving a completely wrong (and un-obvious) answer.
  • DATESBETWEEN(dim_Date[Date], TODAY(), TODAY()+30) builds a 30-day forward-looking date window from today.
Why this measure is included deliberately: it is the single best teaching example in this whole dataset of (a) why Power BI restricts a table pair to one active relationship at a time, and (b) how USERELATIONSHIP lets a measure reach for the inactive one on demand. Every student should be able to explain, from this one measure, why fact_Training[DateKey] and fact_Training[ExpiryDateKey] cannot both be active relationships to dim_Date simultaneously.
Impact: this measure powers the "certifications expiring soon" alert table on Page 5, which is the single most actionable item on that page for an HSE training coordinator.

GROUP 7 - KPI STATUS / CONDITIONAL FORMATTING HELPER MEASURES

7.1 LTIFR Status (traffic-light helper)
LTIFR Status =
SWITCH(
    TRUE(),
    [LTIFR] = BLANK(), "No Data",
    [LTIFR] <= 0.5, "On Target",
    [LTIFR] <= 1.5, "Watch",
    "Off Target"
)

Line by line:

  • SWITCH(TRUE(), condition1, result1, condition2, result2, ..., default) is the standard DAX pattern for an IF/ELSE-IF chain that is easier to read than nested IF() statements.
  • Each condition is checked top to bottom; the first TRUE condition wins.
  • Thresholds (0.5, 1.5) are illustrative targets that should be replaced with the organization's actual internal safety targets - documented explicitly so students know these are placeholders, not universal HSE standards.
Impact: this text measure is bound to a card's conditional formatting / to a KPI visual's "format by rules" so the LTIFR card shows green/amber/red without a separate visual just for color - and it is also usable directly in a table/tooltip as a readable status label.
7.2 Environmental Compliance Status
Environmental Compliance Status =
SWITCH(
    TRUE(),
    [Environmental Compliance %] = BLANK(), "No Data",
    [Environmental Compliance %] >= 0.95, "Compliant",
    [Environmental Compliance %] >= 0.85, "Marginal",
    "Non-Compliant"
)

Same SWITCH(TRUE()) pattern as 7.1, applied to environmental compliance thresholds.

Used to color the Page 4 KPI card and the site-level compliance table.

Design: Card - "Total Days Lost" -> measure [Total Days Lost].

Training Pass Rate

Design: Card - "Training Pass Rate" -> measure [Training Pass Rate %], formatted 0.0%.

Design: Line and clustered column chart - X axis: dim_Date[MonthShort] (sorted by MonthNumber), Columns: [Total Incidents] for current year, Line: [Incidents PY] for prior year overlay.

Why this chart: overlaying current vs prior year on the same month axis is the fastest way for an executive to see if the organization is improving seasonally, not just in raw totals.

Design: Donut chart - Legend: fact_Incidents[Severity], Value: [Total Incidents].

7. Cross-Page Design Standards

These rules were applied consistently across all five pages so the finished report reads as one coherent product rather than five disconnected pages.

  • Every KPI card uses the same card visual style (rounded corners, 2px border, category label above value, YoY/target sub-label below in smaller gray text) for visual consistency.
  • Every page has the same slicer panel position (top strip, height 60px) so students learn to build a repeatable dashboard template, not a one-off page.
  • Every chart has a one-line "Why this chart" note placed in the Word document and HTML solution file (not on the canvas itself) so students learn the reasoning, not just the mechanics.
  • Tooltips: every column/bar/line visual should have a tooltip page or extended tooltip fields added (Site, Department, Date) so hovering reveals context without needing to click through.
  • Bookmarks (optional stretch task): create a bookmark group toggling between "Count view" and "Rate view" on Page 1, to teach students bookmark + selection pane + button interactions.

8. Final Quality Checklist

  • Every visual on every page renders with no error triangles and no "(Blank)" categories.
  • Every KPI card's conditional formatting (LTIFR Status, Environmental Compliance Status) displays the correct color at realistic filter combinations (try filtering to a single small site to confirm BLANK() handling works).
  • The Certifications Expiring Next 30 Days measure returns different, sensible numbers than a naive count using the active DateKey relationship - if it returns the same number, USERELATIONSHIP is not being applied correctly.
  • Every slicer on every page cross-filters the visuals on that page correctly, and does not unexpectedly affect other pages (Power BI report-level vs page-level slicer scope should be deliberately chosen, not accidental).
  • All monetary values are formatted consistently (USD, thousands separator) and all percentages are formatted to one decimal place throughout the report.
  • The report has been tested with at least three different slicer combinations to confirm no visual breaks or shows misleading blank results.
