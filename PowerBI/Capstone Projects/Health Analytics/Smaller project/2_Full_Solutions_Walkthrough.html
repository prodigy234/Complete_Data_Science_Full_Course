1. Solution Overview

This file is the fully worked solution to every task listed in the Tasks and Problem Brief file. It follows the standard Power BI project sequence: Load & Shape > Model & Relate > Measure with DAX > Visualise & Publish. Read it alongside the Tasks file rather than instead of it - the real learning happens in attempting each task before checking it here.

2. Step 1 - Loading & Preparing the Data

1Get Data

Open Power BI Desktop, choose Get Data > Excel Workbook, and select Hospital_Health_Analytics_Dataset.xlsx. In the Navigator window, tick all 8 data tables (skip the Read Me sheet) and click Transform Data to open Power Query Editor before loading, so every type can be checked first.

2Confirm data types

Click through each query and confirm: every *ID key column is Text; DateOfBirth, RegistrationDate, DateJoined, AdmissionDate, DischargeDate, PaymentDate, TreatmentDate and Date are all Date; every *NGN column is Whole Number. Power Query usually infers these correctly from a clean Excel source, but this dataset was built specifically so a student practises verifying, not assuming.

3Rename queries

Confirm the query names in the Queries pane exactly match the sheet names (Dim_Patients, Dim_Doctors, Dim_Departments, Dim_Diagnosis, Dim_Date, Fact_Admissions, Fact_Billing, Fact_Treatments), since every relationship and DAX formula in this walkthrough references these exact names.

4Close & Apply

Click Close & Apply. Power BI loads all 8 tables into the semantic model. Open Model view and confirm you see 8 tables with no relationships yet - Power BI's autodetect sometimes proposes relationships on load; delete any that were auto-created so you build every one deliberately in the next step.

3. Step 2 - Building the Data Model

In Model view, drag from the key column on the dimension (one) side to the foreign key column on the fact (many) side for each relationship below, in this order. Power BI infers cardinality automatically from the data, but always open the relationship's properties and confirm it reads One-to-Many before moving to the next one.

#RelationshipCardinalityCross FilterStatusWhy
1Dim_Patients[PatientID] → Fact_Admissions[PatientID]One-to-Many (1:*)Single (Dim_Patients filters Fact_Admissions)ACTIVEThe foundation relationship of the whole model. One patient can have many admissions over the two-year period, which is why PatientID must be unique in Dim_Patients but repeats freely in Fact_Admissions.
2Dim_Doctors[DoctorID] → Fact_Admissions[DoctorID]One-to-Many (1:*)SingleACTIVELets every visual filter admissions by doctor. Because DoctorID is unique in Dim_Doctors, Power BI can autodetect the 'one' side correctly as long as Dim_Doctors is not duplicated anywhere else.
3Dim_Departments[DepartmentID] → Fact_Admissions[DepartmentID]One-to-Many (1:*)SingleACTIVEThe primary relationship used for department-level filtering across every dashboard page.
4Dim_Diagnosis[DiagnosisID] → Fact_Admissions[DiagnosisID]One-to-Many (1:*)SingleACTIVEConnects every admission to exactly one clinical diagnosis, enabling the disease-burden analysis.
5Dim_Departments[DepartmentID] → Dim_Doctors[DepartmentID]One-to-Many (1:*)SingleACTIVEThis is the snowflake link. It means a slicer on DepartmentName will filter Dim_Doctors, which will then filter Fact_Admissions through the DoctorID relationship - a two-hop filter path students should trace visually in Model view.
6Dim_Date[Date] → Fact_Admissions[AdmissionDate]One-to-Many (1:*)SingleACTIVEThe primary, active time relationship for the whole project. Every default monthly trend visual uses this path unless a measure explicitly overrides it.
7Dim_Date[Date] → Fact_Admissions[DischargeDate]One-to-Many (1:*)SingleINACTIVEPower BI only allows one ACTIVE relationship between any two tables at a time, so this second link to Dim_Date must be created as INACTIVE. It is switched on inside specific measures using CALCULATE with USERELATIONSHIP('Dim_Date'[Date], Fact_Admissions[DischargeDate]).
8Fact_Admissions[AdmissionID] → Fact_Billing[AdmissionID]One-to-Many (1:*)Single (Fact_Admissions filters Fact_Billing)ACTIVEA fact-to-fact relationship. About 12% of admissions have two billing lines, which is why this must be modelled as one-to-many rather than one-to-one.
9Fact_Admissions[AdmissionID] → Fact_Treatments[AdmissionID]One-to-Many (1:*)SingleACTIVEAnother fact-to-fact relationship; each admission generates one to five treatment rows.
10Dim_Date[Date] → Fact_Billing[PaymentDate]One-to-Many (1:*)SingleACTIVEBecause Fact_Billing is not directly reachable from Dim_Date through Fact_Admissions in a single active hop for payment purposes, a direct relationship on PaymentDate is added and kept active so financial trend visuals default to payment-date behaviour.
11Dim_Date[Date] → Fact_Treatments[TreatmentDate]One-to-Many (1:*)SingleACTIVEGives clinical operations visuals (most common treatments over time) their own direct time relationship, independent of the admission date.
12Dim_Doctors[DoctorID] → Fact_Treatments[AdministeredByDoctorID]One-to-Many (1:*)SingleINACTIVEDim_Doctors already has an active relationship to Fact_Admissions[DoctorID]. A second relationship to Fact_Treatments must therefore be created INACTIVE and activated with USERELATIONSHIP inside the specific measures that analyse treatments by the administering doctor, to avoid an ambiguous model.
When you build relationship 7 (Dim_Date to DischargeDate) and relationship 12 (Dim_Doctors to AdministeredByDoctorID), Power BI will automatically create them as inactive (shown as a dashed line in Model view) because an active path to each of those tables already exists. This is expected and correct - do not try to force them active.

Mark Dim_Date as a Date Table

Right-click Dim_Date in the Fields pane > Mark as Date Table > Mark as Date Table, then choose the Date column when prompted. Confirm the dialog reports no errors. This step is mandatory before any DATEADD, SAMEPERIODLASTYEAR or TOTALYTD measure will calculate correctly, because Power BI needs to verify the column is unique, contiguous and contains no gaps or blanks across the full calendar range.

Calculated Columns

Full Name = Dim_Patients[FirstName] & " " & Dim_Patients[LastName] Full Name (Doctor) = "Dr. " & Dim_Doctors[FirstName] & " " & Dim_Doctors[LastName] Age Band = SWITCH( TRUE(), Dim_Patients[Age] < 18, "0-17", Dim_Patients[Age] <= 35, "18-35", Dim_Patients[Age] <= 55, "36-55", Dim_Patients[Age] <= 75, "56-75", "76+" )

SWITCH(TRUE(), ...) works by evaluating each condition in order and returning the result next to the first one that is TRUE, which is a cleaner alternative to nested IF statements once there are more than two or three bands.

4. Step 3 - Building the DAX Measures

Create a blank Measures table first (Model view > Enter Data > leave it empty > name it Measures) and build every measure below inside it, in this order, since several later measures reference earlier ones.

Total Admissions

Used on: Used on every page
Total Admissions = DISTINCTCOUNT(Fact_Admissions[AdmissionID])

Line by line:

  • DISTINCTCOUNT(Fact_Admissions[AdmissionID]) counts the number of unique AdmissionID values remaining in the current filter context.
  • DISTINCTCOUNT is used instead of COUNTROWS because AdmissionID is already the grain of the table, so both would give the same answer here - but DISTINCTCOUNT is the safer habit since it protects the measure if a duplicate ever slips into the table.
Why this measure exists: This is the foundation KPI of the entire report. Almost every other measure either builds on it (as a denominator) or is filtered the same way it is.
Impact on the dashboard: Appears as the first KPI card on the Executive Overview page and is the value plotted on the Y-axis of the monthly admissions trend line chart.

Total Patients

Used on: Executive Overview, Demographics
Total Patients = DISTINCTCOUNT(Fact_Admissions[PatientID])

Line by line:

  • DISTINCTCOUNT(Fact_Admissions[PatientID]) counts unique patients who have at least one admission in the current filter context, not the number of rows in Dim_Patients.
  • Counting from the fact table (not the dimension table) ensures the number automatically respects whatever date, department or diagnosis filters are active on the page.
Why this measure exists: Distinguishes 'how many people were treated' from 'how many admissions happened', since one patient can be admitted more than once.
Impact on the dashboard: Placed next to Total Admissions on the Executive Overview KPI row; the gap between the two numbers visually communicates the readmission/repeat-visit pattern.

Total Revenue

Used on: Financial & Billing Performance
Total Revenue = SUM(Fact_Billing[ServiceCostNGN])

Line by line:

  • SUM(Fact_Billing[ServiceCostNGN]) adds up the full billed cost of every service line currently in context, before any insurance coverage is subtracted.
Why this measure exists: Represents gross hospital revenue billed, which is the starting point before splitting into insurance-covered and patient-payable portions.
Impact on the dashboard: The largest KPI card on the Financial page and the value summed on the Revenue by Service Type column chart.

Total Insurance Covered

Used on: Financial & Billing Performance
Total Insurance Covered = SUM(Fact_Billing[InsuranceCoveredNGN])

Line by line:

  • SUM(Fact_Billing[InsuranceCoveredNGN]) adds up the portion of every bill that NHIS, an HMO, or another insurer paid on the patient's behalf.
Why this measure exists: Needed as its own measure so the coverage ratio and the patient out-of-pocket burden can both be calculated from it.
Impact on the dashboard: Feeds directly into Insurance Coverage % and is plotted alongside Total Revenue on a clustered column chart of Revenue by Insurance Type.

Total Patient Payable

Used on: Financial & Billing Performance
Total Patient Payable = SUM(Fact_Billing[PatientPayableNGN])

Line by line:

  • SUM(Fact_Billing[PatientPayableNGN]) adds up the amount patients are personally responsible for across the currently filtered bills.
Why this measure exists: Surfaces the out-of-pocket burden on patients, an important story for a Nigerian hospital where InsuranceType varies widely by patient.
Impact on the dashboard: Displayed as a KPI card and used as the base of the Out-of-Pocket % measure below.

Insurance Coverage %

Used on: Financial & Billing Performance
Insurance Coverage % = DIVIDE([Total Insurance Covered], [Total Revenue], 0)

Line by line:

  • [Total Insurance Covered] and [Total Revenue] are both measure references, so this measure automatically recalculates correctly no matter what filters are applied - it is not tied to a fixed set of rows.
  • DIVIDE(numerator, denominator, 0) is used instead of the plain / operator because DIVIDE safely returns the third argument (0 in this case) instead of throwing a divide-by-zero error whenever Total Revenue is blank, for example on a page filtered to a period with no billing activity.
Why this measure exists: Turns two raw currency numbers into a single percentage that is meaningful and easy to read on a KPI card or gauge.
Impact on the dashboard: Shown as a percentage KPI on the Financial page; also usable as the value of a gauge visual with a target such as 60%.

Out-of-Pocket %

Used on: Financial & Billing Performance
Out-of-Pocket % = DIVIDE([Total Patient Payable], [Total Revenue], 0)

Line by line:

  • Structurally identical to Insurance Coverage % but numerator and denominator are swapped in meaning; together the two measures should sum to 100% for any given filter context, which is a useful validation check to teach students.
Why this measure exists: Highlights financial exposure carried directly by patients, an important equity and access-to-care metric.
Impact on the dashboard: Used on a 100% stacked bar chart of Insurance Coverage % versus Out-of-Pocket % broken down by InsuranceType.

Collected Revenue

Used on: Financial & Billing Performance
Collected Revenue = CALCULATE([Total Revenue], Fact_Billing[PaymentStatus] = "Paid")

Line by line:

  • CALCULATE takes the existing [Total Revenue] measure and overrides the filter context by adding a new filter: Fact_Billing[PaymentStatus] = "Paid".
  • Any other filters already active on the report (department slicer, date slicer and so on) are preserved and combined with this new filter using AND logic, which is CALCULATE's default behaviour.
Why this measure exists: Isolates revenue that has actually been received in cash or settled by an insurer, as opposed to revenue that has merely been billed.
Impact on the dashboard: The numerator of the Collection Rate % measure, and also shown on its own as a KPI card labelled 'Cash Collected'.

Collection Rate %

Used on: Financial & Billing Performance
Collection Rate % = DIVIDE([Collected Revenue], [Total Revenue], 0)

Line by line:

  • Divides fully paid revenue by total billed revenue to express how effectively the hospital is turning bills into cash.
Why this measure exists: A classic revenue-cycle KPI for any billing dashboard; low values indicate a growing accounts-receivable problem.
Impact on the dashboard: Displayed as a KPI card with conditional formatting (green above 70%, amber 50-70%, red below 50%) to teach students how to apply data-bars and colour rules to a measure.

Average Length of Stay

Used on: Admissions & Operations
Average Length of Stay = AVERAGE(Fact_Admissions[LengthOfStayDays])

Line by line:

  • AVERAGE(Fact_Admissions[LengthOfStayDays]) computes the arithmetic mean of the LengthOfStayDays column across every admission row in the current filter context, including same-day Outpatient rows where the value is 0.
Why this measure exists: A core hospital operations KPI: longer average stays generally indicate more complex cases, bed-capacity pressure, or process inefficiency.
Impact on the dashboard: Shown as a KPI card and plotted as a monthly trend line on the Admissions & Operations page, letting students spot seasonal spikes.

Average LOS (Inpatient Only)

Used on: Admissions & Operations
Average LOS (Inpatient Only) = CALCULATE([Average Length of Stay], Fact_Admissions[AdmissionType] <> "Outpatient")

Line by line:

  • CALCULATE applies an extra filter, Fact_Admissions[AdmissionType] <> "Outpatient", removing same-day outpatient rows (which always have a length of stay of 0) from the average.
  • This produces a more clinically meaningful number than the unfiltered Average Length of Stay measure, since mixing in hundreds of zero-day outpatient rows would understate true inpatient stay length.
Why this measure exists: Demonstrates how the same base measure can be reused and refined with CALCULATE rather than being rewritten from scratch, which is a core DAX design pattern.
Impact on the dashboard: Placed alongside Average Length of Stay on the same card visual group so students can see, and explain to stakeholders, why the two numbers differ.

Mortality Rate %

Used on: Executive Overview, Admissions & Operations
Mortality Rate % = DIVIDE( CALCULATE([Total Admissions], Fact_Admissions[AdmissionOutcome] = "Deceased"), [Total Admissions], 0 )

Line by line:

  • The inner CALCULATE([Total Admissions], Fact_Admissions[AdmissionOutcome] = "Deceased") counts only the admissions whose outcome is Deceased, while still respecting any Date, Department or Diagnosis filters already on the page.
  • DIVIDE then expresses that count as a percentage of all admissions in the same filter context, returning 0 instead of an error if there were no admissions at all.
Why this measure exists: One of the most sensitive and important quality-of-care KPIs a hospital tracks; students must be taught to present this measure carefully and never on a visual that could expose an individual patient.
Impact on the dashboard: Shown as a single KPI card on the Executive Overview page only, deliberately not broken down to a granularity that could identify an individual case.

Emergency Admission %

Used on: Executive Overview
Emergency Admission % = DIVIDE( CALCULATE([Total Admissions], Fact_Admissions[AdmissionType] = "Emergency"), [Total Admissions], 0 )

Line by line:

  • Same CALCULATE-then-DIVIDE pattern as Mortality Rate %, filtered instead to AdmissionType = "Emergency".
Why this measure exists: Tells management what proportion of hospital activity is unplanned and reactive versus planned (Elective, Outpatient, Referral), which has staffing and resourcing implications.
Impact on the dashboard: Displayed as a gauge visual with an informal target band, and reused as one slice of the Admission Type donut chart on the Executive Overview page.

Total Treatment Cost

Used on: Doctor & Department Performance
Total Treatment Cost = SUM(Fact_Treatments[TreatmentCostNGN])

Line by line:

  • SUM(Fact_Treatments[TreatmentCostNGN]) adds up the cost of every treatment row in the current filter context.
Why this measure exists: A separate cost signal from Total Revenue (which comes from Fact_Billing), useful for comparing clinical cost intensity by department.
Impact on the dashboard: The value field on the Average Treatment Cost by Department column chart, after being divided by admission count in the next measure.

Average Treatment Cost per Admission

Used on: Doctor & Department Performance
Average Treatment Cost per Admission = DIVIDE([Total Treatment Cost], [Total Admissions], 0)

Line by line:

  • Divides total treatment spend by total admissions in the same filter context, producing a per-case cost figure that is comparable across departments of very different sizes.
Why this measure exists: Raw treatment cost totals are misleading when comparing a large department like Internal Medicine against a small one like Psychiatry; a per-admission figure levels the comparison.
Impact on the dashboard: The primary value on the department comparison column chart on the Doctor & Department Performance page.

Doctor Caseload

Used on: Doctor & Department Performance
Doctor Caseload = DISTINCTCOUNT(Fact_Admissions[AdmissionID])

Line by line:

  • Identical formula to Total Admissions, but given a distinct measure name so that when it is placed in a visual with DoctorID (from Dim_Doctors) in the axis, its label reads naturally as 'Doctor Caseload' rather than the generic 'Total Admissions'.
Why this measure exists: A small but important lesson in measure naming: the same DAX logic can be exposed under different, context-appropriate names for readability on different visuals.
Impact on the dashboard: Used as the value on the Top 10 Doctors by Admissions Handled bar chart.

Revenue by Payment Date (USERELATIONSHIP demo)

Used on: Financial & Billing Performance
Revenue by Payment Date = CALCULATE( [Total Revenue], USERELATIONSHIP(Dim_Date[Date], Fact_Admissions[DischargeDate]) )

Line by line:

  • USERELATIONSHIP(Dim_Date[Date], Fact_Admissions[DischargeDate]) temporarily activates the otherwise-inactive relationship between Dim_Date and the DischargeDate column, for the duration of this single CALCULATE call only.
  • Wrapping [Total Revenue] inside that CALCULATE means the measure now filters by discharge date instead of the model's default admission-date relationship, without permanently changing which relationship is active for every other visual in the report.
Why this measure exists: This measure exists purely as a teaching example of USERELATIONSHIP - the single most important DAX function for handling a model with more than one date column pointing at the same fact table.
Impact on the dashboard: Placed on a dedicated 'DAX Concepts' tooltip page so students can compare its output against the default Total Revenue by admission month and see the difference explained.

Admissions Growth % (MoM)

Used on: Executive Overview
Admissions Growth % MoM = VAR CurrentMonthAdmissions = [Total Admissions] VAR PreviousMonthAdmissions = CALCULATE( [Total Admissions], DATEADD('Dim_Date'[Date], -1, MONTH) ) RETURN DIVIDE(CurrentMonthAdmissions - PreviousMonthAdmissions, PreviousMonthAdmissions, 0)

Line by line:

  • VAR CurrentMonthAdmissions stores the value of [Total Admissions] for whatever month is currently in filter context, so the value only has to be evaluated once even though it is referenced later.
  • VAR PreviousMonthAdmissions uses CALCULATE with DATEADD('Dim_Date'[Date], -1, MONTH) to shift the entire filter context back by exactly one month and re-evaluate [Total Admissions] inside that shifted context.
  • DATEADD requires Dim_Date to be marked as an official Date Table with a contiguous, gap-free Date column, which is exactly why the Mark as Date Table step is a mandatory task earlier in this project.
  • RETURN DIVIDE(...) calculates the percentage change between the two variables, safely returning 0 if the previous month had no admissions.
Why this measure exists: Teaches the VAR/RETURN pattern for readable, efficient DAX, and introduces time intelligence functions that depend on a properly configured date table.
Impact on the dashboard: Plotted as a secondary line, on a combo chart, against the Total Admissions column chart on the Executive Overview page.

Weekend Admissions %

Used on: Admissions & Operations
Weekend Admissions % = DIVIDE( CALCULATE([Total Admissions], 'Dim_Date'[WeekdayWeekend] = "Weekend"), [Total Admissions], 0 )

Line by line:

  • CALCULATE filters admissions down to only those whose AdmissionDate falls on a date flagged Weekend in Dim_Date, relying on the active Dim_Date to Fact_Admissions[AdmissionDate] relationship to make that filter flow through correctly.
  • DIVIDE then expresses that subset as a share of all admissions in the current context.
Why this measure exists: A simple, practical example of filtering through a related dimension table rather than filtering the fact table directly, reinforcing how relationships propagate filters in DAX.
Impact on the dashboard: Shown as a small multiple card comparing Weekday versus Weekend average admissions per day on the Admissions & Operations page.

Cross-Page Consistency

Add a Year slicer (Dim_Date[Year]) and a Department slicer (Dim_Departments[DepartmentName]) to every page in the same top-right position. Select both, go to the View ribbon, open Sync Slicers, and tick every page so a filter choice on Page 1 automatically applies across Pages 2 to 5. Add five navigation buttons (Insert > Buttons > Blank, with Action type set to Page Navigation) in a consistent header band so users never need the page tabs at the bottom.

6. Step 5 - Quality Check & Publish

1
Click through every slicer combination on every page and confirm no card visual shows (Blank) and no chart shows an empty plot area.
2
Right-click each measure and use Quick Measure or the Performance Analyzer (View ribbon) to confirm no visual takes longer than roughly one second to render on this dataset size.
3
Check that MonthName axes read January to December in calendar order, confirming the Sort By Column setting on Dim_Date took effect.
4
Verify Mortality Rate % and Collection Rate % conditional formatting rules trigger correctly by temporarily filtering to a department or month where the values cross the threshold.
5
Confirm the two inactive relationships remain dashed in Model view, and that Revenue by Payment Date genuinely returns a different number than Total Revenue when filtered to a single month, proving USERELATIONSHIP is working.
6
Save the .pbix file, then use File > Publish to publish the report to the Prodigy Training Hub Power BI Service workspace for the class.
