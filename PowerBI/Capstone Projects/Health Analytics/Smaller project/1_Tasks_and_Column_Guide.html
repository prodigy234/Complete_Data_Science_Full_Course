1. How to Use This File

This is the problem brief for the Hospital Health Analytics Power BI training project. It does not contain the answers - it tells you what the dataset contains, what every column means, which relationships you must build in the Model view, which DAX measures you must write, and exactly what each of the five dashboard pages must contain. Work through it in order: understand the columns first, then build the model, then the DAX measures, then the dashboard pages. A separate file, the Solutions Walkthrough, shows the fully worked solution end to end once you have attempted each task yourself.

2. Dataset Overview

The workbook Hospital_Health_Analytics_Dataset.xlsx contains 8 related tables built as a star/snowflake schema: 5 dimension tables and 3 fact tables. Study the table below before opening Power BI.

Column Guide - Dim_Patients

Holds every descriptive attribute of a patient. In the star schema this table sits on the 'one' side of a one-to-many relationship with Fact_Admissions, so a single patient record can be linked to many admission records over time.

ColumnData TypeWhat it means / your task
PatientIDText (Key)Unique identifier for each patient, formatted as PAT0001, PAT0002 and so on. This is the primary key of Dim_Patients and the field used to build the relationship to Fact_Admissions[PatientID]. It must never repeat within this table.
FirstNameTextThe patient's given name. Used mainly for display in tables, tooltips and drillthrough pages rather than for analysis, since first names are not statistically meaningful groupings.
LastNameTextThe patient's family name. Often concatenated with FirstName using a calculated column such as Full Name = Dim_Patients[FirstName] & " " & Dim_Patients[LastName] so a single clean field can be used on visuals.
GenderText (Male/Female)Biological sex of the patient. This is a core segmentation field used to slice admissions, diagnoses and revenue by gender on the demographics dashboard page.
DateOfBirthDateThe patient's date of birth. This column is the source for the calculated Age field and can be used to build custom age bands with a calculated column or a DAX measure using SWITCH and TRUE().
AgeWhole NumberPre-computed age in years as at 2026. Used to build age-band groupings (0-17, 18-35, 36-55, 56-75, 76+) that feed the demographics and disease burden visuals.
StateOfOriginTextNigerian state the patient is associated with. This is the field used to build the geographic 'Admissions by State' bar chart and can also power a Filled Map or Azure Map visual if the student enables it.
CityTextCity within the state of origin. Provides a second, more granular geographic level beneath StateOfOrigin, useful for a drill-down hierarchy (State to City).
BloodGroupTextOne of the eight standard blood groups (O+, O-, A+, A-, B+, B-, AB+, AB-). Included as a categorical attribute students can use for slicers and for practising DISTINCTCOUNT and COUNTROWS measures.
GenotypeTextHaemoglobin genotype (AA, AS, SS, AC). Relevant in the Nigerian clinical context, particularly for cross-analysis with Sickle Cell Crisis admissions in Dim_Diagnosis.
InsuranceTypeTextHow the patient's care is funded: NHIS, one of several HMOs, Private Pay or Uninsured. This field is central to the financial dashboard page because it drives how much of a bill is covered versus patient-payable.
MaritalStatusTextSingle, Married, Divorced or Widowed. A demographic attribute used mainly for slicers and cross-tab tables rather than as a primary KPI driver.
OccupationTextThe patient's stated occupation. Included so students can practise grouping free-text-like categorical data and building a Top N occupations visual.
PhoneNumberTextNigerian-format phone number. Included for realism only; it should never be used on a visual and is a good example of a column students should hide in the Model view to keep the field list clean for report users.
RegistrationDateDateThe date the patient first registered with the hospital. Can be used to build a 'New Patients Registered' trend measure that is independent of the admissions trend.

Column Guide - Dim_Doctors

Describes every doctor who can be attached to an admission or a treatment. It also links onward to Dim_Departments, which makes the model a snowflake rather than a pure star for this branch, giving students a real example of a snowflaked dimension.

ColumnData TypeWhat it means / your task
DoctorIDText (Key)Unique identifier such as DOC001. Primary key of Dim_Doctors and the field used on the relationship to Fact_Admissions[DoctorID] and Fact_Treatments[AdministeredByDoctorID].
FirstNameTextDoctor's given name, used for labelling visuals such as 'Top 10 Doctors by Admissions Handled'.
LastNameTextDoctor's family name. Combine with FirstName and a 'Dr.' prefix in a calculated column for a clean display name.
GenderTextDoctor's gender, usable for workforce composition analysis by department.
SpecialtyTextClinical specialty such as Cardiology or Paediatrics. Should align conceptually with the department the doctor sits in, and is a useful field for a matrix visual of Department by Specialty.
DepartmentIDText (Foreign Key)Links each doctor to the department they belong to via Dim_Departments[DepartmentID]. This is the foreign key that creates the snowflake relationship Dim_Departments (one) to Dim_Doctors (many).
YearsOfExperienceWhole NumberNumber of years the doctor has practised. Used on the scatter chart that compares experience against admissions handled on the doctor performance page.
QualificationTextAcademic and fellowship qualifications, for example MBBS, FWACS. A descriptive attribute, not typically used as a slicer, but good for drillthrough detail pages.
HospitalBranchTextPhysical branch the doctor is primarily based at (Ikeja Main Campus, Ota Annex, Lekki Diagnostic Centre). Useful for a branch-level filter across all dashboard pages.
DateJoinedDateThe date the doctor joined the hospital. Can support a simple tenure or headcount-growth analysis, separate from the main admissions Date table relationship.

Column Guide - Dim_Departments

The smallest dimension table in the model but an important one: it is referenced directly by Fact_Admissions and indirectly (through Dim_Doctors) a second time, which is exactly the kind of structure that teaches students to read a real Model view diagram.

ColumnData TypeWhat it means / your task
DepartmentIDText (Key)Unique identifier such as DPT01. Primary key of Dim_Departments, referenced by Fact_Admissions[DepartmentID] and Dim_Doctors[DepartmentID].
DepartmentNameTextFull department name, for example Accident & Emergency or Oncology. This is the field used as the axis on the 'Admissions by Department' column chart.
BuildingTextThe physical building the department occupies. A simple attribute for grouping departments spatially.
FloorNumberWhole NumberFloor of the building. Included mainly as an example of a numeric attribute that should not be aggregated (it should be set to Don't Summarize in the field's default summarization property).
HeadOfDepartmentTextName of the consultant heading the department. Useful for tooltip or drillthrough detail rather than aggregate visuals.
AnnualBudgetNGNCurrency (Whole Number)Department's approved annual budget in Naira. Can be compared against actual revenue or treatment cost generated by that department to build a simple budget-versus-actual visual.

Column Guide - Dim_Diagnosis

Provides the clinical classification for every admission. This table is what makes the 'Disease Burden' analysis on the demographics page possible, since every admission points to exactly one diagnosis.

ColumnData TypeWhat it means / your task
DiagnosisIDText (Key)Unique identifier such as DX001. Primary key of Dim_Diagnosis and the field used to relate to Fact_Admissions[DiagnosisID].
DiagnosisCodeTextA short fictional clinical code in the format NGD-001, included so students can practise combining a code and a name into a single label using a calculated column.
DiagnosisNameTextThe human-readable diagnosis, for example Malaria, Hypertension or Type 2 Diabetes Mellitus. This is the field placed on the 'Top Diagnoses' bar chart and treemap.
DiagnosisCategoryTextBroader clinical grouping such as Infectious Disease, Cardiovascular or Trauma. Used to roll many individual diagnoses up into a manageable number of categories for the stacked bar chart.
SeverityLevelTextOne of Low, Moderate, High or Critical. A key field for cross-analysis with AdmissionOutcome, since severity is expected to correlate with mortality and length of stay.

Column Guide - Dim_Date

A dedicated, contiguous calendar table is mandatory best practice in Power BI. It is what allows time intelligence DAX functions (TOTALYTD, SAMEPERIODLASTYEAR, DATEADD and similar) to work correctly, and in this model it plays multiple roles because three different fact tables each have their own date column that needs to relate back to it.

ColumnData TypeWhat it means / your task
DateDate (Key)The calendar date itself, one row per day with no gaps. This is the primary key of Dim_Date and must be marked as a Date Table in Power BI (Table Tools > Mark as Date Table) using this column.
DayWhole NumberDay of the month (1-31). Rarely used alone but occasionally useful for day-of-month seasonality checks.
DayNameTextFull weekday name (Monday, Tuesday and so on). Used together with WeekdayWeekend to study whether emergency admissions spike on particular days.
MonthNumberWhole NumberNumeric month (1-12). Used to sort MonthName correctly on the X-axis, since Power BI sorts text columns alphabetically unless a Sort By Column is set.
MonthNameTextFull month name (January, February and so on). This is the field placed on the axis of every monthly trend chart in the project; it must have Sort By Column set to MonthNumber.
QuarterWhole NumberCalendar quarter (1-4). Used to build quarterly cards and slicers for executives who prefer a higher-level time view.
YearWhole NumberCalendar year (2023 or 2024 in this dataset). The field most commonly placed in a slicer at the top of every dashboard page.
WeekdayWeekendTextFlags each date as Weekday or Weekend. Supports a simple DAX measure comparing average admissions on weekdays versus weekends.
FiscalYearTextFiscal year label such as FY2023. Included so students can see how a fiscal calendar would be added even though it mirrors the calendar year in this dataset.

Column Guide - Fact_Admissions

The central fact table of the model. Almost every DAX measure in this project starts by aggregating a column from Fact_Admissions or by counting rows in it, and every other fact table (Billing, Treatments) hangs off it through AdmissionID.

ColumnData TypeWhat it means / your task
AdmissionIDText (Key)Unique identifier for the encounter, formatted ADM00001. Primary key of Fact_Admissions and the 'one' side of the relationship to Fact_Billing[AdmissionID] and Fact_Treatments[AdmissionID].
PatientIDText (Foreign Key)Links the admission to Dim_Patients[PatientID]. Many admissions can point to the same patient, which is exactly what makes this a one-to-many relationship from the patient's perspective.
DoctorIDText (Foreign Key)Links the admission to the attending doctor in Dim_Doctors[DoctorID]. Used for the 'Admissions Handled per Doctor' visual on the performance page.
DepartmentIDText (Foreign Key)Links the admission to Dim_Departments[DepartmentID]. This is the single most-used slicing field across the whole project after Date.
DiagnosisIDText (Foreign Key)Links the admission to Dim_Diagnosis[DiagnosisID]. Every disease-burden visual ultimately depends on this column.
AdmissionDateDateThe date the patient was admitted. This is the column that should carry the ACTIVE relationship to Dim_Date[Date], because most reporting in this project (monthly admission trends, YTD admissions) is naturally admission-date-based.
DischargeDateDateThe date the patient was discharged. This column should carry an INACTIVE relationship to Dim_Date[Date], activated only inside specific measures with USERELATIONSHIP when a discharge-date view is genuinely needed.
LengthOfStayDaysWhole NumberNumber of days between AdmissionDate and DischargeDate (0 for same-day outpatient encounters). This is the core numeric field behind every Average Length of Stay measure.
AdmissionTypeTextEmergency, Elective, Outpatient or Referral. A key operational field used to build the donut chart on the executive overview page and the Emergency Admission % measure.
RoomTypeTextGeneral Ward, Private Room, Semi-Private Room, ICU, Maternity Ward, Paediatric Ward, or 'N/A - Outpatient'. Used in the department-by-room-type matrix on the operations page.
BedNumberTextA short bed reference code. Included for realism and drillthrough detail; not intended to be aggregated or charted directly.
AdmissionOutcomeTextRecovered - Discharged, Referred to Another Facility, Discharged Against Medical Advice, Deceased, or Under Treatment. This is the field the Mortality Rate % measure filters on, and it is one of the most sensitive and important fields in the whole dataset for a hospital's quality-of-care story.

Column Guide - Fact_Billing

Drives the entire financial dashboard page. A small proportion of admissions (about 12%) have two billing lines instead of one, which is deliberate: it demonstrates a genuine one-to-many relationship between Fact_Admissions and Fact_Billing rather than a disguised one-to-one relationship.

ColumnData TypeWhat it means / your task
BillIDText (Key)Unique identifier for the billing line, formatted BIL00001. Primary key of Fact_Billing.
AdmissionIDText (Foreign Key)Links the bill back to Fact_Admissions[AdmissionID]. This relationship is Fact-to-Fact, which is a valid and common pattern once one of the two tables (Fact_Admissions here) is treated as the conceptual 'one' side.
ServiceTypeTextThe category of service billed: Consultation, Laboratory Tests, Imaging, Surgery, Ward Admission Fee, Medication, Physiotherapy, Delivery Fee, ICU Fee or Dialysis. This is the axis field for the Revenue by Service Type column chart.
ServiceCostNGNCurrency (Whole Number)The full cost of the service line in Naira before any insurance coverage is applied. This is the column summed by the Total Revenue measure.
InsuranceCoveredNGNCurrency (Whole Number)The portion of ServiceCostNGN paid by NHIS, an HMO, or other insurance. Summed by the Total Insurance Covered measure and used to compute the coverage ratio.
PatientPayableNGNCurrency (Whole Number)ServiceCostNGN minus InsuranceCoveredNGN; the amount the patient is personally responsible for. Central to the out-of-pocket burden analysis.
PaymentStatusTextPaid, Partially Paid, Pending or Insurance Processing. Drives the payment-status donut chart and the Collection Rate % measure.
PaymentDateDateThe date the payment was actually received or settled. This column should carry its own relationship to Dim_Date[Date], separate from the admission-date relationship on Fact_Admissions, because financial reporting is naturally payment-date based rather than admission-date based.
PaymentMethodTextCash, Bank Transfer, POS/Card, HMO Settlement or NHIS Settlement. A useful slicer for a finance-department view of collections.

Column Guide - Fact_Treatments

The most granular fact table in the model, at roughly 2.6 treatment rows for every admission on average. It supports clinical operations analysis such as which treatments are most common and how much they cost, independent of the billing table.

ColumnData TypeWhat it means / your task
TreatmentIDText (Key)Unique identifier for the treatment row, formatted TRT00001. Primary key of Fact_Treatments.
AdmissionIDText (Foreign Key)Links the treatment back to Fact_Admissions[AdmissionID]. One admission typically has between one and five treatment rows.
TreatmentNameTextThe specific treatment or procedure performed, for example IV Fluid Administration or Blood Transfusion. Used on the 'Most Common Treatments' visual.
TreatmentDateDateThe date the treatment was administered, falling between the admission and discharge dates. This column carries its own relationship to Dim_Date[Date] for clinical operations trend analysis.
TreatmentCostNGNCurrency (Whole Number)Cost of the individual treatment in Naira. Summed to build the Average Treatment Cost by Department visual on the doctor and department performance page.
TreatmentOutcomeTextImproved, Stable, No Change, Deteriorated or Resolved. A clinical-quality field that can be cross-analysed against SeverityLevel from Dim_Diagnosis.
AdministeredByDoctorIDText (Foreign Key)Links the treatment to the doctor who administered it, via Dim_Doctors[DoctorID]. Note this is a second, independent relationship from Dim_Doctors into the model, alongside Fact_Admissions[DoctorID].

4. DAX Measures To Be Built

Build the following measures, in this order, inside a dedicated Measures table. For each one, the goal (why it exists) is given - your task is to write the DAX yourself before checking the Solutions file.

Measure NameUsed OnYour Task (goal of the measure)
Total AdmissionsUsed on every pageThis is the foundation KPI of the entire report. Almost every other measure either builds on it (as a denominator) or is filtered the same way it is.
Total PatientsExecutive Overview, DemographicsDistinguishes 'how many people were treated' from 'how many admissions happened', since one patient can be admitted more than once.
Total RevenueFinancial & Billing PerformanceRepresents gross hospital revenue billed, which is the starting point before splitting into insurance-covered and patient-payable portions.
Total Insurance CoveredFinancial & Billing PerformanceNeeded as its own measure so the coverage ratio and the patient out-of-pocket burden can both be calculated from it.
Total Patient PayableFinancial & Billing PerformanceSurfaces the out-of-pocket burden on patients, an important story for a Nigerian hospital where InsuranceType varies widely by patient.
Insurance Coverage %Financial & Billing PerformanceTurns two raw currency numbers into a single percentage that is meaningful and easy to read on a KPI card or gauge.
Out-of-Pocket %Financial & Billing PerformanceHighlights financial exposure carried directly by patients, an important equity and access-to-care metric.
Collected RevenueFinancial & Billing PerformanceIsolates revenue that has actually been received in cash or settled by an insurer, as opposed to revenue that has merely been billed.
Collection Rate %Financial & Billing PerformanceA classic revenue-cycle KPI for any billing dashboard; low values indicate a growing accounts-receivable problem.
Average Length of StayAdmissions & OperationsA core hospital operations KPI: longer average stays generally indicate more complex cases, bed-capacity pressure, or process inefficiency.
Average LOS (Inpatient Only)Admissions & OperationsDemonstrates how the same base measure can be reused and refined with CALCULATE rather than being rewritten from scratch, which is a core DAX design pattern.
Mortality Rate %Executive Overview, Admissions & OperationsOne of the most sensitive and important quality-of-care KPIs a hospital tracks; students must be taught to present this measure carefully and never on a visual that could expose an individual patient.
Emergency Admission %Executive OverviewTells management what proportion of hospital activity is unplanned and reactive versus planned (Elective, Outpatient, Referral), which has staffing and resourcing implications.
Total Treatment CostDoctor & Department PerformanceA separate cost signal from Total Revenue (which comes from Fact_Billing), useful for comparing clinical cost intensity by department.
Average Treatment Cost per AdmissionDoctor & Department PerformanceRaw treatment cost totals are misleading when comparing a large department like Internal Medicine against a small one like Psychiatry; a per-admission figure levels the comparison.
Doctor CaseloadDoctor & Department PerformanceA small but important lesson in measure naming: the same DAX logic can be exposed under different, context-appropriate names for readability on different visuals.
Revenue by Payment Date (USERELATIONSHIP demo)Financial & Billing PerformanceThis measure exists purely as a teaching example of USERELATIONSHIP - the single most important DAX function for handling a model with more than one date column pointing at the same fact table.
Admissions Growth % (MoM)Executive OverviewTeaches the VAR/RETURN pattern for readable, efficient DAX, and introduces time intelligence functions that depend on a properly configured date table.
Weekend Admissions %Admissions & OperationsA simple, practical example of filtering through a related dimension table rather than filtering the fact table directly, reinforcing how relationships propagate filters in DAX.

6. Full Task Checklist

Section A - Data Preparation Tasks

Open Hospital_Health_Analytics_Dataset.xlsx and review the Read Me sheet to understand the table inventory before touching Power BI.
In Power BI Desktop, use Get Data > Excel Workbook to import all 8 tables (Dim_Patients, Dim_Doctors, Dim_Departments, Dim_Diagnosis, Dim_Date, Fact_Admissions, Fact_Billing, Fact_Treatments). Do not import the Read Me sheet.
In Power Query Editor, confirm each column has the correct data type: text keys should be Text, all date columns should be Date, and every NGN currency column should be Whole Number or Fixed Decimal Number, not Text.
Rename the query for each table to match the sheet name exactly so relationships and DAX formulas in this project line up with what is documented here.
Disable Load for any staging queries you create during transformation, keeping only the 8 final tables loaded to the model.
Close and Apply the Power Query changes and confirm the model loads with the row counts stated in the Read Me sheet (450 patients, 900 admissions, 1,025 billing lines, 2,362 treatments).

Section B - Data Modelling Tasks (Relationships & Cardinality)

Switch to Model view and arrange the 8 tables so the 5 dimension tables sit above the 3 fact tables, roughly mirroring a star schema layout.
Build all relationships listed in the Relationships section of this document, setting the correct cardinality (One-to-Many in every case) and cross filter direction (Single, unless a task states otherwise).
Deliberately leave the Dim_Date to Fact_Admissions[DischargeDate] relationship INACTIVE, and the Dim_Doctors to Fact_Treatments[AdministeredByDoctorID] relationship INACTIVE, since each table can only have one active path to a given fact table.
Mark Dim_Date as an official Date Table in Power BI (right click the table > Mark as Date Table), pointing to the Date column, so time intelligence DAX functions work correctly.
Set Sort By Column on Dim_Date[MonthName] to Dim_Date[MonthNumber] so month names display in calendar order rather than alphabetical order on every chart axis.
Hide technical or non-analytical columns from report view (PhoneNumber, BedNumber, all *ID key columns not needed on visuals) to keep the field list clean for report users.
Create a Full Name calculated column on Dim_Patients and on Dim_Doctors, concatenating FirstName and LastName (with a 'Dr.' prefix for doctors).
Create an Age Band calculated column on Dim_Patients using SWITCH(TRUE()) logic with the bands 0-17, 18-35, 36-55, 56-75, 76+.

Section C - DAX Measure Building Tasks

Create a dedicated Measures table (a blank table with no columns, used purely to organise measures) and move every measure below into it.
Build Total Admissions, Total Patients, Total Revenue, Total Insurance Covered, and Total Patient Payable as base aggregation measures first.
Build Insurance Coverage %, Out-of-Pocket %, Collected Revenue and Collection Rate % as ratio measures on top of the base measures, using DIVIDE rather than the / operator throughout.
Build Average Length of Stay and Average LOS (Inpatient Only), and explain in your own words why the two numbers differ.
Build Mortality Rate % and Emergency Admission % using the CALCULATE-then-DIVIDE pattern, and write a one-paragraph note on why Mortality Rate % should never be broken down to an individually identifiable level.
Build Total Treatment Cost, Average Treatment Cost per Admission and Doctor Caseload for the performance page.
Build the Revenue by Payment Date measure using USERELATIONSHIP to activate the inactive DischargeDate relationship, and confirm its output differs from Total Revenue when sliced by month.
Build Admissions Growth % MoM using the VAR/RETURN pattern with DATEADD, and confirm it returns blank (not an error) for January 2023, the first month with no prior month available.
Build Weekend Admissions % and confirm it correctly filters through Dim_Date[WeekdayWeekend] into Fact_Admissions.
Apply conditional formatting (font colour or data bars) to Mortality Rate % and Collection Rate % on their respective card visuals.
